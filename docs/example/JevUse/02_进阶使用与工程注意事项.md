# 进阶使用与工程注意事项

## 1. 先定义决策，再写问题

Jev 的问题应对应一个边界清楚、程序可以消费的判断。把“请分析这张工单并决定怎么处理”拆成多个原子问题通常更稳：

- `Choice`：应该路由给哪个队列；
- `Score`：严重度或紧急度处于哪个有序等级；
- `Noul`：是否明确要求退款、是否需要人工复核。

多个问题可以放在一次请求中。官方说明这些问题针对同一个 `state` 独立评估，并在一次请求中并行返回；业务逻辑仍由代码负责组合。

## 2. 设计 `state` 和 `instructions`

`state` 可为字符串、JSON 对象或数组。建议只放会改变当前判断、且可以审计的事实。问题 ID 只是响应映射键，不会代替 `instructions` 传递语义。

对于较复杂的问题，可以把 `instructions` 或 `criteria` 写成结构化对象，在字段中分别放问题、背景、边界和示例。先用短字符串验证任务，再逐步结构化，便于比较实验结果。

`Choice` 的候选项要互斥、覆盖业务范围，并在需要时提供 `other` 或 `none_of_the_above`。`Score` 的 criteria 必须按顺序书写，API 文档说明可使用 2 到 10 个等级。`Noul` 可以通过 `criteria.true` 和 `criteria.false` 明确“是”和“否”的边界。

## 3. 如何使用概率和 confidence

`Choice` 返回最高概率的 `choice`、完整的 `probabilities` 和 `confidence`；`Score` 返回概率加权分数、等级说明、分布和 `confidence`；`Noul` 返回 0 到 1 的 `noul` 概率。

不要把 `confidence` 当作一次判断必然正确的概率。它是基于答案分布集中程度的指标。上线前应在自己的标注数据上评估准确率、覆盖率、Brier score/ECE，并预先定义低置信度的处理方式，例如转人工、补充资料或交给生成式模型。

`Score` 可能产生落在等级之间的值。如果业务规则关心是否进入最高等级，应读取该等级的概率，而不是用期望分数替代离散条件。

## 4. 错误、重试和版本

官方 API 文档列出以下常见状态：

| 状态码 | 含义 | 建议 |
|---|---|---|
| `401` | API key 缺失或无效 | 检查服务端环境变量和 Authorization 头 |
| `422` | 请求结构或 question 校验失败 | 记录响应中的字段错误，修正 schema |
| `429` | 超过速率限制 | 指数退避，避免立即重试 |
| `529` | 服务暂时过载 | 指数退避并设置最大重试次数 |

SDK 默认提供重试策略；自己使用 HTTP 时应设置连接和总超时，记录 request id（若响应提供），并避免重复执行不可逆业务动作。正式评测可以固定 `jev-1.13.0`，生产别名使用 `jev-latest` 时保存响应里的实际 `model` 版本。

## 5. 安全和数据边界

- API key 只放在后端环境变量或密钥管理服务中，不放在前端、日志、Notebook 输出或 Git。
- `.env` 已加入项目根目录 `.gitignore`；共享项目时只提交 `.env.example`。
- `state` 会发送到 TypeSafe 服务，发送前要移除不必要的个人信息、凭据和内部秘密，并按组织的数据处理政策评估。
- Jev 输出的 schema 合法性不等于事实正确性。支付、权限、删除、医疗或其他不可逆操作仍应保留确定性规则和人工审批边界。

## 6. 成本和延迟实验

每个请求响应都会返回 `usage.input_tokens` 和 `usage.output_tokens`。实验日志至少保存：时间、模型版本、问题数、候选项数量、输入 token、端到端耗时、HTTP 状态和是否重试。不要只比较模型前向时间；网络、输入长度、服务区域和并发都会影响端到端结果。

同一个 `state` 的多个独立问题应优先合并为一次请求以减少往返，但额外问题仍会增加输入 token。对于重复任务可以按规范化后的 state 与 questions 做缓存，缓存键中应包含模型版本和 schema 版本。

## 7. 与生成式模型的分工

Jev 适合快速的分类、评分、验证和路由。需要写解释、长文本、代码、开放式检索或复杂多步推理时，应交给生成式模型。一个常见架构是：Jev 先做门控和路由，生成式模型处理被选中的复杂路径，再由 Jev 或确定性规则做输出校验。
