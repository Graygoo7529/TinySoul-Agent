# Jev 核心概念与整体说明

本文件把本项目目前对 Jev 的理解整理成一份可反复阅读的导读。它回答三个问题：Jev 到底是什么、一次调用发生了什么、它在 JevKG 和 JevSession 中应该放在哪里。文中把官方文档、本地真实调用和研究判断分开标注。

核查日期：2026-09-23。官方资料入口：[Introduction](https://docs.typesafe.ai/introduction)、[Quick start](https://docs.typesafe.ai/introduction/quickstart)、[API](https://docs.typesafe.ai/api)、[Confidence](https://docs.typesafe.ai/confidence) 和 [Jev 1.13 model notes](https://docs.typesafe.ai/model-jaggedness/jev-1.13)。

## 1. 一句话理解 Jev

Jev 更像一个“把自然语言判断变成类型化概率输出的决策仪表盘”，而不是一个负责写长答案的聊天模型。

可以把它想成机场安检台：输入是旅客资料和安检规则，输出是“放行、拦截、人工复核”以及各自的概率；真正决定是否开门、是否调用工具的程序仍在安检台之后。Jev 的价值在于把原本需要从自由文本中猜测的判断，直接变成程序可以读取的字段。

```text
state（当前事实） + instructions / criteria（判断规则）
                              │
                              ▼
                    Jev / System One
                              │
             ┌────────────────┼────────────────┐
             ▼                ▼                ▼
       Choice 选择       Score 评分        Noul 是/否
       概率+置信度       概率+期望分数      概率+置信度
             └────────────────┼────────────────┘
                              ▼
                  业务代码决定路由、审批或动作
```

官方介绍把 Jev 放在 System One、typed decisions 的位置：它输出预先声明的决策类型，不以自由文本生成作为主要接口。这个定位决定了它适合分类、评分、验证、门控和路由；解释长文、开放式写作、多步规划和代码生成仍应由生成式模型或普通程序承担。

## 2. 一次调用里各部分分别做什么

一个请求可以拆成四层：

| 层 | 作用 | 设计问题 |
|---|---|---|
| `state` | 当前要判断的事实，可为字符串、JSON 对象或数组 | 哪些事实真的会改变判断？哪些信息可以删掉？ |
| `instructions` | 告诉模型要判断什么以及边界 | 问题是否原子、可审计、没有隐藏的第二个问题？ |
| `criteria` / 选项 | 定义“是/否”、评分等级或候选类别 | 选项是否互斥、覆盖业务范围、顺序清楚？ |
| `questions` | 将多个判断绑定到响应键 | 每个键是否对应一个独立、可消费的结果？ |

问题 ID 只是返回结果的映射键，本身不会自动传递语义。真正的语义要写在 `instructions`、选项描述或 `criteria` 中。实践中可以先用短字符串验证路径，再把背景、边界、反例和示例结构化，便于做版本比较。

### 三种基本输出

| 类型 | 它回答什么 | 典型结果 | 适合场景 |
|---|---|---|---|
| `Noul` | “这个条件是否成立？” | `noul: 0.93` | 是否退款、是否需要人工、证据是否支持边 |
| `Choice` | “有限候选中选哪一个？” | `choice`、各选项概率、`confidence` | 队列路由、动作类别、实体候选选择 |
| `Score` | “沿有序等级处于什么位置？” | 期望分数、各等级概率、`confidence` | 严重度、证据强度、上下文充分性 |

`Choice` 的候选项要尽量互斥；必要时显式提供 `other` 或 `none_of_the_above`。`Score` 的 criteria 是有顺序的等级，不能把无序标签硬塞进评分。若业务关心“是否进入最高等级”，应读取该等级概率，而不是只看概率加权后的期望分数，因为期望分数可能落在两个等级之间。

## 3. 多个问题为什么可以放在一次请求里

官方说明同一个请求中的多个问题针对同一份 `state` 独立评估，并在一次请求中并行返回。可以把它想成同一张体检报告同时送给三个专科：心电、血压和体温各自给结果，最后是否住院仍由业务逻辑组合。

例如一张支持工单可以同时询问：

```text
refund_requested  -> Noul：是否明确要求退款？
department         -> Choice：billing / technical / account
urgency            -> Score：低 / 中 / 高 / 紧急
```

这种拆分通常比“请分析工单并给出处理方案”更容易验证。Jev 只负责三个窄判断，程序负责把结果组合成“路由到 billing，并在高紧急度时升级”。问题合并可以减少网络往返，但每增加一个问题都会增加输入 token，也不会自动产生跨问题的推理关系；如果问题之间存在依赖，依赖关系应由代码显式串联。

## 4. 概率、confidence 和真实可靠性

Jev 返回概率分布，通常还返回 `confidence`。最容易产生误解的地方是：`confidence` 表示答案分布有多集中，不等于“这次答案有多大概率是真的”。

可以用两个例子理解：

- `Choice` 的概率是 `[billing: 0.98, technical: 0.01, account: 0.01]`，分布很尖，confidence 通常较高；
- 概率是 `[billing: 0.36, technical: 0.34, account: 0.30]`，模型在候选之间摇摆，confidence 通常较低。

第一种结果仍可能因为输入事实错误而判断错误。因此上线前要在自己的标注集上单独测准确率、覆盖率、混淆矩阵和校准指标（例如 Brier score、ECE），并事先定义低置信度路径：补充信息、转人工、调用生成式模型，或者拒绝执行高风险动作。

对于支付、权限、删除、医疗和其他不可逆动作，概率输出只能作为门控信号，不能替代确定性规则和人工审批。结构合法也不代表事实正确。

## 5. Jev 的能力边界：它擅长窄判断，不擅长什么

官方的 model jaggedness 文档提醒，Jev 对以下任务要谨慎：

- 需要精确计算、计数、日期比较或复杂数学的任务；
- 依赖多层指代、隐含关系或绕行表达的任务；
- `state` 中有大量与问题无关的内容，导致真正证据被淹没；
- 互相矛盾的 instructions、criteria 或输入事实；
- 对抗性、提示注入或试图改变判断规则的文本；
- 要求生成长文本、代码、完整证明或开放式多步规划的任务。

这些限制并不意味着 Jev “不能用”，而是说明边界要前移到系统设计中：先由程序做计算和结构校验，裁剪无关 state，把用户文本当作不可信数据，把生成任务交给生成式模型，再用 Jev 或确定性检查做窄范围验证。

另一个工程约束是输入上下文和媒体类型：官方 API 以文本为主，`state` 使用字符串、对象或数组；本项目当前按官方说明记录 64k 请求上下文以及 state 与最长问题合计约 32k 的限制。图像、音频或视频不能假定会被 Jev 直接理解，必要时先由专门模型转成文本事实。

## 6. 模型版本、别名和实验记录

请求可以使用模型别名，例如 `jev-latest` 或 `jev-preview`，但响应会报告实际使用的版本。本项目真实调用中，别名请求返回的实际模型为 `jev-1.13.0`。因此实验记录至少要保存：

- 请求的模型名和响应中的实际 `model`；
- 问题 schema 版本、候选项数量和样本规模；
- 输入/输出 token、端到端耗时、HTTP 状态和重试次数；
- 低置信度处理策略以及人工标签（如果在做质量评估）。

只保存一次响应可以验证“调用链路通了”，不能推出准确率、校准质量或性能倍数。已有实测结果见[案例与实验记录](./03_案例与实验记录.md)。

## 7. HTTP 与官方 SDK 的关系

HTTP 是最直接的协议核对方式，适合理解请求体、响应体和错误状态；官方 Python SDK 则像一层类型化适配器，主要价值是：

- 用 `Question`、`NoulQuestion`、`ChoiceQuestion`、`ScoreQuestion` 等类型减少手写 schema 错误；
- 通过同步或异步 client 复用连接配置；
- 使用官方 retry policy、异常类型和 `request_id`；
- 通过 `models.list()` 查看账号可用模型；
- 保留 `response_model`、日志和额外请求字段等工程扩展点。

本项目保留两条路径：`examples/jev_client.py` 用标准库发送原始 HTTP，便于协议排查；`examples/sdk_call.py` 用 `typesafe-sdk==0.7.1` 做类型化调用。正式服务可以优先采用 SDK，但仍要保留对原始响应字段、版本和错误码的记录。SDK 的调试日志会隐藏认证头，但请求体可能含有业务数据，因此日志策略仍需由应用控制。

## 8. JevKG：把 Jev 放在知识图谱的“有限决策层”

知识图谱系统通常有候选生成、实体链接、证据检索、冲突处理和图数据库写入等多个环节。Jev 最适合放在候选已经被程序收窄之后：

```text
文档 / 数据源
      │
      ▼
实体识别、候选边生成、证据检索（程序与检索系统）
      │
      ▼
Jev：接受 / 拒绝 / 复核 + 证据强度 + 是否明确支持
      │
      ▼
确定性约束、时间有效性、冲突策略、证据回链、图数据库写入
```

例如对候选三元组“某药物—治疗—某疾病”，`Choice` 可以在接受、拒绝、需要复核之间选择，`Score` 评价证据强度，`Noul` 判断文本是否明确支持该关系。Jev 不负责遍历整个图、替代向量检索或凭空生成可靠三元组；候选生成、来源保留和最终写入必须可审计。详见 [JevKG 应用架构与实验设计](../03_JevKG/03_应用架构与实验设计.md)。

## 9. JevSession：把 Jev 放在 Agent 的“门控层”

Agent 每轮会话都可能面对上下文太长、工具结果不完整、动作风险不一致的问题。Jev 可以用作快速门控器，让生成式模型负责规划，让 Jev 判断是否满足某个窄条件：

```text
会话摘要 + 最近工具结果 + 待执行动作 + 策略约束
                              │
                              ▼
        Jev：是否压缩？动作类别？是否需要确认？上下文够不够？
                              │
               ┌──────────────┼──────────────┐
               ▼              ▼              ▼
          继续观察       可回滚工具       人工确认 / 升级
```

一个删除账号的例子中，Jev 可以同时判断“是否需要用户确认”“动作是否不可逆”“当前上下文是否充分”。即使三个结果都很有把握，真正执行删除仍应经过程序策略和确认流程。Jev 的作用是减少不必要的长模型调用和自由文本解析，不是替代 Agent 的长程规划或安全控制。详见 [JevSession 应用架构与研究问题](../04_JevSession/01_应用架构与研究问题.md)。

## 11. 当前结论与下一步

截至本轮研究，可以较有把握地说：

1. Jev 的核心价值是把有限判断直接输出为类型化概率结果，让程序可以路由、门控和审计。
2. 最重要的工程工作不是写更长的提示，而是设计互斥问题、干净 state、明确 criteria 和低置信度分支。
3. `confidence` 需要通过本地标注数据校准，不能直接当作事实正确率。
4. JevKG 和 JevSession 都适合采用“程序负责事实与动作，Jev 负责窄判断，人工负责高风险例外”的分层架构。
5. 官方 API/SDK 的调用链已经通过少量真实样例验证，但还没有形成质量基准。

下一阶段应优先做三件事：建立带人工标签的小型评测集；比较不同 state、criteria 和问题拆分的误差；为低置信度、冲突证据和不可逆动作制定可执行的回退策略。
