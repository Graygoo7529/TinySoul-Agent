# Core 回答生成与失败反馈改进执行计划

- 日期：2026-10-27
- 状态：`pending`，设计核对完成，准备实施。
- 本轮交付：执行计划与修改预览；尚未修改运行代码、默认资源或测试。
- 依据：当前 `AGENTS.md`、Action/LLM/Context/Session/Workspace 的实现与设计文档，以及此前对回答失败的分析与已确认方向。

## 1. 目标与问题判断

让模型专注于生成回答正文，让执行器负责构造框架结果；让失败反馈说明哪里失败、下一步可以怎样修正。

现有执行链是：Phase2 生成 `core.answer` 参数，Phase3 执行该 Action，Action 再发起一个带 Context 与 TaskPrompt 的 LLM Task。内部模型必须返回 JSON 对象，Core 随后要求对象具有 `text` 字段。这里既有外层 Action 参数协议，又有内层回答包装协议。自然语言正文、引号、代码和列表本身适合回答，却可能因额外的 JSON 包装失败。

Catalog 的 schema 约束模型生成的 **Action 输入参数**，不是统一的 Action 输出 schema。ActionResult 是框架结果，payload 的业务语义由 executor 负责。因此，把 answer 内部生成改为文本，不需要放松外层参数校验，也不需要改变 ActionResult 协议。

另有两个相关问题：

1. answer/reason 的 `references` 输入通过 Core 装配的 Workspace resolver 隐式读取资源，与当前由各 owner Inspect、正文经 Trace 进入 Context 的主线重复，并让 Core 依赖 Workspace 内容服务。
2. 已有失败链路基本完整，但部分反馈只说“缺少调用”“不符合某个分支”，或丢弃 owner 已提供的具体原因；模型难以区分参数有误与 Action 内部生成失败。

本计划解决这些通用问题，不针对某个模型、具体用户问题或某次轨迹添加分支。

## 2. 已明确的设计边界

| 项目 | 决定 |
| --- | --- |
| answer 内部生成 | 使用现有 `AnswerFormat.TEXT`；Core 封装 `text` 与引用元数据 |
| answer 输入 | 必需 `guide_blocks`，可选 `input_blocks`；删除资源加载参数 `references` |
| reason 输入与输出 | 同样删除输入 `references`；保留 `guide_blocks`、`input_blocks`、`output_blocks` 与 JSON 对象结果 |
| Context 与 Skill | 继续由 ActionTaskFactory 组装，保留 domain/action Skill 与现有模型用途绑定 |
| 回答引用 | 保留输出 `references`，从正文的明确内部 Markdown 链接提取 |
| Workspace | compose/describe/analyze 的资源输入仍归 Workspace；其 references/target 语义不迁移到 Core |
| 失败处理 | 沿用局部 Task/Action/Phase 结果及 Runtime bridge；改善反馈，不增加恢复状态机 |
| provider 工具选择 | 不修改 adapter 的 tool choice 策略，不把 provider 的强制选择当作修复手段 |

TinySoul 的 `ToolUse.REQUIRED` 表示至少一次调用；`forced_name` 表示结果中必须包含指定工具。两者都不等于“只允许调用某一个指定工具”。本次保持 Phase1/Phase2 的工具语义及本地校验，不改变 provider 映射或模型链策略。

移除 Core 资源输入也移除它经该入口直接加载 Workspace 图片的能力。当前 resolver 确实会构造 `ImagePart`，而 `workspace.inspect` 对图片只返回元数据；不能把文本 Inspect 当作等价替代。Workspace 自身的图像任务仍保留。通用图片语境或只读视觉分析需要单独设计，本计划不顺带新增此能力。

## 3. 回答生成与结果契约

### 3.1 生成流程

```text
Phase2：生成 core.answer 的 guide_blocks / input_blocks
    ↓ Catalog 校验、归一化
Phase3：CoreAnswerActionExecutor
    ↓ ActionTaskFactory：已安装 Context + TaskPrompt + Skills
LLM Task：生成最终正文（TEXT）
    ↓ 检查调用完成状态与非空文本
Core：构造 ActionResult {text, references}
    ↓ 既有完成检测与必要收尾
TurnOutput → Session / SDK / Endpoint
```

这里的 TEXT 表示不要求 JSON 包装。正文仍可按用户要求包含 Markdown、代码或 JSON；执行器原样保留生成正文，不额外解析、去除代码块或猜测其中的对象。

具体修改：

- `CoreAnswerActionExecutor` 使用 `AnswerFormat.TEXT` 和 `ActionTaskOutput.text`；删除 answer 专用 JSON 字段校验及从输入 sources 回填引用的逻辑。
- `ActionTaskOutput.text` 的 `max_chars` 改为 `int | None = None`。answer 不传文件字符上限；Workspace 等真实工件消费者继续显式传入所属 owner 的限制。
- 文本必须含有非空白内容；校验可使用 `strip()` 判断，成功结果保留原文。
- provider 明确报告输出截断、过滤或未完成时，仍由现有 LLM completion 检查返回失败，不能把半截回答当作成功。沿用当前生成额度、超时和取消语义。
- answer 成功才参与现有 Turn 完成检测。生成失败只形成局部 ActionResult，不发布用户回答。

### 3.2 保留 `text`，澄清 `references`

`text` 已被完成检测、TurnOutput、Session 和展示接口共同使用，命名清楚，无需改成 `answer` 或 `content`。

`references` 有真实消费者：Session 用它记录回答与所引资源的关系。保留该字段，但取消两种来源：模型额外生成的引用数组、所有已加载输入资源的兜底集合。新语义是 **正文显式引用的内部目标**。

实现采用轻量提取：

1. 复用 `infra.references.markdown_references` 的 CommonMark 解析；只提取正文中的真实链接，不扫描普通 prose、代码块或反引号中的 ref 字样。
2. Core 在结果封装处筛选公共内部命名空间 `home:`、`memory:`、`workspace:`、`session:`、`turn:`，按出现顺序去重。完整目标和 fragment 保留；不推算相对链接的基准。
3. 此步骤记录引用的出现，不进行内容读取、存在性检查、redirect 解析或真实性背书。资源语法、可读性及身份解析仍归目标 owner；正文中的链接不会因元数据筛选而被删除。
4. 外部 Web 链接仍完整保留在回答正文；相对路径及其他 URI 不进入这个内部资源列表。没有内部引用时，Core 输出空数组。

示例：

```text
模型正文：
[结论] 方案已完成，具体取舍见 [设计说明](workspace:docs/decision.md#tradeoffs)。

Core 结果：
{
  "text": "[结论] 方案已完成，具体取舍见 [设计说明](workspace:docs/decision.md#tradeoffs)。",
  "references": ["workspace:docs/decision.md#tradeoffs"]
}
```

不为了提取引用注入新的 owner 服务或建立引用注册平台。当前 `ReferenceResolver` 面向资源 canonical identity，且不覆盖全部 Context 引用；它不是“回答引用出现记录”的必要依赖。

Session 继续保存原始 ref 与当时绑定。需顺手补齐一个直接相关的现有缺口：`resource_locator` 当前只识别不带 fragment 的动态 Memory 引用。改为按基础 ref 查当时的 `resolved_references`，使用已有 `append_locator_fragment` 附加 fragment；无绑定时仍标记 `unresolved_origin`，不按今日状态重新解析历史。Workspace 的来源日、普通持久引用和 Trace/Session 引用继续走现有定位协议。

## 4. 简化 Core 输入与资源所有权

### 4.1 参数与提示组装

| Action | 保留参数 | 删除参数 | 内部生成 |
| --- | --- | --- | --- |
| `core.answer` | `guide_blocks`；可选 `input_blocks` | `references` | 文本正文 |
| `core.reason` | `guide_blocks`、`output_blocks`；可选 `input_blocks` | `references` | JSON 对象 |

每个 block 继续使用 `{text, label?}`，不重命名现有字段。`guide_blocks` 描述本次生成目标；`input_blocks` 补充任务局部信息；reason 的 `output_blocks` 描述期望的 JSON 对象结果。当前 Context 已自动进入任务，不要求模型复制整份语境。

缺少正文证据时，先通过对应 owner 的 Inspect/分析能力取得结果，再 answer/reason。已经 Inspect 过的正文仍受现有 Context 容量与披露规则管理；删除隐式加载不意味着每个历史读取结果永远完整可见。信息不足时可以继续读取或询问用户，不能仅凭资源目录推断正文。

Core 的其它引用参数不一并删除：`core.context.inspect` 的定位参数、search 的候选引用和 `core.session.organize` 的来源证据各有独立业务消费者，不属于回答任务的隐式 Workspace 加载入口。

### 4.2 清理依赖

- `_PromptArgumentBuilder` 删除 resolver、`_parse_reference_refs` 和 `source_refs`；剩余提示组装成为同步纯操作，保留参数解析的局部失败语义。
- `register_core_actions`、两个 Core executor 与 `CorePlugin` 删除 Workspace resolver 的传递和专用 `WorkspaceService` 依赖。
- Core 已用于 Context search 的 `ReferenceResolver`、ModelServices 等依赖继续保留，不因名称相近误删。
- 删除失去跨 owner 消费者的 `kernel.context.projection.references` 协议及公共导出。
- Workspace 的解析实现留在 `plugins/workspace/prompts.py`，不再继承上述协议。将必要的提示资源错误移至 Workspace owner，使用模块私有的明确错误类型及有界 `feedback`、reason、摘要字段；删除仅供 Core 使用的 Workspace 顶层导出。
- 清除无消费者的固定文案、旧测试替身与注释，不留兼容参数或空壳协议。旧 `references` 输入由当前 Catalog 正常拒绝。

## 5. 模型可见文案与失败反馈

### 5.1 任务文案与 Catalog

保持已确认的回答风格与协作语义，只调整本次协议相关内容。

answer 的 Expected Output 修改预览：

```diff
 # Expected Output
-Return a JSON object with a string field 'text'. If source refs are used, include a 'references' array of source ref strings.
+Return the final user-facing answer directly, in the requested language and format.
```

answer 的工具简介：

```diff
-Produce the user-facing response that concludes the current User Turn, optionally using read-only references.
+Produce the user-facing response that concludes the current User Turn from the assembled Context and answer guidance.
```

两个 Catalog 的 `input_blocks` 说明各增加一句轻量提示：

```text
The current Context is included automatically. Inspect missing source content before calling this action.
```

删除两个 Catalog 的 references 字段；reason 的 “Analyze workspace references…” 示例改为 “Analyze inspected evidence to decide which approach fits the requirements”。answer Skill 在现有证据说明处补充：

```text
When citing an internal source, use its known ref in a Markdown link where it supports the answer.
```

不要求每个回答强行加引用，不重写整套 Phase 提示、身份文案或回答风格。

### 5.2 沿现有 owner 提供短反馈

保留 `reason`、`scope`、`disposition`、必要 constraint 和内部 frame 摘要。改善 `feedback` 的含义，不增加平行失败类型或新的模型叙事结构，也不复制完整 schema、请求正文或原始异常。

| 所在边界 | 修改 | 反馈示意 |
| --- | --- | --- |
| Action 参数校验 | 保留字段路径，类型错误补充实际 JSON 类型；缺失字段说明所缺字段；enum 给出有界候选值 | `params.guide_blocks must be an array; received a string. Follow this field's tool definition.` |
| schema 的 oneOf | 零匹配时保留少量去重的分支失败摘要；多匹配时说明参数同时匹配多个候选 | 说明具体字段缺失/类型不符，而非只有“必须符合一个分支” |
| Action 内部 LLM | 复用 `ActionTaskOutput` 的 subject，给各类任务失败加清晰来源 | `Answer generation failed: the response reached its output limit. Reduce the requested scope.` |
| 空回答 | 复用文本结果失败路径 | `Answer generation returned no usable text.` |
| LLM 缺少工具调用 | 说明本任务需要调用可用工具 | `This response contained no tool calls. Call a tool available for this task.` |
| LLM 调用了域外工具 | 点出工具不在当前任务中，不输出整个工具目录 | `Tool '<name>' is unavailable in this task. Use the current tool definitions.` |
| 保留的 JSON 任务 | 说明需要单一 JSON 对象，可附短解析位置/原因 | `Return one JSON object; the response could not be parsed at line …` |
| Workspace 资源准备 | 传递 owner 已生成的原因，不再盖成统一的“sources unavailable” | 目录应先 inspect、文档需要转换等现有短说明 |

这些是语义示意，固定英文措辞在 `prompts` 的原 owner 文案中维护。schema 反馈从实际 schema 产生，不为 answer 编写特殊纠错分支；只报告少量候选/分支原因，不创建匹配评分、自动修参或递归诊断树。新增摘要在既有 ActionLocalFailure 的 2000 字符上限内构造，不新增配置项。

`ActionTaskOutput` 只包装内部生成任务的来源，不改变稳定 reason/disposition 的映射。Workspace 的普通 I/O、内部不变量失败仍交给现有 bridge；仅已经归类为可修正输入问题的资源错误成为局部结果。

当前 Phase 反馈已说明未接受、未执行任何 Action，继续复用；不重复再套同义叙事。局部失败仍反馈至下一完整 Cycle，不在当前 Phase 内重试、不接受部分协议失败的响应、不自动切换模型修复输出。

## 8. 可行性核对与完成标准

本方案复用现有 TEXT、ActionTaskFactory、ActionResult、Markdown parser、Turn 完成管线与 Session 引用消费者。主要变化是删除回答的二次 JSON 包装及 Core 的资源读取职责；不需要新增模型协议、生成预算、Endpoint 路由或重试机制。影响集中在几个明确 owner，具备现成测试入口，合理可行。

预期效果：模型生成正常正文即可形成回答；错误仍能明确反馈并继续修正；回答引用与正文一致；Core 与 Workspace 的依赖更清楚。不会保证每次 Action 参数或工具选择都正确，也不会把 provider 成功响应等同于业务成功。

已明确取舍：Core 不再通过 references 直接看图；reason 继续使用 JSON 对象；输出 references 保留为正文内部链接的出现记录。没有必须阻塞实施的未决项。当前状态为准备实施，不是已完成。
