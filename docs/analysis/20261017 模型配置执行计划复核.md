## 3. 已复现的实施缺口

### 3.1 运行方案应用会删除后续新增任务

位置：`tinysoul/infra/config/editing/controller.py` 的 `_preset_mutations`、`_preset_projection`、`_publish`；`presets.py` 的 `PresetDefinition.replacements`。

`_preset_mutations` 仍对 `llm.tasks`、`action.models.bindings` 等根路径先 delete，再 set 整组值。matches 仍比较完整 capture；retrieval 要求当前 consumer 集合与保存集合完全相等。

复现使用现有配置测试 fixture 和真实 ConfigController，在隔离临时目录执行：

1. 保存仅包含任务 `main` 的方案。
2. PATCH 新增 `llm.tasks.extra`，没有修改 main。
3. saved_match 变为 false；应用原方案后，任务集合从 `[main, extra]` 变为 `[main]`。
4. 随后新增一个 retrieval policy，原方案 validation_issues 返回 `Preset retrieval consumers differ from current capabilities`。

该行为违背原计划 §6.3/§6.4 及 P3 的“只应用方案声明项，不删除其它任务、不要求 owner 集合完全相等”。如果新业务路由引用新增任务，整组替换还可能在候选校验处失败。模型与 Provider 目录当前确实不被方案恢复，这部分已正确实现。

### 3.2 family 筛选导致任务模型显示与实际值不一致

位置：`visualization/src/features/settings/models/LlmTaskChainsPage.tsx` 的 `ModelChoicePicker` 和 `TaskChainEditor`。

family/query 筛选先剔除不匹配模型；后面的“保留已选项”仅豁免 collapsed，无法保留被 family/query 排除的当前值。原生 select 的 value 不在 options 中时，页面显示空值或其它候选，React state/任务草稿仍持有原值。

复现结果（使用现有页面 fixture）：

- 已有链 `[kimi-k2, glm-latest]`，点击 Kimi 胶囊后，第二行 select 显示空值；保存配置仍为原链。
- 新建任务时初始值为 `glm-latest`，点击 Kimi 胶囊后页面显示 `kimi-k2`；直接创建任务，草稿实际保存 `[glm-latest]`。

这会影响日常选择模型的正确性，不能以样式问题处理。空搜索结果也应遵守同一选择有效性规则，避免显示无候选却提交隐藏值。

### 3.3 family 选择体验只实现了一部分

同一页面只有新任务的首模型使用 `groupModels`/optgroup；追加模型和逐行替换直接输出平铺 option。三个入口各自维护过滤逻辑，已经出现行为差异。

此外，模型管理和任务选择生成胶囊时都使用 `filter(Boolean)`，缺少计划要求的“未分组”胶囊；任务候选标签只拼接 family 与 ID，没有标出搜索/展开后出现的默认折叠模型。缺少 family 的模型仍可从“全部”访问，运行任务链也未按 family 重排，这两点是正确的。

## 4. 运行方案：按声明的业务条目更新

### 4.1 更新单位

方案描述如何使用任务和模型。保存时捕获所选 active/saved/draft 视图中的任务定义、路由和可选预算；应用时只恢复其中声明的业务条目。暂不增加逐项勾选管理范围的编辑器，再次捕获方案才纳入后来新增的条目。

| 声明内容 | 更新单位与行为 | 未声明内容 |
| --- | --- | --- |
| `llm.tasks` | 以 profile ID 定位，恢复该任务的完整定义，包含有序模型 ID、调用参数及重试/切换策略；当前不存在时可重新建立该任务 | 其它任务完整保留 |
| Phase1/Phase2 路由 | 仅更新方案中声明的对应字段 | 其它路由保留 |
| `action.models.bindings` | 按 consumer 匹配，完整替换该条 binding 的 implementation、target、options；新增绑定仍须通过现有 consumer/target 校验 | 其它 consumer 的绑定及其顺序保留 |
| retrieval | 按 consumer 定位，只更新已声明的 query.channels 和预算字段 | 其它 consumer，以及同一 consumer 的来源/操作能力等配置保留 |
| 全局预算 | 只更新方案声明的预算路径 | 不含预算的方案保持当前预算 |

“完整任务定义”是明确的声明单位：例如方案中的 `main` 未配置 temperature，而当前 main 显式配置了 temperature，恢复该任务时该参数回到 owner 默认值。否则仅递归合并字典会残留不属于方案的调用参数。Action binding 同理，implementation/target/options 必须作为一条一致的路由恢复，不能混合新旧 target。此规则不意味着可以清空整个任务集合或绑定集合。

模型链和 query.channels 是有序数组，声明后的值整体替换，不做集合并集。空任务/绑定集合表示没有声明条目，不表示删除当前全部条目。预算等可选叶字段中的 `null` 延续现有“移除显式配置、使用 owner 默认值”语义，不写入 TOML null；缺少声明则不管理。任务内不另存一份 owner 默认值表。

方案不创建、删除或恢复 model/provider/use 目录。已声明的 retrieval consumer 或操作能力消失时继续返回现有 ConfigError/validation_issues；允许当前存在更多 consumer，不再要求集合完全相等。不增加历史转换、缺失模型兜底或自动改写方案。

### 4.2 实施位置与写回

保留已经落地的 `PresetDefinition(values, retrieval, include_budgets)` 表达，在其内部解释上述有限业务单位，不为此次修正重写存储格式，也不引入通用 deep-merge、JSON Patch DSL 或独立方案执行器。tasks/routing/budgets 是业务内容分组，当前 JSON 中不另建同名副本。

- `presets.py` 负责声明范围、值投影与按当前配置生成目标值；将 `replacements` 的整组覆盖语义收敛到明确条目。完整 capture 仍只服务保存/重新捕获方案，不再用于判断另一个配置是否匹配。
- `controller.py` 负责真实 source 定位、现有候选加载、validator、持久化与激活。任务写回边界缩小到 `llm.tasks.<profile>`，保留其它 profile 的来源；需要清除被覆盖的旧任务字段时也只处理该 profile。
- binding 当前以数组存储：先按 consumer 合并当前有效数组，再写回其正常来源；保留未声明行，不能直接用方案数组替换。已匹配行保持原位置，新声明行按方案顺序追加。
- retrieval 沿已有配置对象结构保留其它字段；即使现有 TOML 编辑要求写回对象，也必须写入合并后的完整对象，而非方案子集。不能将含点的 consumer 身份误当作任意点路径拆分。
- 沿已有来源和 catalog 的创建落点恢复缺失任务，不因为拆分条目就把内容写到任意最后一个 include 文件。无需增加新的 source 规则或文件迁移功能。

active_match、saved_match、应用后的声明核对、matching_presets 均只检查同一套声明单位。额外任务/绑定/检索 consumer 不影响匹配；已声明任务内容变化才影响匹配。来源路径、模型版本、family/collapsed 不参与方案匹配。

候选可用性与匹配分开：匹配表示使用策略相同，不能代替依赖校验。预览与实际 apply 共用构造、加载和校验候选的流程，实际发布继续走现有 ConfigFileTransaction/activation，不增加 Runtime bridge 或第二套提交状态机。

方案内容按 definition 展示实际值：

### 5.2 比较基准与后端投影

实际 apply 先从已保存配置加载，合入方案，再激活整个候选。这意味着已有 saved 与 active 的差异也会在这次激活中生效，不能仅比较“方案值与 active 的同名字段”后称为完整应用预览。

扩展现有 `GET /v2/config/presets/{id}` 详情，返回只读 `preview`，不新增写接口、不持久化预览结果。列表响应保持轻量，不携带每个方案的完整变化列表。建议投影为两组变化：

| 字段 | 比较 | 用途 |
| --- | --- | --- |
| `preview.saved_changes` | 当前 saved → 合入方案后的候选 | 显示方案会改写哪些配置值 |
| `preview.active_changes` | 当前 active → 同一候选 | 显示本次激活实际改变哪些运行配置值 |

“应用变化”默认看“运行中 → 应用后”；提供“已保存 → 应用后”基准切换。若存在未由方案管理的待激活修改，在运行比较内显示为“已保存、将同时生效”的变化，避免让用户误认为是方案捕获的模型版本或 Provider 配置。二者使用同一个表格组件。

每条变化只需稳定配置路径/业务定位、before、after；值不存在与存在应在协议上区分，以显示“新增 / 修改 / 恢复默认”。binding 按 consumer 对齐，不能按数组下标把未变行报成修改；模型链以有序 ID 列表展示，不逐项生成噪声。两组变化使用相同的业务定位；仅出现在 active_changes 的行可以明确标为已有 saved 修改随本次生效。读取 preview 的调用方只负责分组与格式化，不再实现另一套方案合并算法。

后端以真实值判断是否变化，再复用现有凭据脱敏规则输出；敏感值只显示“已变更”，不能因两端都投影为 `<redacted>` 就漏报。预览只承诺配置差异，不猜测 provider 远端行为或自动填充各业务 owner 的默认参数。候选不可构造/校验时返回 validation_issues、preview 不可用，不能用空变化伪装为无改动。

示例：

| 配置项 | 当前 | 应用后 |
| --- | --- | --- |
| `frame-stage1` 模型链 | `gpt-luna` | `gpt-sol → deepseek-flash` |
| 用户轮最大 Cycle | 40 | 80 |

后来新增的 `extra-task` 不进入变化表，应用后仍在。若 `gpt-sol` 有已保存、尚未激活的远端型号修改，它只在“运行中 → 应用后”显示为同时生效的已有修改，不进入方案内容。

### 5.3 应用入口与草稿

设置方案页和聊天快捷入口共用一个应用预览弹窗，沿现有 `usePresetApplyFlow` 改造，不叠加“预览确认”和“草稿确认”两层弹窗。点击应用时重新获取详情，展示上述变化和现有可用性提示；实际确认后仍仅提交 `{preset_id}`，后端按最新 saved 重新构造候选。无需预览 token、revision、锁定快照或新冲突恢复协议。

有本地草稿时，在同一弹窗中提供“先处理草稿 / 丢弃草稿并应用 / 取消”；明确预览不包含这些草稿。延续现有成功后清理已同意草稿、失败保留草稿的行为，不增加草稿与方案的隐式合并或连续两次 apply。

`active_match` 只表示方案声明已满足，不能单独禁用应用入口：active 匹配而 saved 中声明项已改动时，仍需允许用方案恢复 saved；存在其它待激活修改时也应可以查看实际影响。最终确认在候选不可用、配置正忙或两种比较均无变化时禁用，继续沿当前写入/激活可用性控制。

详情不能只依赖 `preset.updated_at` 刷新：saved/active 配置刷新、重新捕获、重新打开比较或应用弹窗时重取预览。使用现有配置刷新状态，不新增轮询服务或第二套缓存失效协议。

## 6. 共用模型列表与单模型选择

### 6.1 组件职责

在 `settings/models` 内提取实际被多个入口消费的模型候选列表，例如 `ModelSelectionList`，以及包装触发框/弹出层的 `ModelPicker`，可放在同一 `ModelPicker.tsx`。列表管理搜索、family 胶囊、折叠候选可见性及行展示；选择器只控制开关、当前 ID 与一次选择回调。它们接受 `projectCollection(saved + drafts)` 的投影，不自己读取 API 或新建配置 store。

复用位置：

| 入口 | 使用方式 | 点选结果 |
| --- | --- | --- |
| LLM 模型管理页 | 内嵌同一候选列表，保留右侧模型编辑器 | 选中要编辑的模型 |
| 任务链现有行 | 显示当前 model ID 的选择框，点击弹出列表 | 只替换该行 |
| 任务链追加 | “添加模型”打开同一列表 | 选一个模型，追加链尾并关闭 |
| 新建任务 | 创建表单内嵌同一候选列表，显示已选首模型 ID | 保存一个首模型 ID，创建任务时写入 |

`ObjectEditorLayout` 保留已有布局、移动端选择面板和其它集合的默认列表，仅增加一个有实际消费者的列表内容插槽供模型页嵌入共用列表；不复制整套布局，也不把所有配置对象编辑器都改成模型组件。沿现有弹层和样式组织选择弹窗，关注正常的焦点、Escape、点击关闭和窄屏体验，不引入新的 UI 框架。

### 6.2 过滤与选择规则

1. family 胶囊来自完整模型投影：全部、各实际 family，以及确有无 family 模型时的“未分组”。所有入口按同一 family/ID 顺序展示。
2. 默认隐藏 `collapsed=true` 候选；“显示折叠模型”可展开，非空搜索可找出折叠模型，并显示“默认折叠”标记。family 筛选与搜索共同作用；不会根据 ID 是否带版本或是否有 family 推断折叠。
3. 胶囊、搜索、折叠开关只改变弹窗候选列表，绝不提交模型选择、自动改选首项或修改任务链。
4. 关闭状态的选择框始终直接显示当前 ID，即使该模型默认折叠或弹窗筛选条件排除了它。折叠是显示偏好，不改变任务可执行性；引用已缺失时显示原 ID 和缺失提示，不悄悄替换。
5. 点击候选或键盘明确确认才触发 `onSelect(id)`，关闭弹窗；取消或无结果不产生草稿。当前候选可带选中标记，但不为维持选中状态破坏搜索/family 过滤。
6. 追加时已在链中的候选禁用并说明“已在任务链中”；替换时仅禁用其它行占用的模型。由任务编辑器传入限制，列表不拥有任务链业务。
7. 新建任务首模型初始为空，用户明确选择后才可创建。没有可用候选时保留空态，不使用隐藏的第一个模型作为实际值。
8. 当前任务链保留全部成员及原顺序，继续使用已有移动/删除控件，至少保留一个模型。模型字段仅显示 ID，删除 `family 路 model-id` 文案；摘要使用正常分隔符，并清理本页已有“楂樼骇”等乱码。

不再在整条任务链上方放模型搜索和 family 胶囊；也不保留“先在平铺 select 选一个、再点添加”的另一套选择状态。新建任务弹窗内嵌同一候选列表，不叠加两层模态窗口；行为仍为单模型选择，筛选后已选首模型 ID 单独准确显示。

### 6.3 选择后的配置提交

选择器不提交配置。追加、替换、移动和删除统一生成新的有序 `models` 数组，经既有 `setObjectField` 写入共享草稿；创建任务沿 `stageObjectCreate` 提交首模型及任务定义。只保存 model ID，不保存 family 筛选、搜索词或候选可见性。

新 family/模型的草稿立即进入同一投影，可在任务弹窗选择；保存时继续用现有统一操作集合提交 `create_source → model 定义 → task 引用`，整体候选有效后落盘。无需为了选择新模型先单独保存一次模型页。模型重命名沿既有引用更新能力同步任务草稿。

全局保存与应用成功后刷新 saved/active、列表、已选值和 dirty 标记；失败由当前提交边界展示问题并保留草稿。重复编辑同一任务只留下当前数组，取消选择不产生多余修改。组件不私藏一份会在配置刷新后覆盖草稿的 models 数组，也不创建新的提交按钮/状态机。
