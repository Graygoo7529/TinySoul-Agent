## 1. 已确认目标与设计范围

维护者已确认以下方向：

1. 整理推理模型、专用模型和其它能力的环境变量示例。
2. 通用能力统一使用“决策模型 / Decision model”；供应商实际模型名仍按外部协议保存。
3. 模型配置域中的预置 ID 使用连字符；逻辑模型使用稳定、无版本号的 ID。
4. family 用于显示分组，collapsed 只用于默认收起；两者不决定模型调用资格。
5. 折叠 GPT Terra，删除模板中的 GPT 5.5；保留仍有实际用途的任务链关系。
6. Provider、Model 统一来自项目 TOML，前端能够创建和编辑，不按“内置/自定义”赋予不同权限。
7. 运行方案保存任务链、路由和预算，通过稳定 ID 使用模型，不保存模型版本、Provider 连接和模型规格。
8. 支持从前端创建物理 TOML 配置来源；按 family 组织模型文件，让新增 family 与已有 GPT、Kimi 等以相同方式被加载和使用。
9. 优先实现清楚的正常流程和必要结束边界，复用配置加载、草稿、事务、激活与模块失败处理。
10. 2026-10-16 确认：family 与首个模型一起创建并保存；本轮不添加 GPT Astra。
11. 新建模型只有一条主线：选已有 family / 新 family → 选择 Adapter → 选择 Provider 并填写该端点的远端模型名称。取消复制模型、选择已有模型作为模板和复用其配置的入口。
12. 前端可按新后端契约直接调整，运行方案与模型管理保持简洁；不保留没有当前用途的旧 UI、兼容标签或中间层。

本轮涉及配置基础设施、LLM 配置资产、专用模型术语、运行方案及前端设置。Agent 调度、Context、LLM 请求解释和供应商重试策略不因本计划增加新的执行流程。

## 3. 目标语义与所有权

### 3.1 稳定模型身份

| 概念 | 所有者与含义 | 例子 |
| --- | --- | --- |
| Model ID | 项目配置中的稳定逻辑模型身份，任务链引用它 | gpt-sol |
| Provider ID | 连接配置身份，声明端点、凭据及支持的 Adapter | orca、sublyx-proxy |
| provider_model | Binding 中发送给具体端点的不透明字符串 | gpt-5.6-sol |
| Adapter | 代码实现的请求映射、协议选项、响应解释与供应商错误分类 | openai、kimi |
| family | 模型显示分组文本，也是前端组织新模型文件的依据 | GPT、DeepSeek、Kimi |
| collapsed | 默认收起偏好 | true |
| Task profile | 一种任务用途的有序模型链和调用策略 | frame-stage1 |
| 专用 use | 业务用途到专用逻辑模型的绑定 | decision-main |

模型升级通过修改同一 Model 的 Binding 和相应规格完成，任务、Action 路由和运行方案继续引用稳定 ID。升级时一起检查 capabilities、context_window_tokens、adapter_options 和 request_overrides；同一模型的多个 Provider Binding 应满足该模型声明的共同契约。

调用观察继续分别记录 model_id、provider_id 和 provider_model，稳定身份不能遮蔽本次实际请求的远端名称。过去的调用记录保留当时值，不随模型目录升级重写。

family 与 Adapter、Provider 保持独立。例如 GPT family 使用 openai Adapter，经 orca Provider 调用。任何解析分支均不依赖 family 或逻辑 Model ID 的拼写。

不增加 tag、alias、latest 解析注册表。确需保留旧版本比较时，显式建立带版本号的模型定义并设置 collapsed；不自动保留每次升级的旧模型。latest 表示维护者选择的当前路线，不表示 TinySoul 自动探测或升级远端模型。

## 4. family 与 TOML 文件组织

### 4.1 保持一份模型事实

已确认采用“创建 family 与首个模型一起保存”的流程，family 从模型定义推导，不另存 family 注册表，也不增加单独的空 family 创建页面。

模板按以下文件组织：

| family | 模型文件 |
| --- | --- |
| GPT | configs/llm/models/gpt.toml，由 openai.toml 调整而来 |
| DeepSeek | configs/llm/models/deepseek.toml |
| Kimi | configs/llm/models/kimi.toml |
| GLM | configs/llm/models/glm.toml |
| MiniMax | configs/llm/models/minimax.toml |
| 未分组 | configs/llm/models/ungrouped.toml，替代 custom.toml 的默认落点 |

模型继续存为 `[llm.models.<id>]`，family 是模型自身的显示字段。后端仍加载普通 TOML，不从文件名推导 Adapter、模型可用性或强制修正 family。

对已有手写配置保持明确规则：读取所有 include 来源，按实际 family 展示；编辑已有字段写回实际来源。文件名与 family 不一致、同一 family 分散在多个文件，本身不触发自动重排。

### 4.2 前端创建

新建模型弹窗提供已有 family 选择和“新 family”输入。新 family 填显示文本，默认生成小写连字符文件名；无法生成明确文件名或与另一分组文件冲突时，才在同一弹窗提示填写文件名。普通创建不展示 source graph、文件分配策略等基础设施概念。

正常流程：

1. 选择已有 family：优先复用该组唯一的模型文件；若手写配置分散在多个来源，则把新模型写入该 family 的规范文件，不移动或合并其它模型。不引入通用来源选择器。
2. 创建新 family：在 catalog 声明的模型目录下准备新 TOML source，并在同一草稿中准备首个完整模型。
3. 按 family → Adapter → Provider / provider_model 顺序填写。逻辑 ID 是同一表单中的必要字段，可建议 family-latest 形式并允许编辑；与远端 model 分别输入，不再把 gpt-sol 等逻辑 ID 自动当作远端型号。
4. Adapter 选项来自后端 catalog/rules，Provider 候选按其声明的 adapters 筛选。没有兼容 Provider 时提示先到 Provider 页创建，不自动选用无关端点。删除“复制模型”和“Model template”选择入口，新建不读取其它 Model 的配置。
5. 新模型、family 和 source 在保存前均为同一草稿的投影。取消创建不会产生物理文件。
6. 保存/应用通过统一配置事务完成；成功读取 saved 后获得正式 source 与模型项。

模型规格（context_window_tokens、capabilities）和 Adapter 必需协议选项仍需有合法值；以现有编辑器补充必要项，扩展参数放在高级区域，不另做多页向导。catalog 的普通初始值是表单起点，不代表已探测出远端能力；不能根据名称推断规格。

新建并保存即写入普通 TOML 定义，之后统一经 ProjectConfig → LLMConfigParser 加载和注册。草稿只是未提交配置，不建立“自定义模型存储”、临时运行注册或绕过 TOML 的调用入口。沿用现有统一保存/应用按钮，不增加单独的新模型发布流程。

已有模型的普通编辑和重命名写回原来源。修改 family 只更新显示元数据，不自动搬迁文件；按 family 分文件是模板和新建的组织惯例，不是运行时不变量。本轮去掉独立模型移动/文件重排交互，避免把模型管理扩成文件管理器。

最后一个模型被删除后，空 TOML 可继续存在；没有成员的 family 不再由模型列表投影。不建立空分组持久化协议，也不自动删除文件。再次使用相同 family 时可直接复用已有空文件。

### 4.3 创建与后续 Binding 编辑的一致规则

- 首次创建必须明确选择 Adapter，不能由 providers[0] 的第一个 Adapter 反向决定。
- 首条 Binding 的 provider_model 由用户填写；新增备用 Provider 时同样填写该端点型号，不复制其它 Provider 的型号，因为端点别名可能不同。
- 切换 Adapter 时只保留与目标 Adapter 兼容的连接和明确存在的对应 Binding；没有对应远端名称时留待填写，不回退到 object.id。依赖原 Adapter 的 options 按现有规则清理。
- 禁用 Provider 仍是可配置的连接，可用于提前定义模型；enabled 与凭据就绪由现有配置校验/运行选择处理，family 和 collapsed 不参与。
- 不删除共享 JSON 深拷贝等仍有真实消费者的基础函数；只删除模型复制这一业务入口及其分支。

### 4.4 catalog 的最小扩展

模型 collection 继续保留默认 `create_source`，指向 ungrouped.toml；family 新文件的物理路径由前端按 `configs/llm/models/<family>.toml` 生成，后端只验证路径边界和 include 可达性，不增加 `create_directory` 元数据。

移除按 custom.toml 判断身份的规则。所有对象显示草稿/修改/只读等真实编辑状态，能够查看来源；不显示 Built-in/Custom 分类。

共享集合设施只保留 `all` 与 `none` 两种删除策略；模型来源不再派生内置/自定义权限，具体可写来源由 source-aware mutation 决定。

## 5. 创建物理 TOML 的配置基础设施

### 5.1 扩展现有配置操作协议

在既有 operations 中新增明确的 source 创建操作，示意：

```json
{
  "operations": [
    {
      "op": "create_source",
      "source_id": "project:configs/llm/models/qwen.toml"
    },
    {
      "op": "set",
      "source_id": "project:configs/llm/models/qwen.toml",
      "path": "llm.models.qwen-latest",
      "value": {
        "family": "Qwen",
        "collapsed": false,
        "adapter": "openai_compatible_chat",
        "providers": [
          {"provider": "example-provider", "provider_model": "remote-model-name"}
        ],
        "context_window_tokens": 32768,
        "capabilities": ["text_input"]
      }
    }
  ]
}
```

示例只说明操作形状；example-provider、remote-model-name 和规格不是新增可调用模型的承诺。真实提交必须引用候选中存在且兼容的 Provider，并填写真实规格。

基础类型沿现有 owner 放置：保留字段修改类型，增加 frozen 的 source 创建类型与明确的操作联合类型；操作种类使用有限枚举。HTTP 通过 discriminated union 接收，SDK 和 Controller 使用同一基础类型。不要以空 path 冒充 source 创建，不给普通 set 增加“未知 source 自动创建”的隐式副作用。

同一批次先登记来源创建声明，再应用普通字段变更，最后一次性校验。前端按 create_source 在前的顺序输出，后端无需维护依赖图。

### 5.2 创建边界

首个真实消费者是普通 include 加载的项目 TOML：

- source_id 由 `project:` 和项目相对文件路径组成；解析后的路径须在项目 configs 内，扩展名为 .toml。
- 目标必须是尚不存在的文件；已有 source 使用普通 set/delete，create_source 不覆盖已有文件。
- 目标必须被候选主配置的 config.include 覆盖，且不与 document_sets 来源重叠。
- family 文件已被现有 models/*.toml 覆盖，无需每次修改主配置。
- 一般新增位置可以在同批次明确更新主配置 include；创建操作不暗中改变 include 顺序。
- 不接受原始任意文件内容，不创建 dotenv、进程来源或 Action Catalog document_set 文档。后续若这些来源有真实创建需求，再按各自语义扩展。

这些限制用于保证新增文件是会被项目读取的配置来源，不建设独立的文件权限或治理系统。

### 5.3 统一候选加载与真实加载

当前候选构造只替换 environment.sources 中已有项，不能把新来源简单 append 到末尾。否则候选校验通过的覆盖顺序可能与保存后重新加载不同。

应在现有 ProjectConfig/source loader 中提取或扩展共用装配能力：输入磁盘配置与本批次已解析的暂存 TOML 数据，按同一 config.include 规则、glob 排序和去重规则重建 source graph，再构造 ConfigEnvironment。

实现要点：

1. 用内存中的 staged documents 覆盖对应磁盘文档；把已声明的新路径加入 include 枚举候选。
2. 主配置 include 的本批次变更也参与相同装配。
3. 候选保留环境变量和显式 overrides 的既有优先级。
4. 新来源以最终 source_id 出现在候选 sources/effective fields 中，后续 set 和引用校验可直接使用。
5. 复用现有 validator 和 activator；ConfigFileTransaction 负责实际写入。
6. 保存后重新从磁盘加载，应得到与候选相同的配置值、source 身份及顺序。

现有 document_sets 文档编辑仍要把本批次暂存内容交给原 owner 校验。共用装配不能把它们重新从磁盘读取后覆盖掉候选修改；这里只限制其新增来源能力，不移除已有编辑能力。

只需要一个有限的暂存文档输入，不建设通用虚拟文件系统。读取 active 配置制作方案时，继续使用对应活动来源值；不能因为共用 loader 而改为读取最新 saved 文件。

### 5.4 保存、激活与失败

PATCH 只保存并形成 pending_reload；apply 继续在允许激活时 prepare、保存并发布；reload 激活已保存配置。新文件走同一流程。

配置形状、路径、来源冲突、模型引用和 Adapter 兼容性错误由 ConfigError 表达，经现有 Endpoint 映射反馈。校验失败不落盘。提交或激活失败复用现有 receipt 回滚，本次新文件恢复为不存在。

沿用现有短操作 join、取消和 generation 关闭语义。不加入文件版本号、CAS、后台恢复循环或新的 Runtime 原因。

### 5.5 前端草稿与 API 对接

在现有 ConfigDraft store 中增加有类型的 source 创建草稿，与字段草稿共用保存、撤销、应用状态。来源创建与字段修改是两种事实，不用虚构字段路径混在一起；source 草稿是无 `path` 的独立联合成员。

pending source 可用于同一草稿内的模型、任务链和来源选择；不加入第二个模型目录缓存。buildOperations 汇总 source 创建与字段操作。撤销新模型时，若该 source 已无其它字段草稿，同步撤销创建声明；按页应用要带上所提交字段必需的 source 创建。source-only 草稿按 source 前缀路由到模型设置页。

草稿被清空、应用成功或切换项目时，来源声明与其它草稿同生命周期处理。网络失败沿用当前失败展示和保留草稿行为，不自动重复创建文件。

SDK patch/apply、Endpoint schema/route/engine、前端 API 类型与契约 fixture 同步支持操作联合。方案从草稿建立时也可使用这个内存候选，但不会因保存方案而写入配置文件。

## 6. 运行方案改为简洁的使用方案

### 6.1 保存范围

| 内容 | 是否保存 | 说明 |
| --- | --- | --- |
| Task profile 定义 | 是 | 有序稳定模型 ID、调用参数和重试/切换策略 |
| Phase1/Phase2 任务路由 | 是 | 引用任务 profile ID |
| Action model-use binding | 是 | consumer 对应 implementation、task/use target 和业务 options |
| 检索 query.channels | 是 | 保留当前真实的策略切换能力，归入路由 |
| 全局及检索预算 | 可选 | 延续当前明确登记的预算范围 |
| LLM Model 定义 | 否 | Binding、版本、规格、options、family、collapsed 属于统一目录 |
| Provider 定义和凭据 | 否 | 属于连接配置 |
| 专用 model/provider/use 目录 | 否 | 方案通过稳定 use ID 引用 |
| 授权、来源/操作能力、知识内容 | 否 | 由原 owner 管理 |

运行方案只保存上述“如何使用”的配置值，不保存 ModelSpec、ProviderSpec 或专用模型的连接细节。任务自身的 temperature、max_output_tokens、重试和等待参数属于 task profile，随任务链保存；include_budgets 控制是否保存全局/检索预算。

### 6.2 定义结构

以 PresetDefinition 取代完整模型 Snapshot；ConfigPreset 继续持有 id、name、description、时间和 definition。definition 只有实际方案消费者需要的三个部分：

- tasks：profile ID 到任务定义的映射。
- routing：Phase 路由、按 consumer 标识的 Action bindings、按检索 owner 标识的 query.channels。
- budgets：可选的已登记全局预算及按 owner 标识的检索预算。

JSON 记录使用当前 `schema_version = 2`，并用 definition 替换 snapshot；included_scopes 只报告 tasks、routing 和可选 budgets。API 路由仍使用 /config/presets，capture 的 source 继续支持 active、saved、draft。旧 schema 不读取、不转换。

建立方案时直接捕获所选视图中的完整任务链、Phase/Action 路由和可选预算，不增加逐字段选择器或模型版本选择器。新模型不会进入方案记录；新增任务或路由是否纳入方案由用户再次保存方案决定。definition 缺少某个可选部分表示该部分不由方案管理。

配置基础设施不导入上层 LLM TaskSpec 或 Action 实现。结构在 config owner 转为明确的定义对象，具体任务和 binding 契约继续由现有注入 validator 校验，不复制第二套业务 parser。

只迁移运行方案记录及其前端读模型；saved/active 配置快照、Context 快照等真实快照概念不改名。

### 6.3 应用语义

方案应用把 definition 中的 tasks、routing 和 budgets 作为一个使用策略提交。没有携带的 budgets 保留当前值；其它已登记的方案部分按当前配置的正常对象来源写回。模型、Provider、专用模型目录和未由方案管理的配置不参与写入。

应用前由现有候选校验检查稳定模型 ID、task/use、consumer 和 Adapter/implementation 关系。依赖不存在时明确拒绝，不自动替换模型、不恢复模型目录、不建立临时模型。

### 6.4 匹配、差异与使用效果

active_match/saved_match 只比较方案管理的任务、路由和预算值；不比较模型目录、Provider 连接或未管理配置。单独升级 gpt-sol 的 provider_model、调整 capabilities 或 collapsed，不会让运行方案变为“不匹配”。

匹配与可用性分开：策略值一致不等于依赖一定就绪，现有 validation_issues 继续解释缺失/不可用依赖。

示例：

- 保存“日常”方案，链中包含 gpt-sol。
- 将统一目录中的 gpt-sol 更新为新 Binding，添加其它模型和任务。
- 应用“日常”方案后，其 definition 声明的任务链、路由和预算恢复；gpt-sol 使用当前 Binding，模型目录始终由当前 TOML 管理。

前端方案页只展示方案名称、管理范围、任务链/路由/预算摘要、匹配状态和验证问题。删除原始 Snapshot JSON 树和通用逐字段 diff 表；需要查看模型具体 Binding 时回到模型页。这样运行方案只表达使用策略，不把底层配置快照暴露为业务对象。

从包含未保存新模型的草稿建立方案时，只保存稳定 ID 引用；模型目录仍须另外保存。应用方案时按当前目录校验。

## 7. 统一模型编辑和选择交互

### 7.1 所有来源同等编辑

移除 Built-in/Custom 徽章及由它派生的 Adapter 锁、删除和重命名限制。字段可写性仍来自真实 source；引用约束由候选配置校验。

普通字段写回字段来源；对象重命名和删除使用 sources.values 定位所有实际定义，不只使用 effective fields。标准模板每个对象只有一个定义时，操作直接落到该文件。

本轮不实现模型移动或文件重排。family 文件是组织模型的约定，不把模型管理页变成通用文件管理器；已有模型的 family 编辑只更新模型字段。

模型重命名更新任务链引用；Provider 重命名若提供该交互，更新模型内的 provider binding。运行方案只在显式保存时捕获当前稳定引用，不在普通字段保存时自动改写方案。

### 7.2 模型选择交互

模型管理页和任务链页使用同一份 saved + draft 模型投影与相同筛选语义；页面根据各自已有编辑器提供分组展示和选择控件，覆盖：

- 任务链追加模型。
- 任务链中替换已有模型。
- 新建任务的初始模型。
- 模型管理列表的分组、搜索与折叠规则。

交互规则：

1. family 胶囊由 saved + draft 模型集合生成，包含“全部”和必要的“未分组”。
2. 默认显示未折叠模型；模型管理列表按 family 分组，任务选择器使用 family 分组的 option group，并提供全局显示折叠模型开关。
3. 搜索可命中折叠模型，展示其默认折叠状态；搜索逻辑 ID 和 family。远端 provider_model 属于模型编辑详情，不作为任务选择器的目录字段。
4. 已有任务链按真实顺序展示全部成员，已选折叠项始终可识别。
5. 候选选择可以分组，任务链自身绝不按 family 重排。
6. 没有 family、不带标签、ID 含版本号均不会触发自动折叠。
7. 当前选择保留，管理页首次默认选择优先取可见模型，避免自动选中第一项绕过折叠。
8. 组内采用稳定明确的显示排序，折叠状态只影响默认可见性，不猜测版本新旧；不额外持久化 family 展开状态。

选择列表主文案使用逻辑 ID，摘要可展示 Provider/远端型号。无需增加模型 display_name 字段，也不把 Adapter 描述放进任务使用流程的必填决策。新建模型不提供复制、模板或“复用已有配置”选择。

## 11. 可行性复审与复杂度控制

### 11.1 结论

方案在现有架构内可行。工作量集中在配置候选 source graph、方案应用语义和共享前端草稿/选择交互，属于多个模块协同调整，不是单纯改名；无需改造 Agent/Turn 生命周期或供应商运行器。

已有可复用能力包括：TOML include 与 source identity、ConfigFileToml 内存编辑、ConfigFileTransaction 新文件回滚、ConfigController 校验和激活、saved/active 配置视图、前端统一草稿、模型 metadata 和任务链引用。

### 11.2 复审后落实的修正

| 潜在缺口 | 本计划处理 |
| --- | --- |
| 只改稳定 ID，旧方案仍恢复版本 | definition 排除全部模型目录，并修改应用/match/diff |
| 只允许新 source，候选顺序与真实加载不同 | 共用 include 装配，暂存文件参与 glob 排序 |
| 新 family 被当作第二套模型目录 | 与首个模型同批创建并保存，从模型字段推导；不保留空 family 元数据 |
| 逻辑 ID 不带版本后仍被默认发送为远端型号 | 空白创建要求显式 Binding，不自动复制逻辑 ID |
| 取消内置限制后重命名仍搬到 custom.toml | 改为真实 source 内重命名；不提供模型文件移动操作 |
| effective fields 未包含被遮蔽定义，删除后旧对象重现 | 使用已有 sources.values 收集对象的实际定义 |
| 新来源创建绕过前端统一草稿 | 来源声明纳入同一 store 和提交生命周期 |
| 新方案继续整组清空任务或要求 owner 集合完全相等 | 只更新 definition 声明的策略字段；未声明的 budgets 保留当前值，不写模型目录 |
| 新旧方案协议混用 | 新 schema + 直接采用新协议，不保留旧格式读取、转换或旧覆盖逻辑 |

### 11.3 保持实现适度

必要处理限于来源路径/存在性、include 可达性、候选有效性、引用闭合及现有事务结果。继续使用当前失败边界，不新增后台补偿队列、配置 CAS、动态 Adapter 发现、标签分配、自动模型升级、文件同步守护或通用迁移框架。

LLM 和专用模型仍由各自 typed 协议服务真实消费者；本次统一术语与编辑体验，不合并它们的运行调用协议。family 文件组织首先服务 LLM 模型目录，不强行把专用模型原子数组拆成相同文件结构。
