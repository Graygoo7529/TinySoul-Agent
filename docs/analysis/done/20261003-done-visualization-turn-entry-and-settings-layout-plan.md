# Turn 入场与设置页信息层级、窄屏布局改进计划

状态：`done`。已完成实施、设计文档同步和逐项验证，2026-10-03 归档。

分析基点：`3276940`。主对话的表现基线为 `c479ca0`，数据与执行契约继续使用 v2。

## 1. 目标与已确认边界

本轮处理两个问题：从发送输入到 LiveStatus 开始的连续入场，以及设置页主要配置的可达性、信息顺序和窄屏布局。

已确认的交互方向：

- 移除主对话的 `Queued as the next turn` 文本条，不重复展示初始输入。
- 移除 Composer 左下角的发送模式选择；已有可接收输入的 User Turn 时，普通发送直接追加到该 Turn。
- 移除 LiveStatus 顶部的 Stop 按钮。Composer 保持空白时显示停止、有文字时显示发送，不增加并列停止按钮。
- 保留 `c479ca0` 的用户气泡、单一 Agent 区域、LiveStatus、动作浮层、滚动锚点和完成收束。设置页延续现有材质、色彩和控件，调整信息层级与响应式布局。

不改变 Agent 的根请求调度、TurnInbox、Context 安装或 Session 事实语义。前端不维护第二套执行状态机；发送回执、正式交互和 Observation 仍各司其职。本轮方案可以使用现有 v2 能力完成，未发现需要新增后端接口的缺口。

## 2. 现状与原因

| 位置 | 已核对事实 | 影响与处理方向 |
|---|---|---|
| `tinysoul/agent/services.py` 的 `turn_interactions` | 尚未找到 Context 时，会为 UserTurnRequest 返回 `queued_request`，包括已处于 `preparing` 的请求；摘要最多 240 字符 | 字段存在不等于 Turn 此刻仍在排队，运行状态须读正式 snapshot |
| `features/chat/ChatView.tsx` 的 `QueuedRequestRow` | 只要存在摘要就插入一行原文，Context 就绪后删除；同时顶部已有本地输入气泡 | 两份输入先后出现，摘要行消失后高度收缩，是此次闪烁的直接原因 |
| `EchoDelivery` 与 `UserBubble` | 发送中、已接受提示另占一行；正式 `user.input` 接管时删除该行，并切换气泡透明度 | 即使移除排队条，也需要检查成功交接时的高度与明暗跳变 |
| `ConversationTurn` | 用户气泡的稳定 key 已建立，但 AgentRow/Details 可以早于 LiveStatus 出现 | 应按内容准备情况组织同一 Agent 区域，避免先出现空壳或孤立 Details，再插入主卡片 |
| `interactions.ts` 的 Composer 意图推导 | 用户可主动选择 queue；活动 snapshot 缺失或不匹配时也回退为新 Turn | 只删除菜单仍可能把本应追加的输入提交成下一轮，需一并整理目标推导 |
| `SettingsOverviewPage.tsx` | 运行代次、原始状态和完整配置来源列表位于本地修改、待激活及方案前；来源 ID 与路径可能重复 | 优先呈现可操作信息，来源与代次改为按需展开 |
| `behavior/ActionsPage.tsx` | 较长的只读 Behavior 在 Model Uses 之前；授权、支持、可用状态分别占用徽标 | 常用的模型绑定被下推，需要先给出状态摘要，再呈现可编辑内容 |
| `SettingsNav`、`ObjectEditorLayout`、字段行 | 导航固定 220px；对象列表在 viewport 的 `md` 断点占 240px；模型字段行又在同一断点要求至少 220px + 260px | 800px 窗口扣除两级列表后，详情区域无法容纳字段两列；需以实际内容空间安排布局 |
| 普通设置与 ACP/MCP 集合编辑 | 存在固定宽输入框、不可收缩的控件区与固定标签列 | 只修复模型页不足，需一起覆盖实际复用这些布局的设置页 |

上一轮已经修复初始气泡从 Agent 区域移到顶部的问题；本轮继续处理气泡之后的重复条目与成功交接。不能把此次原因归结为入场动画时长，也不靠延迟显示整轮内容掩盖问题。

## 3. Turn 入场与输入交互

### 3.1 从回车到运行的可见过程

| 实际时点 | 用户看到什么 | 数据与表现约束 |
|---|---|---|
| 按下回车，HTTP 请求尚未返回 | 输入立即成为顶部用户气泡；气泡边角用小型发送指示表示正在提交 | 复用已有 local echo 身份；不出现另一行输入、排队提示、空 AgentRow 或孤立 Details |
| 创建回执已返回，snapshot 尚未就绪 | 同一气泡保留，发送指示更新；不额外插入“已接受，等待出现”的整行提示 | 回执绑定真实 Turn ID；不把回执等同于 Context 已安装，也不伪造 Phase1 |
| snapshot 为 `preparing` | 气泡下方出现单一 Agent 区域及 LiveStatus 的 `Preparing context` 抬头 | 使用现有卡片和淡入方式；没有活动时保持紧凑抬头，正文等待真实内容自然展开 |
| Context 安装，正式 `user.input` 可读 | 同一气泡由正式数据接管，发送指示淡出 | 不重新挂载气泡，不改变其正常高度，不重复入场或重新定位滚动 |
| Phase / reasoning / control / Action 到达 | 同一 LiveStatus 更新抬头并依原版节奏展开思考与活动 | 原有滚动、交叉渐变、动作浮层和完成收束继续复用 |

这些是实际数据可能经过的时点，不要求逐帧播放全部中间状态。后端很快就进入运行或结束时，直接呈现已知事实，不补播 Preparing，也不设置人为最短等待时间。

具体实施约束：

1. 删除 `QueuedRequestRow`。初始正文优先使用正式 `user.input`，其次使用本地 echo；重连时若只有 `queued_request` 摘要，可以作为同一气泡的暂时线索，并保留摘要已截断的提示，不能冒充完整输入或单独成为第二行正文。
2. 初始发送成功路径采用不额外占行、不改变正文换行的指示。保留 `aria-label`/title 等状态说明；不以整块气泡反复改变透明度表达发送交接。明确失败仍应显示原因与可执行操作。
3. 只有具备可呈现的运行或交互内容时才挂载 Agent 区域。Preparing 的空活动状态由正式 snapshot 派生，不依赖首条 Observation 恰好已到达，不把“尚无事件”误判为“尚无 Turn”。Details 随可用的运行卡片或正式内容出现。
4. 若真实状态仍是 `queued`，同一紧凑抬头仅显示“等待开始”这一开始前状态；不显示队列编号、重复原文或额外的队列操作条，不显示虚假的 Phase 或运行计时。进入 `preparing` 后原位更新。
5. `viewKey` 从本地 echo 到真实 Turn、再到 Session 接管保持稳定。已完成上一轮后立即发送下一轮时，也须及时绑定新回执；不能因屏幕仍保留上一轮而迟迟不读取新 Turn。
6. 保留原来的顶端锚定与用户手动滚动接管；不得通过全局固定卡片高度、延长折叠时间或反复强制滚动来消除跳动。Activity 正文从真实内容增长，结束时沿用既有折叠和回答显现顺序。

### 3.2 Composer 只表达直接输入

删除 `IntentChip`、`ComposerIntentChoice`、`applyIntentChoice` 以及仅服务于菜单的文案与状态。输入框保留发送快捷键提示、运行方案入口，以及现有发送/停止位置。

| 当前情况 | 普通发送的目标与行为 |
|---|---|
| 后端就绪，无未完成 User Turn | 创建一个新的 User Turn |
| 当前 User Turn 在准备、运行或等待用户/预算，且未请求取消 | 追加到该 Turn；发送前固定目标 ID，发送中不随状态刷新改投其他 Turn |
| 已获得本窗口新 User Turn 回执，但它尚未开始执行 | 先读取该请求的正式 snapshot，再针对这个已接受的 User Turn 追加；不因它暂未成为 active Turn 而连续创建多个根请求 |
| 状态同步中，尚不能确定已知活动 User Turn 的目标 | 可继续编辑草稿，发送暂不可用；刷新已知目标，不默认创建下一轮 |
| User Turn 已请求停止或正在收尾 | 保留草稿，发送暂不可用；正式结束后恢复新 Turn 发送，不自动提交草稿 |
| 明确处于 Reflection 等非 User Turn 工作 | 不向 Reflection 追加用户文本；新用户请求仍交 Agent 原有调度入口，创建后按上面的已接受 User Turn 规则处理，不提供排队模式选择 |
| 历史只读页、离线或后端未就绪 | 沿用对应只读/连接状态，不从历史页向另一轮隐式投递 |

目标由已有 RuntimeStatus、TurnSnapshot 和创建回执推导。不要建立另一个本地消息队列或定时自动发送器；真实 `queued` 状态仍属于后端契约，取消其前端模式菜单不等于删除后端队列。

普通追加与明确回复保持区分：QuestionCard 按 question ID 提交回复，预算卡提交补额；Composer 的文本始终是追加，不因当前有问题就自动变成回复。

追加过程中若 Turn 恰好关闭，保留输入与明确的未发送结果，不静默改投下一轮。已有失败恢复入口可保留“作为新对话发送”，由用户显式操作；只有目标已结束时提供，不将其变成新的排队入口。

### 3.3 停止入口与正常入场反馈

- 删除 LiveStatus 的顶部 Stop 按钮、`onStop` 属性，以及确认无其他消费者的 `canStop` 表现字段和推导；取消执行仍由已有 controller/v2 command 负责。
- Composer 有文字时显示发送；空白且目标 User Turn 可取消时显示停止。遵循此次确认，不为有文字的状态新增停止按钮。
- 停止始终针对当前可交互的 User Turn ID。已接受但尚未执行的 User Turn 同样使用它自己的 ID；不能误停全局正在运行的 Reflection。
- 取消请求提交后等待正式状态收敛，保留现有“正在停止”的抬头语义，不在本地伪造 Turn 已结束。
- `pending_items` 中真实的追加和回复继续可见、继续按 ID 与正式交互收敛；不把它们与本轮删除的初始请求摘要条混为一类。

## 4. 设置页的信息顺序

### 4.1 总览：先看状态与待处理修改

建议顺序：

1. **紧凑运行摘要**：配置是否已生效、当前能否应用修改；只保留一处可读状态。运行代次放入详情，不再用英文原始状态重复说明同一事实。
2. **需要处理的修改**：先显示应用失败、字段问题或基线变化，再显示本地草稿；已保存待激活内容单独标明。两者可以相邻呈现，但不混称“未保存”。
3. **运行方案**：保留现有查看、保存与管理入口。没有后端明确事实时，不推断某个方案就是当前活动方案。
4. **配置来源与运行详情**：默认折叠，标题显示来源数量；展开后列出来源、路径与只读/缺失状态，支持本地筛选。ID 与路径相同时只展示一次，较长路径可展开或复制。

没有本地草稿或待激活修改时，不保留两个大块空状态说明；在摘要中用简短状态表达即可。出现真实修改或错误后，对应内容自动可见。安全脱敏、字段定位和原始诊断入口继续保留。

底部应用栏仍是集中处理全部草稿的主要入口。总览承担解释与定位，不复制另一套应用流程。前端本地界面偏好继续即时保存，不纳入后端待应用数量。

### 4.2 Action：先理解用途，再选择内部模型

建议从上到下呈现：

1. **Action 标题、简短用途、情景与状态**。正常状态合并为一个可读摘要；不可用或不可由模型选择时，直接显示实际原因。展开详情仍可分别查看 grant、support、availability 与 visibility，不能把授权和模型可见性合并成一个伪造的开关。
2. **模型用途**。优先显示每个已声明 consumer 的实现选择与目标模型/任务链；全情景共享的绑定只作一次简短说明。无模型用途的 Action 用一行说明即可。
3. **Search 能力与策略关联**。仅对支持的 Action 呈现；解释候选来源/约束操作与绑定关系，复用当前策略入口，不增加第二套策略编辑器。
4. **执行策略与来源详情**。超时、并行策略、hooks、executor、trace mode 和配置来源默认折叠；明显限制或异常在摘要区保留提示。
5. **协议详情**。参数、原始定义等继续按需展开。

已保存配置、草稿与运行时绑定的差异保持可见；当前只读的执行策略不能因为布局重排就变成可编辑控件。Reflection 与普通情景继续使用同一套 Action 模型用途配置。

### 4.3 模型与供应商：突出决定调用的内容

- 模型页前置供应商顺序、供应商模型名、必要适配协议与主要能力；顺序依旧有明确编号、拖动和上移/下移入口。
- ID 与必要的接入方式保留在紧凑头部或首组；family、折叠偏好等显示辅助项移到次要分组，不占据供应商链之前的大量纵向空间。
- 上下文窗口、核心能力与必要协议不能一概藏入“高级”。扩展请求参数、适配器附加选项等采用已有或统一风格的折叠分组。
- 供应商页保持连接地址、凭据引用等必要配置直接可达；专用模型遵循相同信息层级。任务链继续用直观的有序列表表达。
- 隐藏区若有错误、草稿或字段定位请求，标题显示对应状态，定位时先展开再滚动。不能折叠后让用户不知道为何无法应用。
- 使用现有 `settings/i18n` 翻译标题、说明和显示标签；协议值、ID、用户内容不改写。减少重复标签与文件路径长说明，不减少真实配置能力。

## 5. 窄屏与视觉布局

### 5.1 三层空间分别处理

以 Settings 可用区域宽度衡量页面布局，而非只使用浏览器 viewport 的 `md`。以下为初始设计阈值，实施时用真实页面校验边界附近的可用性：

| Settings 可用宽度 | 页面导航 | 对象列表 | 编辑内容 |
|---|---|---|---|
| 至少约 1200px | 保留左侧约 220px 导航 | 模型、Action 等保留约 240px 列表 | 宽裕时标签与控件左右排列 |
| 约 900–1199px | 保留左侧导航 | 改为详情顶部的对象选择入口 | 编辑区占剩余全部宽度 |
| 小于约 900px | 标题附近的“设置页面”按钮打开导航面板 | 顶部对象选择入口 | 单列内容，长字段上下排列 |

字段行再依据**所在编辑区域**的实际宽度决定排列：约 600px 以下，长文本、下拉框、键值列表等改为标签在上、控件在下；短开关仍可与标签同排。固定宽输入框必须允许收缩到容器宽度，编号、拖动柄和必要操作保持可用。

优先使用现有 CSS 与容器查询解决空间分配。响应式仅改变布局与导航呈现，不复制整套表单，也不根据断点重新挂载编辑内容。

### 5.3 复用与交互细节

- `SettingsPage/SettingsNav` 管页面导航；`ObjectEditorLayout` 管模型与 Action 等对象选择；`editors/collection.tsx` 的 ACP/MCP 集合采用相同窄屏空间原则，继续保留各自草稿与业务编辑逻辑。
- `models/controls.tsx`、`editors/controls.tsx` 与集合 `ObjRow` 共享一致的排列规则；可提取已有真实复用的布局外壳，但不强行合并不同配置绑定协议。
- 调整窗口宽度、开关导航面板都不得丢失尚未 blur 提交的输入，不改变当前对象或折叠编辑内容的身份。对象切换本身沿用原有编辑提交规则。
- 导航与对象面板使用现有 Modal/弹层材质及交互基础，补齐键盘关闭、焦点恢复和可访问标签。表单主体始终只有一份。
- 应用栏处于设置页底部正常布局中，不盖住最后一个字段。窄屏时状态说明可独立一行，“应用配置”保留主按钮；重置此页与放弃全部收进“更多操作”，清楚标明范围。无修改时不堆放不可用按钮。
- 不因窄屏隐藏字段错误、应用阻止原因或只读限制；说明可换行，长技术值可展开/复制，主体不出现横向滚动。
- 延续 `bg-bg-elev`、`bg-bg-sunken`、`accent-soft` 与原有边框、阴影。淡色强调用于当前选项、脏字段和定位结果；不让所有设置区持续发光。仅加载/应用中的局部状态需要动效，并尊重 reduced-motion。
