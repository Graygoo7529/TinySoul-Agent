## 目标

在现有前端中文界面的基础上，建立可维护的 `zh-CN` / `en-US` 双语界面，允许通过项目共享的 Interface 设置切换语言。语言、主题、字体、字号、密度和动态效果由同一个 PresentationService 读取、保存和投影；前端固定文案由稳定 message ID 管理，配置目录和协议状态由稳定身份翻译，用户内容和后端动态业务内容保持原样。

目标状态如下：

```text
项目 presentation/configs/interface.toml
    └── locale = "zh-CN" | "en-US"

Gateway PresentationService
    └── InterfaceSettings / InterfaceSettingsPatch / HTTP response

前端 uiPrefsStore
    └── saved + pending locale

前端 i18n
    ├── t(messageId, params)       固定 UI 文案
    ├── catalogText(identity)      后端配置目录展示元数据
    ├── protocolText(code/value)   稳定错误、状态和枚举
    └── raw dynamic content        用户、项目和 Agent 产生的内容
```

本计划基于 [AGENTS.md](../../../AGENTS.md) 的 owner、配置和呈现语义制定。它只改变 Gateway Presentation 和 visualization 的显示能力，不改变 Agent/Turn/Context/Action 的业务状态、模型提示、持久 Memory、Session 或 Endpoint 连接协议。

## 已确认的设计决定

### 1. 语言是项目共享 Interface 配置

`locale` 属于 Gateway 的 `PresentationService`，与 `theme`、`font_sans`、`font_mono`、`font_size`、`line_height`、`density` 和 `reduced_motion` 同属 `InterfaceSettings`。

```toml
locale = "zh-CN"
theme = "light"
```

支持的值只有：

- `zh-CN`：简体中文；
- `en-US`：英文。

默认值固定为 `zh-CN`，不根据浏览器语言、操作系统语言或前端运行环境自动切换。缺少 `locale` 的旧 `interface.toml` 按默认值读取；非法值仍按 Presentation 配置错误处理。保存其它 Interface 字段时，结构化写入会把完整当前设置（包括 locale）写回文件。

项目共享语义意味着同一项目的多个浏览器或 Tauri 客户端最终使用同一个语言设置。修改生效后，其它客户端在重新连接、进入 Interface 页面或显式刷新时读取新值；不新增实时同步或 revision 协议。最后一次成功保存继续采用现有 Presentation 语义。

### 2. `locale` 是配置身份，不是前端连接身份

语言不进入 `.env`、`.auth`、前端 address/token 存储、Endpoint handshake、Agent 配置草稿或运行方案。它保存在后端项目的 `presentation/configs/interface.toml`，由项目 reset 的既有模板物化流程处理。

前端在未连接后端时使用内存中的 `zh-CN` 默认投影。连接新项目时，`resetPresentation()` 清理旧项目投影，连接成功后立即读取新项目 Interface 配置。客户端不另外持久化一份 locale，避免旧项目语言污染新项目或使客户端状态与项目事实分叉。

### 3. 后端提供源 catalog，不建立第二套 UI i18n

当前后端没有独立的界面 i18n 系统：

- `tinysoul/infra/config/catalog/*.toml` 是后端拥有的配置展示目录，提供英文源标题、说明和 choice label；
- `tinysoul/gateway/presentation.py` 只负责项目界面配置，不生成翻译文本；
- `tinysoul/prompts` 中的语言要求属于模型任务提示，不属于前端界面本地化；
- Endpoint 错误 envelope 已有稳定 `code` 和结构化 `details`，`message` 是后端诊断文本。

因此不在 Python/Gateway/Infra 中复制一套 `zh-CN` / `en-US` UI 字典，也不让后端根据 locale 改写 catalog 或错误 message。后端继续负责真实语义和源文本，前端负责面向用户的显示投影。这符合 Infra 拥有 catalog 描述、Gateway 拥有 Presentation 配置、前端拥有视觉交互的边界。

## 内容所有权和本地化边界

| 内容 | 事实 owner | 前端处理 | 是否翻译 |
| --- | --- | --- | --- |
| 按钮、标题、说明、空状态、加载提示 | visualization | message ID 字典 | 是 |
| Settings 页面固定标签 | visualization | message ID 字典 | 是 |
| ConfigCatalog 字段标题、说明 | Infra/业务 catalog owner | 按稳定身份覆盖源文本 | 已知条目翻译 |
| ConfigCatalog choice label | catalog owner 提供 value；前端提供显示 label | 按父字段身份 + `choice.value` | 已知条目翻译 |
| collection、surface、field group、document field | catalog owner | 按稳定 id/组合身份 | 已知条目翻译 |
| Action Catalog 的 description、semantic、examples | Action Catalog/项目配置 | 原样显示；周围 UI 由前端翻译 | 否 |
| 模型名、提供方名、Action ID、配置值、路径、引用 | 对应业务 owner | 原样显示 | 否 |
| 用户输入、Agent 回答、Home/Memory/Workspace 正文 | 对应内容 owner | 原样显示 | 否 |
| Endpoint 错误 code、运行状态、协议枚举 | Endpoint/业务 owner 定义稳定值 | 前端按 code/value 映射 | 是固定摘要 |
| Endpoint `message`、Observation 自由文本 | Endpoint/Observation owner | 显示原文，必要时附加本地化摘要 | 不翻译自由文本 |
| 模型提示和模型回答语言 | prompts/LLM/业务 owner | 不纳入 UI i18n | 否 |

前端本地化是显示投影，不会向后端发送翻译后的 title、description 或 choice label，也不把本地字典当成配置 schema、默认值或校验规则。

## 前端 i18n 结构

### 1. 专属目录

新增全局目录，避免继续把 UI 文案放在 Settings feature 内：

```text
visualization/src/i18n/
  index.ts
  types.ts
  messages/
    zh-CN/
      common.ts
      shell.ts
      connection.ts
      settings.ts
      chat.ts
      workspace.ts
      home.ts
      memory.ts
      runtime.ts
      history.ts
      resources.ts
    en-US/
      common.ts
      shell.ts
      connection.ts
      settings.ts
      chat.ts
      workspace.ts
      home.ts
      memory.ts
      runtime.ts
      history.ts
      resources.ts
  catalog/
    zh-CN.ts
  protocol/
    zh-CN.ts
    en-US.ts
```

文件按 UI owner/页面职责拆分，所有字典在 `src/i18n/index.ts` 组合。不要按每个组件创建独立的翻译系统，也不要将动态后端内容复制到字典中。

### 2. 稳定 message ID

固定 UI 文案使用分层稳定 ID，例如：

```ts
t("common.retry")
t("shell.logout")
t("connection.addressLabel")
t("settings.interface.language")
t("workspace.empty.title")
```

字典使用类型推导或显式类型保证两个 locale 的固定 key 集合一致。字典缺 key 不静默显示另一种语言的 source copy；开发测试应直接报告缺失。运行时对未知 ID 可保留可读的开发回退，但不能把回退当成正常翻译路径。

插值通过参数完成，不把变量拼到 message ID 中：

```ts
t("search.resultCount", { count })
```

字典只返回纯文本，不插入 HTML。需要 `<code>`、链接、图标或按钮的句子拆成可组合的文本片段，避免在翻译字符串中保存 React/HTML 标记。

### 3. 访问 API

React 组件使用响应式 hook：

```ts
const { locale, t } = useI18n();
```

非 React 的 controller、store 和错误处理使用读取当前 `uiPrefsStore` 的纯函数：

```ts
translate("common.retry", params)
```

`translate` 不拥有 locale 状态，只读取现有 `uiPrefsStore`；语言事实和待保存 patch 仍由 `presentationController` 管理。`document.documentElement.lang` 在 App 根部随当前有效 locale 更新，默认值为 `zh-CN`。

### 4. Settings 旧本地化迁移

现有 `visualization/src/features/settings/i18n/` 的内容拆成三类：

1. `ui.zh-CN.ts` 中的固定英文原文映射，迁移为 `src/i18n/messages/zh-CN/settings.ts` 的稳定 message ID；
2. `catalog.zh-CN.ts` 中的字段、文档和 choice 翻译，迁移为 `src/i18n/catalog/zh-CN.ts`；
3. 动态字段值、Action description、模型名称或用户文本，移除 `settingsText()` 包装，直接使用后端/配置值。

最终删除 `settingsText(source: string)` 作为通用翻译入口。Settings 页面只能使用 `t()`、catalog 本地化函数或原始动态值。

## 动态 ConfigCatalog 的翻译协议

### 1. 稳定身份

前端本地化函数必须接收后端 descriptor 和当前 locale，而不是只接收 source string：

```ts
localizeField(field, locale)
localizeChoice(fieldIdentity, choice, locale)
localizeDocumentField(field, locale)
```

身份规则：

- 普通 field：`field.path`；
- document field：`document_set + document_kind + path`；
- choice：父 descriptor 身份 + `choice.value`；
- collection、surface、field group：各自稳定 `id`；
- action catalog document：`document_set + document_kind + path`，不按实际 description 值匹配。

字段 path pattern 是当前 ConfigCatalog 的稳定契约。字段重命名时，源 catalog 和对应的前端翻译 key 一起更新；不为旧字段建立兼容别名。

### 2. locale 处理

- `en-US`：优先显示后端 descriptor 当前的源文本；不复制一份重复英文字典；
- `zh-CN`：已登记身份使用前端中文翻译；未登记身份回退后端源文本；
- 新增 field、provider、model、choice 或 action 文档不会导致页面失败，也不要求同步修改测试；
- 前端不能根据 dotted path 猜测字段归属或生成 schema，只能使用后端 catalog。

搜索需要同时匹配原始 title/description、当前 locale 的 title/description 和稳定 path。显示结果使用当前 locale 的本地化投影。

### 3. 防止动态内容误翻译

迁移时审查所有 `settingsText(...)` 调用：

- 固定 UI 文案替换为 `t(messageId)`；
- catalog descriptor 通过身份本地化；
- Action semantic、model/provider/action 名称、后端返回的正文和错误详情直接显示；
- 不再通过“碰巧等于某个字典 source key”翻译动态值。

## 协议状态和错误本地化

Endpoint 继续返回稳定 `code`、结构化 `details` 和原始 `message`。前端新增纯显示映射：

```ts
tError(error)                 // known code -> localized summary
tStatus("ready")              // stable runtime status
tActionState("available")    // stable action state
```

规则如下：

1. 已知 code/value 映射到 `protocol/<locale>` 中的稳定 message ID；
2. `details.key`、`details.step`、`details.owner` 等结构化值作为插值或定位信息，保持原样；
3. 未知 code 使用原始后端 `message`，不猜测、不解析文本；
4. 原始诊断可在详情区域继续查看，不因为切换语言而改写；
5. Observation 的事件类型、运行状态和固定标签可翻译，事件 message 和模型/Agent 文本不翻译。

这沿用 [errors.ts](../../../visualization/src/api/v2/errors.ts) 现有“只根据稳定 code 分类”的协议，不新增后端 locale negotiation，也不让后端根据前端语言返回两套错误 envelope。

### 1. Presentation owner

修改：

- `tinysoul/gateway/presentation.py`
- `tinysoul/gateway/endpoint/http/schemas/presentation.py`
- `tinysoul/gateway/endpoint/http/schemas/responses.py`

### 2. 默认和模板语义

不要求所有模板立即写入 `locale`；缺少字段即可由 `InterfaceSettings()` 提供默认值。若模板已有显式 `interface.toml`，可在模板中加入 `locale = "zh-CN"` 以提高可见性，但不能通过模板复制推导运行时默认。

`init/reset` 不新增独立迁移系统。reset 继续用现有 Presentation 文件重建语义；项目已有 interface 文件按既有项目模板规则处理。旧文件缺少 locale 时读取为 `zh-CN`，首次保存时补齐。

### 3. 后端不新增的内容

本计划不新增：

- Python UI 翻译字典；
- `Accept-Language` 或 Endpoint locale handshake；
- 后端根据 locale 翻译 ConfigCatalog；
- 将 locale 写入 Agent `configs/`、`.env` 或运行时状态；
- 对用户 Markdown、Agent 回答或 Action Catalog 正文做机器翻译。

## 前端实施范围

### 1. Interface 投影和生命周期

在 `uiPrefsStore.ts` 增加 `locale`：

- `UI_PREFS_DEFAULTS.locale = "zh-CN"`；
- `prefsFromApi` / `prefsPatchToApi` 处理 locale；
- `applyUiPrefsToDocument` 或 App 根 effect 设置 `document.documentElement.lang`；
- `resetPresentation` 恢复 `zh-CN`；
- `refreshInterface` 和自动保存沿用现有 epoch、pending、失败重试语义。

Interface 页面新增语言选择控件，并将其作为项目共享设置说明的一部分。修改后界面立即预览，保存失败保留 pending locale；“恢复项目界面默认”恢复服务端 defaults。

### 2. 全局固定 UI 迁移

按以下顺序迁移，避免长期保留两套入口：

1. `App`、`AppShell`、`NavRail`、`TopBar`、`StatusBar`、Toast 和通用按钮；
2. ConnectScreen、连接错误、重连提示和 logout；
3. Settings 页面、导航、搜索、配置草稿、字段控件和保存状态；
4. Chat、Turn/Question/Composer、Trace/Runtime；
5. Workspace、Home、Memory、History、Context、Resources/Search；
6. Markdown/代码块/资产等通用展示组件中的 aria-label、title、placeholder、空状态和错误摘要。

迁移时同时处理可访问性文本、placeholder、tooltip、`aria-label` 和按钮文本，不只替换可见标题。

### 3. Settings catalog 迁移

重构 `features/settings/i18n/index.ts` 为全局 catalog adapter 或删除其旧 source-string API：

- `translatedField` 改按当前 locale 返回稳定 descriptor projection；
- `localizeDocument` 使用完整 document identity；
- choices 按 choice value 翻译；
- `labels.ts` 的页面和分组标题改为 message ID；
- `pages.ts`、对象编辑器、字段控件、方案差异和搜索复用同一投影；
- 未知 descriptor 保留后端源文本。

- protocol code/value 映射已知本地摘要，未知 code 保留原始 message。

### 3. 页面测试

- InterfacePage 能加载、切换和保存 locale；

- 未知后端 catalog 字段可以显示，不因没有本地字典失败。

测试优先使用 role、稳定属性、状态和 message ID 对应的显示结果，减少对某个历史中文句子的逐项固化。模型、provider、prompt、Action catalog 可编辑内容不作为全量快照断言。

## 风险和处理

### 1. 连接前后语言短暂不同

未连接时默认 `zh-CN`，连接成功后以项目值替换。这是共享设置的自然边界。不要把旧项目 locale 暂存为客户端事实，否则会重新产生项目连接目标之外的持久状态。App 根部应保证切换是完整 React 重渲染，不保留两种语言混排的长期状态。

### 2. 后端新增 catalog 字段

后端 descriptor 增加时，英文会自动可见，中文暂时回退英文。测试只检查 fallback 规则，不要求每个项目新增字段立即补翻译。稳定字段 path 或 descriptor id 变化时，维护者同步更新对应的中文 catalog。

### 3. 动态字符串误翻译

删除 `settingsText` source-string API，并对其调用逐项分类，是阻止动态内容被错误替换的主要措施。必要时以 TypeScript 类型区分 `MessageId`、`CatalogText` 和普通 `string`，避免将任意动态 string 传给 `t()`。

### 4. 后端错误 message 仍为英文

已知稳定 code 显示本地化摘要；未知 code 和原始诊断继续显示后端 message。这保留真实诊断，避免在后端和前端之间建立无法维护的双语错误协议。未来若确实需要更细粒度翻译，可增加稳定错误 detail/message ID，但不在本次范围内。

### 5. 字典规模和维护负担

按 UI owner 拆分字典，使用完整 key 集合测试；不为每个动态模型、provider、Action 或 catalog 值复制翻译。新增固定 UI 文案必须同时补齐两种语言，否则测试失败。

## 完成标准

- `InterfaceSettings`、HTTP schema 和前端投影支持 `locale`，默认值为 `zh-CN`。
- Interface 页面可以切换 `zh-CN` / `en-US`，自动保存到项目 presentation 配置，刷新或重新连接后保持。
- 未连接时使用 `zh-CN`，切换项目时不残留旧项目语言。
- Shell、连接、Settings 和主要功能页面的固定 UI 文案都通过稳定 message ID 切换。
- `settingsText(source)` 旧入口删除；动态内容不会被当作固定文案翻译。
- ConfigCatalog 使用稳定 path/id/value 本地化，未知 descriptor 回退后端源文本。
- 已知协议错误和状态使用稳定 code/value 本地化，未知错误保留原始诊断。
- 后端没有新增第二套 UI i18n 字典、locale negotiation 或业务内容翻译。
- 用户内容、Agent 回答、模型/provider/action 名称、路径、引用和 Action Catalog 正文保持原样。
- Python、前端测试、TypeScript/Vite build、类型检查和 Tauri 检查通过。
- 文档、测试和代码共同说明 Presentation owner、前端 message ID 和动态内容边界。

## AGENTS.md 对照

- `PresentationService` 继续是项目共享界面配置的唯一 owner；前端只保存服务端确认值和待提交 patch。
- locale 不进入 Agent 配置、Context、Session、Home、Memory、Workspace、Endpoint 连接凭据或运行世代。
- 前端 i18n 字典只拥有显示文案，不复制配置 schema、Action 语义、用户正文或持久业务事实。
- ConfigCatalog 仍由 Infra/业务 owner 声明，前端只按其稳定身份生成显示投影，不按 dotted path 猜测配置语义。
- 错误处理继续依赖稳定 code 和结构化 details；不解析自由文本改变控制流。
- `prompts` 保持无业务依赖的模型文案包，不承担界面翻译。
- 不为历史英文/中文调用保留兼容别名；项目处于开发阶段，旧 source-string 本地化入口可以直接删除。

## 计划可行性结论

本计划合理可行，原因是：

1. 后端已有独立、项目级 PresentationService，增加一个枚举字段不需要新存储 owner、迁移系统或 Endpoint 生命周期改造；
2. 前端已有 `uiPrefsStore`、`presentationController`、自动保存和连接 epoch，可以直接复用 locale 的加载、保存、失败和切换语义；
3. 当前 ConfigCatalog 已提供稳定 path/id/value，现有中文 catalog 可迁移为稳定身份映射，不需要修改所有后端 descriptor 或建立后端翻译系统；
4. Endpoint 已有稳定错误 code，协议状态本地化可以在前端完成，不改变业务错误和 Runtime 语义；
5. 用户内容与动态配置内容边界明确，新增配置条目可以通过源文本 fallback 保持可用；
6. 实施可以按 backend → i18n 基础 → Settings → 其它页面逐步落地，每一步都有局部测试和可编译边界。

当前没有未决架构决策。实施时只需按本计划处理常规命名、字典分组和组件迁移细节；若发现某个动态字段实际承担固定 UI 语义，应依据 owner 和稳定身份重新分类，不应临时把它加入 source-string 字典。
