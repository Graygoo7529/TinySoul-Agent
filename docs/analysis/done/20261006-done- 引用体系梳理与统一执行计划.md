## 1. 目标与边界

让维护者和模型能够用一致的概念回答三个问题：这个引用指向什么、在什么范围内有效、怎样读取或操作它。统一不仅涉及显示文字，也涉及 Action Catalog、typed request/result、Context、SDK/Endpoint 和当前设计文档中的机器字段。

目标语义是：**引用是由 owner 解释的精确定位值；模型用旁边的标题、摘要或命中依据判断是否需要读取，再把精确值交给支持它的操作。** 资源内容、历史出现位置、动态指向和临时读取状态不能因都含字符串而混为同一种事实。

本计划不建立新的资源数据库、通用文件 API、全局引用图或动态插件发现系统，不复制 Session 的关系图，也不赋予模型原本未授予的读取或写入能力。复用现有 owner、`ReferenceResolver`、`ResourceLocator`、Context segment 路由和 Disclosure/Search 协议；只有真实消费者无法由现有结构表达时才调整公共类型。

## 2. 已核对的引用类别与实际消费者

以下是当前实现清单，不是未来新类型清单。引用类别与来源 owner 是两个维度；不需要为每一行增加一个跨模块枚举。

| 内容片段与命中依据 | URI fragment；ContentUnit.ref/location；SearchEvidence.unit_id/range；ContentSlice | owner 按标题/行等解释片段；Search 把命中范围指回实际读取内容 | fragment、行号、字符范围不保证资源变化后仍是同一段原文；unit_id 是该快照内身份 |

## 3. 当前真实问题

### 3.1 同一语义使用多个机器字段

Home/Memory 的 Inspect 参数使用 `ref`，却接收被其它接口称为 Link 的资源身份；Workspace read 使用 `link`，修改使用 `target_link`，内部任务使用 `reference_links`，Search 范围使用 `ResourceScope.locator: str`。后者不是 `ResourceLocator` 对象，只是资源字符串。

Context Background 仍有 load_links/evict_links 与 entry.link；SearchCandidate、DisclosureHint 则用 ref。仅改中文 ToolSpec 的“链接”为“引用”无法消除维护者对这些字段的理解负担。

还发现具体说明与实现不一致：HomeTopLink 要求无后缀逻辑名，默认 Home Skill 说明也如此，但 `home/top_write.toml` 的 description 仍称 agent link 包含真实 `.md` 路径。应在 schema/Skill/owner 同步审核时修正，不能将旧说明继续写入统一规范。

### 3.2 不同语义又使用同一个名称

Session resource occurrence 同时有 ref、link、locator：其中 ref 是历史出现位置，link 是被引用的资源，locator 带原日/动态绑定。三者不是三个等价名字。若直接把全部 link 改成 ref，会覆盖原字段并丢失历史关系。

Search result_ref 也不是稳定内容 ref；Workspace cursor 与 continuation 也不是可长期保存的回忆入口。必须按消费者迁移，不能全局替换字符。

### 3.3 稳定身份、可读权限和历史原文容易混淆

稳定的 Memory/Home 身份不保证不可变正文；Workspace 还需日绑定。Trace entry、Action fact、Session canonical result、已保存 Heap snapshot 和 owner 当前文件保存的信息量不同。统一命名后仍要明确“读取当时已保存的事实”和“重新读取资源现态”的区别。

同样，Home prompt mount、MCP 工具、Trash 恢复入口都是可指代对象，却不都支持 core.context.inspect。模型知道引用值，不等于它拥有所有操作能力。

### 3.4 引用的解释随压缩丢失

`DisclosureHint(ref,title,clue)` 已有合适结构，Search 也有真实 preview/evidence。但部分 sources 只传裸字符串；foldable Action 只保留 selected refs；Trace node 的 clue 主要是类型、数量或 JSON 截取。这使模型获得精确身份，却不知道为什么需要读取。

“引用与解释一起显示/折叠”的投影修正在叙事计划实施，本计划负责保证身份和读取语义一致，不另建一套摘要状态。

## 4. 建议采用的统一设计

### 4.1 公共词汇与编码原则

1. 模型和当前设计文档以“引用/reference”为总称；“资源引用”“交互引用”“动态引用”等只在差异影响操作时使用。
2. 建议内容身份统一编码为 `ref`，集合为 `refs`；多个不同角色的引用保留 `target_ref`、`source_ref` 等明确名称，局部任务的参考输入可用 `references`，避免 reference_refs 一类重复表达。操作的可接受 owner/目标类别由 schema 与 owner 校验表达。
3. `link` 留给 Markdown/URL 的链接语法或边的自然语言概念，不再作为与 ref 并列且含义模糊的资源身份字段。owner 的 HomeTopLink/MemoryLink 等类名和包名是否改为 Ref，在同一 owner 的调用迁移中统一处理，不建立旧新类名 alias。
4. `locator` 专指“引用及解析所需绑定”的对象，不再同时指裸身份字符串。建议 ResourceLocator 收敛为唯一 `ref` 身份槽及有意义的 day/turn_id/view，保持公共无业务依赖边界。
5. Session 中“出现位置指向资源”明确为 `ref` 与 `target_ref`（以及必要的 target locator），两者同时保留。source_ref、reply_to、references 等有真实关系语义的字段不强行缩成同一个 ref。
6. 临时集合建议使用 `result_handle` 等明确名称，续页继续使用 continuation。Job ID、问题 ID、请求内短 ID 保持原语义。Workspace cursor 是否迁移只由分页契约是否相同决定，不属于必要的命名清理。

这些是目标契约建议，尚未宣布现有接口已经改名。迁移每个 owner 前记录旧字段、目标字段、全部真实消费者与存储影响；完成同一边界全部调用者后移除旧入口，不维持双名协议。

### 4.2 字符串编码按语义审阅

保留 owner 对地址的解释权，按人和模型的可理解性审阅 `@`、`/`、`#` 的用法。Home 顶层与深层资源有真实加载差异；Trace 根、原始 occurrence 与压缩节点也不相同。字符串可以改，不以旧格式兼容或旧测试作为保留不清楚编码的理由；但结构变化须具有实际语义收益。

第 4.7 节列当前合法形式及迁移原因；已确认的目标格式由 `docs/design/references.md` 维护。实施同步 owner parser/生成、默认 Markdown/Skill、持久格式、前后端和实际解析消费者，清除旧形式，不加双格式别名，不为测试目录建立迁移流程。

### 4.3 引用作用域按维护者确认收窄

- 普通 User Turn 的交互回忆范围是当前 Turn 与当日已完成 Session，Workspace 引用默认指向当日资源。跨日长期记忆沿 Session → Memory → recall 发展，本计划不让模型通过旧 Session/Workspace 引用跨日回读。
- Home 和持久 Memory 本来就跨日存在，不受“Workspace 当日”限制；不把 memory:daily 的日期误当成新增历史 Session 访问。
- 动态 Memory 与当日 Workspace 沿现有 owner 绑定解释；模型看到用途和必要日期即可，无需拼装 resolved_references 的内部对象。
- 现有 Endpoint 历史浏览、Reflection 来源日和归档段属于已存在消费者。本轮字段迁移准确保留它们所需的绑定，既不借机增加普通 Turn 的能力，也不把删除既有读取能力混进改名。
- 不设计新的跨日引用编码、自动跳转旧 Turn 或历史文件读取门面。Memory Reflection 避免把 Workspace 引用写入长期记忆不在本轮实施。

### 4.4 读取动作的一致理解

统一的使用方法是“看线索 → 选择引用 → 用支持它的只读操作读取 → 继续沿返回的直接引用探索”，无需统一为一个万能工具：

| 当前引用 | 当前读取入口 |
| --- | --- |
| Trace、已安装 Session、已安装归档 Workspace | `core.context.inspect` |
| Home 顶层与深层资源 | `home.inspect`；顶层也可显式加载至 Background |
| Memory 文档 | `memory.inspect`；动态内容依实际 Context/服务支持读取 |
| 活动 Workspace 文本 | `workspace.read`；非文本按资源类型使用对应 owner Action |
| 搜索结果句柄 | Search 的 `source=result`，不能传给任意 inspect |

上表描述当前实现。维护者已选择 **U0**：统一抽象原语和理解方式，保留插件、域选择及各自 Action 入口。本计划不引入 core.inspect 通用门面，也不扩大 core.context.inspect 的 owner 范围。

目标使用方法统一称 Inspect。新增 Workspace Inspect 的设计见第 4.9 节；现有 read 保留在上表作为当前事实，不再要求模型在顶层指导里学习 Inspect/read 双重称呼。Home/Memory/Core 继续沿各域已有入口，不要求它们具有完全相同的参数集。

共同原语约定如下：

1. ref 定位一个 owner 可解释的对象或内容片段；标题/摘要帮助决定是否读取，模型原样使用返回的精确值。
2. Inspect 对已知目标进行只读、按需披露，返回真实内容、覆盖说明和可继续读取的直接引用；不自动递归加载全部引用，不自动改变 Background。
3. Search 用于发现目标、筛选或排序；拿到已知 ref 后的读取不要求再做一轮搜索。若某个片段当前仅能由 Search 的 refs 模式读取，由所属 Inspect 补齐直接读取契约，不能让模型猜测转换参数。
4. 分页继续沿原调用入口和 continuation/cursor；全文、摘录、metadata 有明确区别。临时 Search 集合通过 result_handle 复用，不冒充普通 inspect 目标。
5. 无效目标、范围或已过期句柄按现有局部结果反馈。每个 Action 保留所属 Catalog 的执行策略、timeout、Skill 和 profile 服务权限。
6. 顶层背景说明只讲这套共同方法，域级 Skill/ToolSpec 说明 Home 顶层加载、Memory 动态内容、Workspace 行读取等真实差异。无需让模型理解内部 locator、digest 或存储协议。

因此不强制所有工具同名，不强制所有返回值退化为相同 JSON，但精确引用、内容覆盖和后续读取的含义应一致。

### 4.5 引用与解释成为一个导航单元

模型可见导航通常呈现“有意义的标题或实际摘录 + 精确引用”，必要时附日期、覆盖范围或下一读取方法。同一领域的通用读取方法在入口统一说明，不每行复制冗长工具教程。

优先复用 DisclosureHint 和 Search 的真实内容投影。label、已有 summary、命中片段可作为线索；“命中依据”只在确有搜索证据时使用，普通引用不编造相关性理由。

一个条目过大时，将它的引用和解释作为整体收进父层，父层保留自身解释和引用。Inspect 只展开选定层与页面，让下一层引用自然出现在正文旁边。不会把所有子引用永久保留在顶层，也不会折叠到只剩没有入口的总结。

“引用 + 摘要”是可见性约定，不要求存储所有 refs 的字段都改成 `{ref,abstract}`，也不新建摘要数据库。显示 owner 从当前已安装事实构造说明；底层原始关系仍可使用精确字符串。

### 4.6 result_handle 的专用语义

`result_handle` 是对当前 `result_ref` 的命名澄清：由 SearchViews 保存的、一次搜索处理完成后**完整最终候选集合**的临时句柄。它不只是某一页，也不包含已经被 select/filter 排除的候选，更不代表整个来源库。

例如一次搜索最终保留 120 项，当前页面展示 20 项：

- `items[i].ref`：某项资源或片段的引用，目标契约中用该 owner 的 Inspect 读取；
- `result_handle`：全部 120 项的内容快照入口，可在同一搜索服务/视图作用域内继续 filter/select/rerank；不会仅处理已展示的 20 项，也不会重读文件自动替换快照；
- `continuation`：继续读取下一页的定位令牌，不重新评估候选。

使用结果集合发起新请求时保留实际内容与来源覆盖，但原查询的模型评估/分数会重置，按新请求重新计算；被之前筛选排除的内容不会凭句柄恢复，需要从原来源另发请求。

句柄生命周期受所属 Turn/profile 或 SDK Search lease 及容量回收约束。当前 SearchViews 有视图数量/总内容容量上限，即使 Turn 未结束，旧集合也可能被回收。失效返回既有 view_expired 等局部失败，让调用方重新搜索；不保存为长期 Memory 证据入口，不跨搜索 owner 猜测复用，也不传给普通 Inspect。

目标协议示意（字段尚未实施）：

```json
{"source":{"kind":"result","result_handle":"search-result:<opaque-id>"},"steps":[{"op":"filter","where":{"tags":["pinned"]}}]}
```

上例 filter 属性仅表示 Workspace 中真实声明的标签筛选，具体可用属性仍由该 owner 的 schema 限定。句柄值继续使用 `search-result:<32位十六进制标识>` 即可，不因字段改名再增加一套字符串编码。

#### 已定位的具体不一致

1. **Trace 根与压缩节点语法不一致。** 根使用 @，节点改用斜线。已确认目标根为 `turn:trace/<turn-id>`，片段统一为 `#input/...`、`#action/...`、`#entry/...`、`#node/...`。所有子位置共用根；不增加裸 turn:trace 动态别名。
2. **Home 的入口类别依靠不同标点区分。** 当前 @ 表示可加载顶层，/ 表示深层文件，第二个冒号表示挂载。已确认改为显式路径 `home:top/agent/identity/soul`、`home:top/skills/tinysoul-docs`、`home:resource/skills/.../guide.md`、`home:mount/domain/workspace`、`home:mount/action/core/ask`。类别、加载资格及 owner 对真实内容的映射必须一起迁移。
3. **Workspace 片段从 Search 到读取不直接贯通。** Search refs 能处理 `#L10-L20`/标题片段，workspace.read 当前接收文件 link + start_line/end_line 并直接交给 reader，未统一解析 ref 片段。按维护者本轮方向，由新的 workspace.inspect 接收完整 ref 并解释片段，复用公共行/标题规则；不将修补旧 read 参数作为 U0 的前提。
4. **目录范围拼写有差别。** WorkspaceLink 不接受末尾 /，Search scope 接受后会去掉末尾 /；目录类型已有 kind=directory，建议对外规范输出 `workspace:docs`，不另设一套目录 Link 格式。
5. **片段解析前后端不完全一致。** 后端文档范围接受 L10-L20 和 L10-20，前端 parseLineFragment 只识别前者，且目前会将反向范围改成单行。建议规范输出 L10-L20，并统一边界校验，不靠前端静默修正隐藏错误。
6. **前端引用识别覆盖不完整。** 后端有 session:unclassified，当前前端 resources/reference.ts 的 SESSION_REF 未包含它。前后端同步不止改 TypeScript 字段，也要按 owner 支持范围逐项核对路由、片段和点击读取。
7. **整体范围使用空 locator 占位。** 当前 Workspace 全范围是 `{"kind":"workspace","locator":""}`，并没有合法的空资源引用。迁移时建议整体范围只保留 `{"kind":"workspace"}`，目录/文件范围才要求 `ref`，例如 `{"kind":"directory","ref":"workspace:docs"}`。schema、typed scope、解析与前端共同表达该不变量，不把空字符串改名为“空 ref”，也不为此虚构 workspace 根资源。

Trace 新格式与 Home 显式类别路径已确认；Memory、Workspace 主体、Session 主体和文档 #L/#heading 沿用。身份长度的进一步设计见下节，不以缩短 ID 重新打开已确认的命名空间和层级决策。

### 4.8 身份长度：日内编号、时间戳与局部序号（request/Turn 分工与显式日期已确认）

当前身份并非统一的 UUID：Agent 默认 request_id 是 `request_<32位hex>`，TurnHandle 与 Turn 复用此身份；Context 单独启动也能自行分配 Turn 身份。输入可继承外部 command_id；Trace Entry/node 使用不同长度的 UUID hex 截取；Session 注释节点使用完整 hex，Action occurrence 则已经是稳定序号。不能只在 ref 拼接处截断而破坏关联。

建议按对象职责处理，避免新增“长 ID ↔ 短 alias”注册表：

| 路线 | 收益 | 代价与判断 |
| --- | --- | --- |
| 完整 UUID 可逆压缩编码 | 128 位可用 22 字符 base64url 或 26 字符 base32 表达，无损转换 | 仍然没有内容语义；统一修改 canonical 编码才避免双重身份，节省有限 |
| 较短随机正式身份 | 例如 16 字符小写 base32 表达 80 位随机值，可直接成为 owner 的身份 | owner 在实际唯一性范围内避免重复；需要修改产生身份的边界及真实消费者，不能仅改 ref 显示 |
| owner 内不可重编号序号 | Trace `#entry/17`、`#node/3` 等简短且具有位置线索 | 只在所属根内有效；分配后固定，不能根据当前热区/树层级重编号，重放/install 不能重新分配同一事实 |
| 日内 Turn/Session 全部顺序编号 | 如 t42/n7，最短且易口述 | 要设计跨 restart/reload 的分配与恢复；Agent 当前在排队时已有 request_id，不能等 Session completion 再替换 Turn 身份 |
| 标题或模型生成 slug 作为身份 | 字符更有自然语言含义 | 重复、改题、修订和多语言使身份与内容变化耦合，不适合通用交互身份 |

上表保留身份方案的权衡。当前以真实活动日期 + 日内分配序号作为 Turn 身份的目标方向；维护者已明确确认 request/Turn 分工，以及模型正式引用保留日期。标题/摘要与引用共同显示和折叠的原则不变，也不承诺字符缩短等于 tokenizer 成本同比下降。

输入的 command/input_id、问题 reply_to 等仍承担去重和关联。若把 Trace input 改成 `#input/2`，应明确它是已接受输入序列的稳定 occurrence，与原 input_id 分工；复用现有 canonical 输入顺序及 completion 映射，不建立第三份输入事实。Session 当前已有该 occurrence 语义，可在后续身份方案中评估对齐。

范围建议限于模型实际复制的 Turn、Trace 局部身份、Session 解释节点，以及确有收益的临时结果句柄。generation/request/job 等内部 ID 不因含 UUID 就全库替换；但若 Turn/request 共用身份，必须一并核对 queue、SDK handle、Endpoint、Observation、存储和前端。Memory fact/note 身份已有较短稳定 cite，不在此次讨论中顺带重设计。

实施预览继续明确身份产生者、唯一性作用域、持久保存和所有解析消费者。此前禁止“短别名”的约束继续有效；它不禁止把唯一正式身份设计得更短，不再为已确认的 request/Turn 分工和显式日期重复设批准点。

#### 日内序号的可行落点

正式业务身份采用 `(active_day, sequence)`，完整引用如 `turn:trace/2026-10-06/42#entry/17`、`session:turn/2026-10-06/42#action/2`。具体编号、分配状态落点与消费者预览见第 5.3 节，尚不表示 parser 已支持。日期表示所属 CalendarDay，不是接收请求的日期、结束日期或 Reflection 的 source_day。

真实主线为：排队接受 request → 日协调完成 → 取得 active_day lease → 分配并保存本日下一个 Turn 序号 → 启动 User/Reflection Turn → 按既有生命周期完成。跨午夜排队的请求依真正启动时的活动日编号；已启动的长 Turn 跨午夜保持其原日与身份。received_at/started_at/finished_at 各自继续记录真实时间，不由 ID 推算。

Agent 是唯一根调度者，日内 Turn 分配职责放在 Agent；低层原子文件设施可以复用 infra。持久化一个很小的当前日/已分配高水位，发出身份前原子推进；沿既有世代与日协调装配，不放进 Session map，不靠已完成 Session 记录个数生成下一号。原因是失败/取消、Reflection 以及进程退出前未完成的 Turn 都可能不产生 User Session 记录。允许跳号，不重用已分配号码，不承诺重启续跑 Turn。高水位的持久存放点及初始化边界见第 5.3 节；不建立执行 journal 或第二套队列。

单一 Turn 序列可由 User/Reflection 共用，Session 中号码可能不连续；序号表示已分配 Turn 的顺序，不表示第几个成功回答。Session 解释节点/边的局部号码仍归 Session owner 分配；Trace entry/node 在所属 Turn 内分配固定序号，不能把局部对象也交给 Agent 的万能编号服务。现有 Archive 会拒绝 CalendarDay 向后切换；日内时钟回拨不应让已经分配的序号退回。

现有主要调整点是 `request_id == TurnHandle.turn_id == Context turn_id`：request 在入队时已存在并参与去重、排队取消和句柄查询，而实际执行日稍后才确定。已确认显式区分稳定 request_id 与启动后分配的 Turn 身份；排队时没有正式 Turn 编号，启动事件与 handle 绑定一次后不再变化。SDK/Endpoint 的排队控制以 request 身份定位，执行、Context/Trace/Session 使用 Turn 身份。两者表达真实生命周期，不是一个对象的显示长短别名。需一起调整 scheduler、handle/result、命令路由、Reflection、Observation、Endpoint/前端及 Session parser/存储，不仅修改 ref 字符串。

#### 模型侧保留日期（已确认）

此前比较了两种契约，维护者已选择第一种：

| 形式 | 例子 | 解析条件与取舍 |
| --- | --- | --- |
| 正式引用显式带日期 | `session:turn/2026-10-06/42` | 自身标明日期；普通工具仍只接受绑定当天，不因此增加跨日访问；更容易发现旧日引用误用 |
| 日作用域内的局部引用 | `session:turn/42` | 当前 Turn/profile、Session 来源和 SDK lease 必须提供确定的 day；更短，但字符串离开绑定环境不能唯一解释 |

第二种不实施：纯文本旧日局部 ref 单独出现时没有足够信息区分同号目标，为此增加隐式日绑定或别名会加重理解和解析负担。所有带出的正式 Turn 引用保留所属日，不能按今天补日期。

模型正式引用保留日期，Turn 标题可简洁显示“第 42 轮 · 14:32”。不支持双格式混用，不增加跨日读取，也不建立动态短别名表。

#### 时间戳身份的权衡

人类可读时间可编码为 `2026-10-06/143205` 或带毫秒的 `2026-10-06/143205.127`，Unix 毫秒整数也可作为标识。这些都不自动保证唯一：连续失败/短 Turn、User/Reflection 同一时间精度下启动、系统校时与日内回拨都可能重复；更细的时间分辨率不能作为唯一性契约。

要确保唯一，仍需同时间戳追加序号，或保存上次分配值并采用单调推进。前者引入复合身份，后者的数值可能超出实际墙钟时间；把逻辑推进后的值宣传成真实执行时间会误导模型。Unix 数字的人工可读性也较低；包含真实日期、时间、小数和冲突后缀的形式未必比日期 + 小序号短。

当前建议把时间作为邻近叙事而非唯一性来源：显示“14:32:05 开始 · 第 42 轮”，精确引用仍用日期/序号。时间戳方案保留为取舍依据，不额外实现另一套身份。Scope 内顺序按 owner 观察/分配事实，不按墙钟猜因果。

### 4.9 Workspace Inspect 与 U0 契约闭合（方向已确认，待实施）

#### 当前事实与断点

- `workspace.read` 在 `actions/operations.py` 直接调用 `read_text_range`，没有内部 LLM。它返回完整有界 text，但 ActionTraceProjection 会删除 text，只把定位信息作为 canonical payload。
- ActionResultRenderer 用完整 payload 产生临时可见 overlay；Trace 压缩后 entry 使用 canonical message；Session completion 的 `project_action_record` 也保存 canonical payload。所以当前限制既影响折叠显示，也影响持久事实，而不只是“下一轮不继承 Trace”。
- 下一 Turn 不继承前一 Trace，但会通过 Session 消费已完成 Action 的 canonical 投影。本轮明确采用有界读取事实，不要求 Session 存储原正文页。
- 当前 `_current_search_facts()` 使用完整 ActionResult envelope，这是活动 Action fact 的读取入口；Entry 则读取叙事条目保留的 canonical 内容。维护者确认 Inspect/search 可读取已有 ActionResult，本次 Inspect 结果独立折叠。撤回要求所有活动 Action fact 强制返回 canonical 的建议；当前 Turn 读取既有结果不扩大 Session 的持久保留契约，也不新增旧正文存储或释放状态机。
- WorkspaceEngine/WorkspaceService 已有名为 inspect 的内部/SDK 方法，但它只返回 WorkspaceResourceRecord 元数据；没有模型可选的 workspace.inspect Action。新接口不能悄悄将旧 metadata 消费者的返回值换成正文页。
- 旧 read 使用范围内的裸 cursor；SDK browse_text 已有内容绑定 continuation；Home/Memory 的 inspect_document 已有共享片段与披露机制。无需另建读文件后端、模型任务或查询快照数据库。

#### 建议输入输出与资源范围

新增 `workspace.inspect`，由 Workspace owner 解释活动资源 ref。最小输入为 `ref`，辅以可选 `continuation`、收紧页面预算的 `max_chars`；选段直接用 ref 的 `#L…` 或 Markdown 标题，不再同时要求 start_line/end_line/cursor，因此不存在两套范围同时生效的冲突。

读取文本/Markdown/代码时，默认直接返回实际正文；小内容可以一次完整返回，大内容分页。目录 ref 返回直接子项的有界“名称/说明 + ref”，不递归展开全目录。无片段文件 ref 也有效，不要求模型预先知道行号。metadata 与正文、选定范围与整份文档的覆盖必须清楚区分。

PDF、Office、图像等不在这个设计中自动转换或调用视觉模型。可返回明确的资源类型/metadata 和该情景已提供的读取或转换能力说明；请求不支持的正文/片段时给出局部反馈，不能用 metadata 冒充读到了文件正文。若要直接返回图像/PDF 模型附件，需要另行设计多模态 ActionResult 的回放与预算，不能在文本 Inspect 中暗中引入。

直接 Markdown 引用沿已有解析器取得，保留原 label/邻近线索并由来源 owner 解析相对路径；不自动读取目标正文，不推导 backlinks，不调用额外模型制造摘要。基础版本不必强加 query 参数；已知 ref 的读取和 Search 的发现/定位分工即可满足 U0。

返回表达实际 ref、可读标题/说明、真实正文或子项、实际范围和下一页。机器覆盖数据支持校验，模型侧不需要 digest、内部 locator 或存储协议。完整正文不在 TextPart 与 JSON 中无意重复两份；复用叙事计划的 Action 可读投影。

#### 正文、压缩与 Session

采用既有 **foldable ActionResult**：本次实际返回页的正文属于真实 payload，经 visible projection 直接进入模型；canonical projection 保存有界读取事实。前轮建议的 standard 正文持久保留不再执行。“正式 ActionResult”表示实际执行的真实返回，不等于其中所有正文都必须成为可永久回忆的 canonical 内容。

Inspect “至少进入一次实际返回的主循环 Phase1/Phase2 的 LLM 请求后才能折叠”的语义继续有效，直接复用已有 visible_overlay 消费保护。这里的“完整”只指本次实际返回的有界页面；ref 选段、可选 continuation 与单页 max_chars 各自控制读取位置、下一页与返回量，不要求完整文档一次进入模型。每次续页返回独立 ActionResult，分别取得展示保护。

当前 Phase1/Phase2 都在 LLMTaskRunner.run 返回后调用 mark_model_consumed；取得模型响应但输出协议失败也会解除保护，容量拒绝、取消或调用异常没有走到该标记则不会解除。这里明确称为主循环 Phase1/Phase2 LLM 调用，与 Action 内部的 LLM、JEV 判断/评分和 Embedding 区分；后者不解除保护。标记只表示该页已获一次提供给主循环 LLM 的机会，不能证明模型理解、利用或在后续独立请求中仍记得正文。正常预算允许正文继续可见，解除保护本身不删正文；后续容量压缩才移除展示层。Phase1 已满足条件，不能承诺正文必然继续保留到 Phase2。

不为本 Action 扩大 standard 结果保护机制。provider 曾跳过无法原生回放的结果，而消费标记只检查内部 MessageStack；该缺口已获维护者明确授权先行修复，代码及验证证据见叙事计划第 8 节。修复采用忠实的普通文本映射，保留真实结果并验证最终请求，不另建消费回执日志。

有界投影保留：资源 ref 和已有标题/说明、请求的片段或目录、实际返回范围/覆盖、是否仍有后续页及既有执行状态/失败。保留实际范围很重要，例如请求第 10–200 行但页面只返回第 10–32 行，不能把请求意图写成已读完整范围。不要求保留原文摘录或额外生成内容摘要；解释可由“读取设计说明第 10–32 行，所请求范围尚未返回完”构造。目录同样保存有界的目标、返回数量与覆盖事实，不无限复制子项。

Session completion 沿既有 projection 路径只保存读取意图及必要结果事实，线性历史与 Session Action Inspect 使用同一有界投影；不持久化本次正文页，也不把未保存的正文称为可恢复快照。canonical payload 由 Action owner 在产生结果时提供，Session 提交不等待 Trace 压缩，也不根据 overlay 是否消费选择正文。Turn 提前结束时可以保存执行成功的读取事实，不能据此声称模型已使用它。问答、用户输入和其它 Action 的事实保留规则不因 Workspace 的选择而全局改变。

因此，针对已完成 Workspace Inspect 的 `core.context.inspect(session:turn/...#action/...)` 回忆“当时对哪个资源的哪一段做了什么、执行结果如何”；若需正文，再用 `workspace.inspect(workspace:...)` 读取当前内容。活动 Turn 的 `#action/...` 仍可读取 Trace 已持有的实际结果，本次读取再生成自己的可折叠 ActionResult；`#entry/...` 读取相应条目保留的内容。旧行范围可能指向新内容、标题可能已不存在，按现态返回内容或局部失败即可，不重建旧版本。用户要求的“上一轮 Trace 重读”沿当日 Session Action 事实实现，不新增跨 Turn Trace 入口。

continuation 用于活动读取的下一页，完整可见返回保留它；canonical 事实只需记录实际范围和是否有后续页，不把旧 token 当长期回忆身份。写入重要结论时由后续推理、计划或 Memory 的正常事实承载，不强迫 Inspect 自动为原文保存快照。

#### 续页机制与可见性边界（已确认）

continuation 与模型调用无关，只表达所属读取接口的后续页面。当前 Trace/Session DisclosurePage、Home/Memory inspect_document、Workspace 文本浏览、SDK/Endpoint PageOptions 和 Job 输出复用 infra.continuation 的 codec；SearchViews 另有绑定有界结果视图的临时 token。共同抽象和各自绑定已补入 `docs/design/references.md`，不以字段同名推导可跨 owner 混用，也不为本轮建设统一 token 存储。Search 续页不重新调用模型或重跑搜索；Job 输出可增长，不能套用固定文档快照的含义。

当前 core.context.inspect 的 next_continuation 只在完整返回中，canonical 仅为 ref/inspected；测试 `tests/kernel/context/test_actions.py::test_context_inspect_continuation_is_visible_only` 明确覆盖这一事实。因此需要区分：折叠不使 owner 中仍有效的 token 自动失效，但它可能移除模型当前能取得 token 的唯一位置。Phase1 消费后、Phase2 因容量折叠时也可能出现这种情况。

已确认沿有界回忆语义保持 token 临时：正常可见期间直接续页；折叠后仍有 token 且 owner 校验有效就可使用，否则根据已保存的资源/请求/实际范围重新 Inspect 当前内容，或主动选择后续范围。没有 token 时不声称延续了同一次分页，新读取返回当前内容并重新建立页面绑定。已发生的续页调用可能在 request 事实中保留旧 token，这不构成持续可用的承诺。

本轮不额外保证容量折叠后仍能取得旧 token，不新增一层投影或 token 保存服务。不把“分页设计成立”误写成“旧分页始终可恢复”。

#### 分页、服务和失败

续页沿同一个 Inspect 入口，token 绑定实际读取目标、范围、内容及 owner 所需作用域；日切、失效或内容变化不能默默续接另一份内容。优先复用现有 OpaqueContinuationCodec、片段解析和 Workspace 文本读取设施，新增能力落在原 inspection/Engine/Service 中。页内原文和范围须来自同次读取，不为分页建立 CAS、跨进程文件快照承诺或无限文件缓存。容量约束区分扫描/来源上限与单页显示上限，不能为输出几千字符就无限读入整个文件；也不能把一个较长文件一律变成无法浏览。

现有元数据 inspect 在 owner/service 内改名为 `stat`，新的 `inspect` 对应正文披露服务；迁移点见第 5.3 节。SDK/Endpoint 保持同一 Workspace owner，前端 metadata、编辑全文及 blob 消费者保留各自真实用途；不能用同名方法返回形状的静默变化蒙混过去。

未知目标、无效/缺失片段、范围不合法、内容类型不支持和 continuation 失效是可修正局部失败；根不可用、存储损坏等仍由 Workspace bridge 处理。正文属于成功结果，失败只保留短反馈、稳定 reason 及有用约束。Action timeout 与能力授予继续由 Catalog/profile 负责。

旧 read 的重新设计或删除由维护者后续处理，本计划不顺带重写其全部用途。新 Inspect 复用底层设施但不调用旧 Action、不建立 read 的兼容别名；默认顶层指导只讲 Inspect，域级指导明确推荐新入口。若现有调用点仍使用 read，作为真实消费者记录并按已确认字段迁移，不声称已经移除。

#### 实施准备结论

已确认新增 Workspace Inspect、无内部 LLM、完整 ref 选段与分页、目录/非文本边界、正文进入真实 ActionResult，并复用有界结果折叠，不保存旧正文。第 4.8 节 request/Turn 分工与模型显式日期已确认；第 4.10 节范围清理沿前轮方案纳入契约。折叠后不额外保留续页 token 已确认；被读取 Action 的既有结果与本次 Inspect 的折叠/持久化分别处理。第 5.3 节已补齐 owner/service 命名、编号分配落点和实现预览，目前没有阻塞实施的产品决策。

### 4.10 全 Workspace 范围与空 locator 的解释

该问题只涉及 Search 请求中的 `source.scope`。当前 ResourceScope schema 对 workspace/directory/file 三种 kind 都要求 locator；typed 校验又要求 kind=workspace 时 locator 必须为空，另外两种则必须是非空 Workspace 引用：

| 搜索范围 | 当前 scope | 建议目标 scope |
| --- | --- | --- |
| 整个活动 Workspace | `{"kind":"workspace","locator":""}` | `{"kind":"workspace"}` |
| docs 目录内 | `{"kind":"directory","locator":"workspace:docs"}` | `{"kind":"directory","ref":"workspace:docs"}` |
| 指定文件 | `{"kind":"file","locator":"workspace:docs/plan.md"}` | `{"kind":"file","ref":"workspace:docs/plan.md"}` |

当前协议能够工作；空串是“没有具体资源范围”的占位，问题是 schema 强迫调用者填写一个在该分支没有身份含义的字段。kind=workspace 已完整表达全范围，机械改名会变成 `ref:""`，违背 ref 精确定位目标的共同理解。

目标 schema 按 kind 表达三种合法形状：whole 分支只有 kind，directory/file 分支必须有非空 ref。typed 对象可以沿现有 ResourceScope 明确表达可选身份及分支不变量，无须为这项清理新建泛用范围平台。全范围若携带多余 ref，应反馈无效请求，不悄悄忽略；文件/目录缺 ref 或为空同样拒绝。

完整请求示意：`{"source":{"kind":"query","scope":{"kind":"workspace"},"query":"问答卡片"}}`。外层 source.kind=query 选择检索来源方式，scope.kind=workspace 只指定在哪个范围检索；不是两套资源身份。

修改范围包括 ResourceScope 的 parse/serialize、SearchCapability 生成 schema、Workspace engine 的范围筛选、前端 searchModel/类型、SDK/Endpoint 示例、默认 Skill 与契约测试。底层搜索范围、where/exclude_refs、预算和页语义不变；无需引入 `workspace:` 根资源、把目录 ref 改成路径串，或调整真正携带 day/view 绑定的 ResourceLocator 对象。

## 5. 实施范围与顺序

两份计划按统一顺序推进：完成准备核对 → 交互叙事与展示保护 → Turn 身份和 Trace/Session 引用 → 各资源 owner 的引用迁移与 Workspace Inspect → 总体验收。每一步同步受影响的 SDK/Endpoint、前端实际消费者、默认资源与文档，不把所有接口对齐留到最后。已确认格式以 `docs/design/references.md` 为准；问答可见性不依赖全库字段重命名，先沿 owner 入口实现，再统一迁移其引用编码。

### 5.3 结合当前代码的实施预览（准备完成，代码未实施）

#### 身份分配、传递和存储

- Agent 在取得 `active_day` lease 后、启动 User/Reflection 内核前分配 Turn 身份。唯一编码为 `YYYY-MM-DD/<正整数>`，日内从 1 开始；两种 Turn 共用序列，允许跳号。`request_id` 继续在接受请求时产生，不改短码。
- 分配状态由 Agent 日协调持有，装配时显式传入实例根下 `runtime/agent/turn-sequence.json`；只保存日期和已分配高水位，复用 infra 单文件原子写。重启/重载读取同一状态，新日首次分配推进到新日期。该文件是运行服务状态，不放入 Session/map 或逐日归档；沿既有实例独占与串行根调度，不增加日志、CAS 或多写者分配服务。已有日切规则继续拒绝倒退，不另做时钟恢复链。
- 日期/序号的值与编解码是 Kernel 执行身份的共享契约，Agent 负责分配；Context、Session、SDK 复用该契约，各自构造自己的 ref。不能让 Context 自行生成另一种生产 Turn 身份，也不让下层导入 Agent 分配器。共享纯值协议确有多个消费者，可独立放在 Kernel，避免各 owner 复制日期解析正则。
- `handles.py` 的 handle/snapshot/result 显式区分 `request_id` 与尚未分配时为 null 的 `turn_id`。排队取消或启动前失败可以没有 Turn；分配后绑定一次。scheduler 字典、排队查询与控制始终按 request 查同一个 handle；`RunScope`、Context、Jobs 和 Session 使用正式 Turn 身份。继续使用同一 inbox、Future 和结束流程，不增加第二套请求状态机。
- `commands.py`、`dispatch/inputs.py`、`user`、Reflection、SDK 服务和 Observation 同步传递正确身份。EnvironmentEvent 的投递目标继续定位已接受请求的 handle，订阅登记与注销使用 request_id；Job 仍按真实 turn_id 直接绑定所属 inbox。事件传输目标与业务事实身份有明确分工，不为二者建立显示别名表。补额参数中的既有 request_id 另明确为 `budget_request_id`，避免与根请求混淆。
- Trace entry/node 各自在 Turn 内从 1 分配固定序号；input/action occurrence 沿既有事实序列从 0 开始，已发出后不重新编号。`input_id`、`reply_to`、question/result/call ID 继续承担关联职责，不作全库 UUID 清理。
- Session node/edge 各自在当日 map 内从 1 分配，格式为 `session:node/<day>/<sequence>`、`session:edge/<day>/<sequence>`。复用 Organize 候选构造与原子提交：map 保留撤回对象，可从已有最大序号继续分配，无需额外计数文件。标题和成员变化不改身份。
- Session 已按日持有根目录；记录落为 `turns/<sequence>.json`，完整日身份仍在记录和 manifest 中。`records/models.py`、`records/store.py` 同步解析、校验归属日和列举，按事实顺序而非文件名词法顺序展示。不能直接把带斜线的 Turn ID 塞进旧文件拼接再继续使用 `glob("*.json")`。
