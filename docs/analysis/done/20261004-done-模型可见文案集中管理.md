## 目标与可行性判断

代码中的固定指引、输出说明、工具描述、自然语言包装和局部修正反馈原先分散在各业务调用处。将这些内容移入 `tinysoul/prompts/`，可以按 owner 集中阅读和维护，并从定义注释与显式引用追踪模型可见位置。

方案可行，因为它分离的是文字内容，不接管业务过程。Context、TaskPrompt、Action schema、来源解析和 Runtime 的所有权均可保留。Python 常量与具体签名的文本函数直接随包发布，不引入资源加载、模板解析或新的失败生命周期，也不会让 Context render 增加文件操作。

“提取硬编码”表示将作者维护的自然语言从业务流程中分离；这些文字仍是源码内容。没有 PromptEngine、PromptRegistry、通用模板参数字典、第二套消息 DTO 或无状态空壳类。

## 规约与现有设计核对

实施前重新阅读根 `AGENTS.md`，核对 Loop、Context、Action、LLM、Home、Reflection、Workspace 与 retrieval 的设计和实际请求出口。

- `kernel/context/prompts.py` 定义 PromptBlock、TaskPrompt、PromptGuidance 及来源协议，保留原位。
- `kernel/loop/prompts.py` 仍组合 Phase 指引、情景、反馈与 domain Skill。
- `plugins/workspace/prompts.py` 仍解析引用、准备正文和组合局部 TaskPrompt。
- `plugins/reflection/turn/prompts.py` 仍选择 Home/Memory 情景，并拒绝未知情景。
- `agent/user/prompts.py` 原先只有固定 tuple，已移入内容包；原转发导出一并删除，不保留兼容别名。
- 模型可见 JSON 的键、枚举、ref、Link、label、状态与事实投影由原 owner 维护；用户输入、资源正文、模型输出和外部工具定义不作为文案常量。

## Action Catalog 与 Home

维护者已明确：Action Catalog 属于可配置能力定义，与源码固定文案是两种用途。domain/action description、selection_hint、use_when、avoid_when、examples 和参数说明继续属于项目 TOML，由 Action loader 与既有配置机制消费。本次只抽出代码中的固定模板和包装，没有增加副本或改变配置生效语义。

Home 继续拥有身份、偏好和 Skill，也保留普通 Turn overlay 与 Reflection review 的职责。内容包不向 Agent 授予编辑入口，不通过 Home 读取固定提示。维护导航指向 Catalog 与 Home 的真实来源。

## 异常处理复核

本次沿实际反馈路径追踪 `feedback`、`model_feedback` 及已知局部异常的 `str(exc)` 来源：

- LLM 的 ResponseInterpretError 仍在 task 边界转为 TaskFailure。
- ActionSchemaValidationError 仍由 SchemaNormalizeHook 转为 ActionLocalFailure；hook、timeout 和 scope 失败保留原有有限原因与结果结构。
- PhaseFailure 仍结束当前 Cycle，由下一完整 Cycle 接收反馈；没有增加 Phase 内协议重试。
- Workspace PromptReferenceError 仍表达已知资源不可用；不可继续的 owner 失败仍进入原 bridge。
- Search、Organize、MCP/ACP 等请求校验保留原局部错误类型、捕获位置和结果投影。
- Action 的取消、RuntimeException、RuntimeTransferInterrupt 与普通局部结果继续独立处理。

纯文本函数不接收 Exception，不决定错误类别或运行转移。不新增通用 catch、吞错、空文本 fallback、PromptFailureKind 或 Runtime bridge。内部候选不变量、SDK 专用反馈、存储解析、日志与 Runtime 诊断未当作提示批量迁移；复核发现的 Session map 持久化解析错误已留在原 owner。

这是对文案提取边界和受影响路径的复核，不宣称完成全仓异常正确性审计。
