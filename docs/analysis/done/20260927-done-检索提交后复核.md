## 复核范围

本次复核重新加载项目协作规约，并对最近两轮检索重构的代码、设计文档、Action schema、插件来源、Search 管道、Inspect 渐进披露和 SDK 服务路径进行交叉核对。重点检查候选来源与约束操作是否仍保持统一内容流，Search 返回是否能为后续 Inspect 提供 refs 及真实内容预览，以及正常执行路径是否仍有旧协议残留。

## 结论

Search 已按有限函数管道实现：query、backlinks、directory 负责发现候选，select、rerank、filter 负责约束候选；候选统一经过来源 owner 的内容展开、证据片段和分页生命周期处理。query 的 lexical 与 embedding 结果通过并集进入候选集合，lexical 不会覆盖语义结果；select、rerank 的模型输入包含候选资源的真实内容预览；最终结果和续接页保留 refs、内容片段和必要命中证据。

Inspect 仍是已知 refs 的确定性、渐进式读取，不调用额外模型；Search 的结果页可作为 Inspect 的入口。Session、Home、Memory、Workspace 和 MCP 的来源实现遵循各自 owner，Reflection Home 查询使用 effective Home 的既定决策，来源范围和权限没有在 retrieval 层重复实现。

## 提交后修正

1. `SessionPlugin` 的 SDK 搜索闭包仍读取已删除的 `request.options.scope`。现改为从类型化 `request.source.scope` 读取，并增加 SDK 搜索及续接页回归覆盖。
2. `filter.where` 的执行对象和解析器已经拒绝空对象，但 Action tool schema 原先没有表达这一约束。Action schema 子集现支持对象的 `minProperties`/`maxProperties`，retrieval schema 为 filter 的 where 设置 `minProperties: 1`，并增加 schema 与 parser 一致性测试。

这两项修正保持既有设计语义，没有增加兼容协议或第二套过滤行为。
