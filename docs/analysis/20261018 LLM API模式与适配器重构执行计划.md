# LLM API 模式与适配器重构执行计划

日期：2026-10-18。

状态：`pending / ready-to-implement`。设计已根据官方 API 文档和当前代码重新核对，等待依赖安装后逐阶段实施；本文件描述目标结构、迁移步骤和验收门槛，尚未把任何实现标记为完成。

目标：以 API 模式组织模型接入，明确 provider、adapter、model 的关系；复用现有调用、配置保存和前端草稿机制，消除重复规则及 SDK 隐藏行为。无需旧配置兼容层。Anthropic Messages 与 Google GenerateContent 本轮先完成模式契约、规则目录、配置投影和通用 adapter 装配边界，真实 SDK 请求在后续阶段接入；本轮仍提供完整的配置与前端编辑能力。

已确认方向：候选思考档位数组与顶层选定值分离；通用 adapter 允许未占用字段的 `extra_body`；OpenAI 采用较新模型的 `prompt_cache_options`，删除旧 `prompt_cache_retention`；provider 以 API 模式 endpoint 组织；专属 adapter 是通用 API adapter 的子类或明确行为实现；Anthropic 与 Google 的 API 模式和 adapter options 本轮同步进入后端 catalog 与前端配置。Anthropic/Google 本轮建立完整配置与 adapter contract，但真实 SDK 网络调用留到下一轮，配置页面不会隐藏它们。

## 1. 已核对事实

| 位置 | 当前行为 | 需要改进的原因 |
| --- | --- | --- |
| `llm/protocol/` | TinySoul 内部消息、工具、请求、响应、模型等契约 | 保留内部协议含义，不用 protocol 同时命名外部 API 与模型变体 |
| `protocol/adapter.py` | adapter 规则、供应商选项验证与 Kimi k2/k3 分支 | 具体适配规则应归 adapter；当前通用 Chat 的 options 为空 |
| `provider/openai_sdk/` | 已有 Chat / Responses 公共请求与响应映射 | 可复用，不需要另写平行 mapper；通用 Responses 尚未单独登记供用户选用 |
| 专属 provider 模块 | 公共 adapter 子类 + behavior 对象组合 | 定制入口重复；统一为通用 adapter 的明确子类覆写点 |
| ProviderSpec | adapters 列表、一个 URL、凭据环境变量 | 应按 API 模式声明入口，避免重复声明 kimi/deepseek 等实现类型 |
| ModelSpec | 单一 adapter、有序 provider_model bindings、能力及两组参数 | 基础关系正确；保留稳定 ID 和有序 binding |
| execution/task.py | task/call 设置、model overrides、provider/model 重试切换 | 保留唯一调用协调者，加入通用 top_p |
| SDK 初始化 | 未显式关闭 OpenAI SDK 重试 | 本地 SDK 默认重试 2 次，会叠加已有任务重试 |
| 前端模型与 provider 页面 | 根据 provider.adapters 筛选；从后端读 options/protocols | 改为 api_mode 匹配，继续消费后端规则，避免前端重写供应商知识 |

当前 `openai` adapter 实际是 GPT 的 Responses 行为；`openai_compatible_chat` 是通用 Chat。Kimi 的 `protocol=k2/k3` 是专属行为分支，两者仍使用 Chat API。Family 和 collapsed 已经只用于展示；模型文件按 family 组织。

现有异常主线合理：ConfigError → 配置边界；ProviderError → LLM 局部重试/切换；TaskFailure → 已完成调用的协议反馈；LLMInvocationFailure → 无法继续的模块失败；`run` 通过 RuntimeLLMBridge 进入 Runtime，`invoke` 保持可组合。重构继续遵循此分层。

本地环境已安装 `openai==2.36.0`，未安装 `anthropic`、`google-genai`；没有真实远端调用验证。参考材料在 `reference/api_mode/`，该目录被现有 `.gitignore` 忽略；本文件独立记录需要版本管理的设计结论。

## 2. 术语与所有权

| 概念 | 负责什么 | 例子 |
| --- | --- | --- |
| 内部协议 protocol | TinySoul 的消息、工具意图、调用输入与输出 | MessageStack、TaskCall、RawResponse |
| API 模式 api_mode | 线上请求/响应结构及 SDK 调用入口 | openai-chat、openai-responses、anthropic-messages |
| Adapter | 从内部协议转换到一种 API 模式，并解释响应 | openai-chat、gpt、kimi、deepseek |
| Adapter variant | 同一 adapter 内有实际语义差异的行为分支 | Kimi 的 k2/k3 |
| Provider | 可独立启停的一组服务入口及其共享凭据 | orca、openai、deepseek |
| Model | 任务引用的稳定逻辑模型、能力、选项与 provider chain | gpt-sol、deepseek-pro |
| provider_model | 特定 provider 接受的不透明远端名称 | openai/gpt-5.6-sol |
| family / collapsed | 展示分组、文件组织与默认折叠 | GPT、DeepSeek |

Provider 不再声明模型 adapter 列表。Model 仍只选择一个 adapter，api_mode 从 adapter 的后端定义派生；不让用户重复填写 model.api_mode，也不允许 binding 再选择另一个 adapter。

Model adapter 与 family 没有强制同名关系。新 family 可以使用通用 adapter，不需新增 Python 类。模型 ID、provider ID、API 模式和 adapter ID 使用 lower-kebab-case；Python 包名、字段名仍用 snake_case。远端模型名及外部参数值保持供应商原样，不做全仓字符串替换。

Kimi 的配置从 `adapter_options.protocol` 改为 `adapter_options.variant`；目录、类型、catalog、前端标签与文档统一称“适配变体”，不根据 provider_model 字符串推断变体。

## 3. API 调研对设计的约束

| API 模式 | 思考控制 | 原生回放状态 | 缓存要点 |
| --- | --- | --- | --- |
| OpenAI Chat | reasoning_effort；模型支持集合不同 | 第三方 reasoning_content 属于兼容扩展 | 支持字段随具体模型变化 |
| OpenAI Responses | reasoning.effort、summary | reasoning items / encrypted_content；摘要另存 | 不能把旧 retention 字段当成全部模型统一配置 |
| Anthropic Messages | thinking mode/budget、output_config.effort | 完整 thinking/signature/redacted blocks | cache_control，与内容块位置相关 |
| Google GenerateContent | thinkingConfig 中 level 或 budget | 与 part 关联的 thoughtSignature | 隐式缓存；部分模型还支持显式缓存资源 |

来源：[OpenAI Chat](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create)、[OpenAI reasoning](https://developers.openai.com/api/docs/guides/reasoning)、[OpenAI caching](https://developers.openai.com/api/docs/guides/prompt-caching)、[Anthropic thinking](https://platform.claude.com/docs/en/build-with-claude/thinking)、[Anthropic effort](https://platform.claude.com/docs/en/build-with-claude/effort)、[Anthropic caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)、[Google thinking](https://ai.google.dev/gemini-api/docs/generate-content/thinking)、[Google caching](https://ai.google.dev/gemini-api/docs/generate-content/caching)。

额外发现：Google GenAI 是 SDK，当前官方文档还区分 Interactions API，并推荐新接入使用它。它的请求结构、状态与缓存不同，应使用单独的 `google-interactions` 身份；`google-generate-content` 明确表示 GenerateContent，不能让同一个 api_mode 随 SDK 升级改变含义。[Google Interactions](https://ai.google.dev/gemini-api/docs/interactions-overview)

OpenAI 最新模型路径使用 `prompt_cache_options`：`mode` 控制 implicit/explicit，`ttl` 当前为 `30m`，内容块可标记 `prompt_cache_breakpoint`；`prompt_cache_key` 只是可选的缓存路由/统计提示。旧的 `prompt_cache_retention` 不再进入新的模型配置。implicit 模式不要求 TinySoul 先实现断点，explicit 模式只有在内部消息能够表达稳定内容边界后才开放给前端。GPT-6 文档还描述了使用 `configuration_update` 在会话中改变 reasoning effort 的方式；本轮模型级 effort 保持固定，不引入任务级动态更新，以保持 TaskCall 和缓存前缀的简单语义。[OpenAI prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)

SDK 代为发送 HTTP 和认证头，不消除 header 概念。额外路由头、版本头或环境变量引用仍属于 provider endpoint。Google 云端 IAM、Bedrock 等接入不自动被“URL + API key”涵盖，本轮不引入无消费者的认证框架。

## 4. Provider 配置

建议使用按 API 模式命名的 `endpoints` table；每个模式一个入口，provider 级 enabled 和凭据保持现有语义。以下仅为结构示例，域名不表示已验证服务：

```toml
[llm.providers.gateway-main]
enabled = false
api_key_envs = ["GATEWAY_API_KEY"]
headers = { "X-Client-Name" = "TinySoul" }

[llm.providers.gateway-main.endpoints.openai-chat]
base_url = "https://gateway.example/chat/v1"

[llm.providers.gateway-main.endpoints.openai-responses]
base_url = "https://gateway.example/responses/v1"
headers = { "X-Route" = "responses" }
header_refs = { "X-Route-Token" = "GATEWAY_ROUTE_TOKEN" }
```

- 共享 api_key_envs 只保存一次，继续按现有顺序取首个已配置值。普通 header 放 headers，敏感 header 保存环境变量引用；复用 Infra 现有 credentials 设施。
- provider 可声明共享 headers/header_refs，endpoint 可局部覆盖；先分别解析两层，再由 endpoint 同名项覆盖共享项。标准认证由 API client 处理。前端只展示凭据名称与状态，不投影密钥值。
- 不另加 endpoint ID、优先级、enabled、模型白名单或 adapter 白名单。删除 endpoint 表示不再提供这个模式；同模式确需不同服务/凭据时，新增一个 provider 即可。
- `base_url` 保存该模式 SDK 接受的根地址，前端按模式提示路径约定；不统一补 `/v1`。未来 Google 的 API version 等字段随实际 adapter 一起引入。
- Provider 启用仍要求本地凭据就绪，不进行隐式网络探测。禁用 provider 可继续保留在模型链中。

兼容判断统一为：`adapter.api_mode in provider.endpoints`。是否启用单独决定运行可路由性，不把禁用 provider 从编辑候选中永久隐藏。API 模式匹配并不证明远端模型存在、所有扩展参数可用；用户继续显式填写 provider_model。

一个逻辑 Model 的各 binding 继续承诺同样的能力和选项。若某条服务路由实际提供不同的能力，应另建模型配置，不逐渐给 binding 添加另一套 options/overrides。

现有模板映射：orca 的 adapters 列表合并为 Chat 与 Responses 两个 endpoint；openai、wenrugou、sublyx-proxy 配置 Responses；deepseek、kimi、glm、minimax 配置 Chat。仅迁移当前声明过的能力，不因服务名称猜测它还支持其他接口。development/standard 共用结构，各自保留正常可编辑的启用状态与路由顺序。

## 5. Adapter 组织与复用

建议 `tinysoul/llm/provider/` 改为 `tinysoul/llm/adapter/`，保留 ProviderSpec 表示服务供应商。拟采用：

```text
llm/
  protocol/                 # 内部调用、消息和响应值对象；只留必要身份类型
  config/                   # TOML 边界、provider/model/task 解析
  adapter/
    base.py                 # ModelAdapter / AdapterRequest / 供应商失败分类
    catalog.py              # API 与 adapter 选项规则，组合与前端投影
    factory.py              # 显式装配，公共入口
    registry.py             # 唯一 client 与绑定 adapter 生命周期 owner
    openai/
      client.py             # AsyncOpenAI 装配、SDK 异常边界
      chat.py               # OpenAIChatAdapter
      responses.py          # OpenAIResponsesAdapter
      ...                   # 复用现有 payload、response、tool-name helpers
    models/
      gpt.py                # GptAdapter(OpenAIResponsesAdapter)
      kimi.py               # KimiAdapter(OpenAIChatAdapter)
      deepseek.py
      glm.py
      minimax.py
  execution/                # 任务、模型链、provider 链与局部恢复
```

通用 adapter 自身可以被模型选择。现有 `openai_compatible_chat` 改为 `openai-chat`，现有 `openai` 专属 adapter 改为 `gpt`，新增可选择的 `openai-responses`。其他专属 adapter ID 保持现有清晰名称。

通用类负责消息、工具、输出格式、usage 和 stop reason；专属类只覆写确有差异的参数/约束/响应处理。现有薄子类再注入同职责 behavior 的双层定制可收敛为受保护方法，不再创建一层重复的 strategy。SDK 客户端注入仍保留，便于资源复用与无网络测试。

后续真实接入 Anthropic / Google 时，按同一边界完成 invoke 和 SDK 生命周期。本轮会建立它们的配置定义与可编辑选项，但不把未接通 SDK 的模式伪装成可执行 adapter。

本轮建立四种模式的定义和前端可编辑规则。`runtime_available` 与简短原因是由已注册 factory、SDK 安装状态和当前配置派生的投影，不写入 TOML，也不建立 `configuration_status/runtime_status` 两套状态机。配置解析、TOML 编辑和 catalog 展示接受四种模式；Generation 只为有实际 factory 的 binding 建立调用 adapter。任务链可以保存尚未接通的模型，但真正调用到该 binding 时返回明确的 LLM configuration failure，不发起请求；保存无关模型或 apply generation 不因它提前失败。等真实 SDK 接入，只需注册 factory 并更新投影。

Client 按 `(provider_id, api_mode)` 创建并复用；绑定 adapter 按 `(provider_id, adapter_id)` 取得相应 client，由实际 Model 引用推导需要的组合。Registry 唯一拥有 client，adapter 借用；generation 结束或装配失败时关闭一次。保留单一公开装配门面，不新增第二套 provider 服务或动态插件发现平台。

## 6. 选项定义与层次

规则层次为：API 模式的通用规则 → 专属 adapter 的增补/限制 → variant 的增补/限制 → 当前 model 的值。规则组合只在后端完成，前端消费有效字段及来源标识。复用当前 AdapterSpec/AdapterOptionSpec 的职责，不做通用 schema 编程语言。

- `ApiModeSpec` 提供该模式通用 adapter 的规则；它不承诺所有兼容服务支持所有选项。
- `AdapterSpec` 指向唯一 api_mode，声明新增、替换或禁用规则；variant 仍只是有限命名分支。
- adapter 配置解析后成为明确 typed options，运行期不用多个模块反复从宽泛 dict 解析同一值。具体 dataclass 归对应 adapter，不把所有供应商字段塞进一个万能类型。
- catalog 暴露已组合的选项、类型、可选值/建议值、适用变体与来源。服务端校验是权威边界，前端只做即时编辑检查。

需要区分真实协议限制与模型易变的可选档位。缓存模式、thinking 对象形状等可以有固定校验；某个模型支持哪些 effort 不应永久硬编码在全局 adapter 枚举里。

### 6.1 Request overrides

`request_overrides` 仍表示模型对通用请求参数的固定覆盖，不是任意 JSON 请求体。增加 `top_p`，与 temperature、max_output_tokens 同级；Task CallSettings 和任务编辑页同步支持 top_p。

优先级明确为 task settings → 单次 call settings → model.request_overrides → adapter 必要的协议归一化。最后一步只能执行已声明的规则，例如思考模式不接受采样参数，不可在 HTTP 400 后猜测性删字段重试。

top_p 是 nucleus sampling 的累计概率阈值，不是模型的置信度。通用边界验证有限数值及合理范围，API/模型进一步限制由 adapter 解释。temperature 与 top_p 都允许配置，界面提示通常选一种调节方式，不强加所有 API 都不允许二者并存的错误限制。

对于不接收采样参数的通用 API 模型，可提供简单的 adapter 选项 `sampling="omit"`；默认 `pass-through`。专属 adapter 可以声明更准确的约束，例如当前 GPT 推理规则；UI 据此说明实际会省略哪些参数。这样不需要给 TOML 引入 null 或让用户通过 extra_body 覆盖 temperature。

### 6.2 思考强度的声明与选择

按照用户建议，编辑可用档位时输入逗号分隔文本，模型主面板用下拉框选当前值。持久化保持数组和单一选择分离：

```toml
[llm.models.example-latest]
family = "Example"
collapsed = false
adapter = "openai-responses"
providers = [{ provider = "gateway-main", provider_model = "vendor/model-latest" }]
context_window_tokens = 131072
capabilities = ["text_input", "tool_calling", "reasoning_output"]
reasoning_effort = "xhigh"

[llm.models.example-latest.adapter_options]
reasoning_efforts = ["high", "xhigh", "max"]
reasoning_keep = "encrypted"
reasoning_summary = "auto"
store = false
sampling = "omit"

[llm.models.example-latest.request_overrides]
max_output_tokens = 32768
```

这是 schema 示例，不表示该虚构模型真实支持这些档位。

- `adapter_options.reasoning_efforts` 是该模型的适配能力声明，只供校验和控件使用，不直接发送给供应商。AdapterOptions 的定义应相应改为“适配声明与专属行为设置”，不是原样转发的请求字典。
- 顶层 `reasoning_effort` 是选定值，只存一份；不再同时保留 adapter_options.reasoning_effort。必须属于声明列表。
- 不配置选定值表示不发送 effort，使用远端默认；字符串 `none` 只在模型明确支持时代表实际档位，不等同于没有配置。
- 输入 `high, xhigh, max` 后去外围空白、去重并保序，写入 TOML 数组。删除当前选中档位时明确要求重新选择或清空，不静默改选第一档。
- API/variant 不支持 effort 时不显示该控制，并在后端拒绝相关配置；思考 budget 单独保留，不把 token budget 换算成虚构档位。
- 当日实现使用的 Kimi k3 max、DeepSeek low/high/max 等集合迁入相应模型配置；新增模型版本支持档位时可编辑 TOML，不用改全局枚举。现有固定协议限制仍由 adapter 保证。
- 本轮 effort 仍是模型级选择，任务链只选模型；不再引入任务级 effort 标签、模型版本快照或 binding 参数覆盖。

### 6.3 通用 adapter 的可用能力

通用 Chat/Responses 都应具有正常的文本/图片、工具、JSON 对象、采样、输出上限、思考与缓存映射；仅呈现该模式实际支持的选项。一般 Responses 的 summary、加密推理回放、verbosity、store、缓存等规则下沉，不再只有 gpt 能用。

对于常见 Chat 兼容差异，提供由 adapter 规则决定的 `output_token_field`（max_completion_tokens / max_tokens）；这是映射元数据，不属于 `request_overrides`，不额外保存第二个 token 上限值。

Chat 的 reasoning_content 可作为显式启用的常见兼容扩展，不能冒充所有 Chat endpoint 的标准能力。新模型需要额外 body 字段时，可使用 `adapter_options.extra_body` 的 JSON 对象；它允许补充未由框架/typed 选项占用的顶层字段，拒绝覆盖 model、messages/input、tools、输出协议、认证、保留容器或已经映射的参数。校验后的扩展仅在 SDK 边界传入，不新增第二套 HTTP 客户端。

extra_body 能解决请求扩展，不能描述任意响应解析、签名回放或工具协议。出现真实不同的响应语义时增加专属 adapter，避免发展成字段映射 DSL。

四种模式本轮的 catalog 规则应至少覆盖下列正常配置能力。字段是 TinySoul 的稳定 option ID，adapter 再映射到外部字段；不是把供应商原始 JSON 全部复制到 TOML。

| API 模式 | 通用/模式选项 | 模型级候选与选择 | 回放/缓存配置 |
| --- | --- | --- | --- |
| `openai-chat` | temperature、top_p、output token field、reasoning_effort | `reasoning_efforts` + `reasoning_effort` | reasoning content（兼容扩展）；缓存 key/policy 按实际端点 |
| `openai-responses` | reasoning summary/context、verbosity、store、sampling policy | `reasoning_efforts` + `reasoning_effort` | `reasoning_keep=encrypted`；`prompt_cache_options.mode/ttl` |
| `anthropic-messages` | thinking mode、thinking budget、output effort、thinking display | `effort` 候选/选择，或专用 `thinking_budget_tokens` | thinking/signature 保留策略；cache mode/TTL |
| `google-generate-content` | thinking level/budget、include thoughts、temperature、top_p | `thinking_level` 候选，或专用 `thinking_budget`，不二次换算 | thought signature 保留策略；implicit/explicit cache 声明 |

选项组合规则：

1. API 模式定义基础字段和字段形状；具体 adapter 可以增加、收窄或禁用字段；variant 再处理有限分支。
2. `reasoning_efforts` 是候选能力声明，`reasoning_effort` 是当前选值；Google 的 budget、Anthropic 的 manual budget 等无法自然表示为档位时保留专属 typed number，不强行换算。
3. `reasoning_keep` 只在 adapter 已实现相应回放时进入可运行配置；Anthropic 的 signature、Google 的 thoughtSignature 先由规则目录描述为 opaque replay，运行 adapter 完成后再接入 `Reasoning` envelope。
4. 缓存 `mode`、TTL、breakpoint 或 cached-content 名称不得合并成一个跨 API 的布尔值。没有真实内部资源 owner 的 Google explicit cache 只允许保存声明，不触发创建、刷新或删除。
5. 前端从组合后的 `effective_options` 渲染控件，并显示派生的 `runtime_available`/reason；不在页面内硬编码另一份供应商参数表。

## 7. 推理状态、缓存与内部协议

以下四件事分别表达：思考模式/投入、可见推理摘要、原生推理状态回放、输入前缀缓存。不能统一成一个“推理开关”或“缓存开关”。

当前 Reasoning.content/summary 可保留语义；encrypted_items 的命名只适合当前 Responses。以有来源的 ordered `NativeReplay` 载荷替代裸 encrypted_items：包含 API 模式、adapter/variant、provider 与远端 model 身份，以及由相应 adapter 校验、按原顺序保存的 JSON blocks/parts 和 tool 关联。当前 Chat 文本回放和 Responses items 是实际消费者；Anthropic/Google 本轮建立统一 envelope 和校验边界，真实 SDK 解析在后续接入。

来源用于当前已有的模型/provider 切换主线：默认只在匹配的调用来源回放不透明状态，不因 API 模式相同就把一家的签名发给另一家。无法原生回放的历史工具交换沿用现有文本投影路径，保留行动与结果事实；这是 TinySoul 的默认回放策略，不宣称供应商绝对不支持跨平台签名。

`reasoning_keep` 本轮继续表达 none/content/encrypted 这些已消费的选择，由 adapter 约束可选项；不为未来模式预填空壳枚举。以后接入完整 block/part 回放时，再增加对应原生策略及关联结构。不能以当前 envelope 已有 JSON 为由宣称完整兼容所有未来 API。

状态仍附着在已有 AssistantMessage/Trace，不新增 provider 私有会话历史。Kernel 只运输 typed envelope，不解析供应商字段。Context 的投影、容量统计和安全 Observation 同步消费它，可读界面不显示加密正文。

PromptCache 改为一次调用的 typed intent（可选 key、implicit/explicit、TTL、最终消息边界），OpenAI 模型选项映射为 `prompt_cache_options = { mode = "implicit", ttl = "30m" }`，不再接受 `prompt_cache_retention`。`prompt_cache_key` 只是路由/统计提示，不是跨 API 缓存资源句柄。OpenAI explicit breakpoint、Anthropic 内容断点和 Google 显式缓存资源需要各自的 typed 边界；本轮不创建没有真实消费者的缓存管理器。

## 8. 调用与错误处理主线

```text
TaskCall + TaskSpec
  → 选择稳定 model ID
  → Model.adapter 确定 api_mode 和有效规则
  → 有序 binding 选择 provider 及 provider_model
  → provider.endpoints[api_mode] 取得 URL / headers / client
  → 合并通用参数、模型覆盖、选定 effort
  → adapter 映射消息/工具/专属参数
  → SDK 一次请求
  → adapter 归一化 RawResponse
  → LLMTaskRunner 解释任务结果，或按既有策略重试/切换
```

1. ConfigError 尽早报告缺少 endpoint、非法 effort 选择、变体选项冲突和未知键；失败候选配置不持久化。
2. ProviderError 继续表达服务错误及 provider/model scope。已知 SDK 鉴权、限流、超时等只在 adapter 边界映射；原始异常链仅用于调试。
3. SDK 重试设为 0，由 Task retry policy 唯一管理。取消、剩余时限与关闭流程复用现有机制。
4. 已返回但不满足任务输出契约的响应继续是局部 TaskFailure，不被重写成无限重试。无法继续才进入模块失败及 Runtime bridge。
5. 缩窄 create 周围异常捕获：SDK 失败与 TinySoul 内部缺陷分开，不能把 TypeError 等实现问题包装成供应商瞬时错误。Observation 仅携带稳定 kind、scope、路由身份等摘要。
6. SDK 不自动执行业务工具、不维护另一份上下文；未来使用 Google SDK 时关闭自动函数调用，并明确关闭或接管自动续写，保持一次 LLM Task 的时限和预算可解释。

## 9. 前端改动预览

Provider 页面：顶部编辑 ID、启用状态和共享凭据；下方为“API 入口”列表，每项显示模式、URL、附加 headers。增加一个模式即增加一个 endpoint 表。去除 kimi/deepseek 等 adapter 多选框。

## 12. 逐阶段执行步骤

每阶段完成后先运行该阶段的聚焦检查，再进入下一阶段。若发现当前代码与本计划冲突，暂停该阶段并修订计划，不用兼容字段或临时分支绕过。

### 实施前：SDK 安装和版本核对

先在 TinySoul Conda 环境安装当前 PyPI 稳定版，不把会变化的 patch 版本预写进设计：

```powershell
conda activate TinySoul
python -m pip install --upgrade openai anthropic google-genai
python -m pip check
python -c "import importlib.metadata as m; print('openai', m.version('openai')); print('anthropic', m.version('anthropic')); print('google-genai', m.version('google-genai'))"
```

若 shell 未激活环境，使用 `C:/Anaconda3/envs/TinySoul/python.exe -m pip ...`。用户安装完成后，阶段 C 会重新检查三套 SDK 的实际 signatures，并将项目最低版本设为本轮真正使用的稳定接口。`google-genai`、`anthropic`、`openai` 分别是三个安装包名称。

### 阶段 A：建立身份、模式和规则正典

1. 在 `llm/protocol/` 增加稳定 `ApiMode`、`AdapterKind` 和派生的 `runtime_available` projection；明确 `openai-chat`、`openai-responses`、`anthropic-messages`、`google-generate-content` 四种模式。若保留 Interactions 预留，只进入设计说明，不进入本轮可编辑模式，避免与用户指定的 GenerateContent 混淆。
2. 将当前 `ProviderApiStyle` 语义改为 API 模式；通用 adapter 与专属 adapter 使用一对多关系：一个 adapter 只指向一个 mode，一个 mode 可以有通用和专属 adapter。
3. 将 `protocol/adapter.py` 的规则拆为 API mode rule、adapter rule、variant rule，迁移 Kimi `protocol` 为 `variant`。删除旧 ID 和字段，不添加 alias。
4. 建立四种模式的 option catalog：字段类型、候选值、是否模型声明、是否请求覆盖、runtime availability、来源说明。规则包含 Anthropic thinking/effort/budget/cache 和 Google thinking level/budget/include thoughts/cache 声明，但不生成未实现的调用代码。
5. 为 `extra_body` 定义 JSON object 校验：拒绝保留字段（model、messages/input、tools、response format、认证、已占用 typed option 及其保留容器），允许未占用的扩展顶层字段；不得在内部传播 `dict[str, Any]`。

验收：后端可生成一份包含四种模式和当前 adapter/variant 的稳定 catalog；未知 option、错误 variant、effort 不在候选列表均成为 ConfigError；前端可以仅依赖 catalog 渲染，不读取 Python 常量。

### 阶段 B：重构 Provider 和 Model 配置

1. `ProviderSpec` 从 `adapters/base_url` 改为 `endpoints`：endpoint key 就是 `api_mode`，每个 endpoint 有 `base_url`、可选 `headers`、`header_refs`。provider 保留 `enabled`、`api_key_envs` 和共享 headers。
2. 解析时合并 provider 与 endpoint headers，endpoint 同名项覆盖 provider 项；敏感 header 只保存环境变量引用。禁止把 API key 或 header secret 写回 TOML。
3. Model 只保留 `adapter`、稳定能力、bindings 和 model options；从 adapter 取得 mode，候选 provider 按 endpoint mode 筛选。一个 Model 的所有 binding 仍必须共享能力和选项语义。
4. `request_overrides` 加入 `top_p`；output token field 是 adapter mapping rule；删除 `prompt_cache_retention`；OpenAI 模型改用 `prompt_cache_options.mode/ttl`，默认仅允许最新模型的 `implicit/30m` 组合，explicit 需内部 breakpoint 能力后开放。
5. Model 顶层保存 `reasoning_effort`，adapter options 保存 `reasoning_efforts`；Kimi/DeepSeek/GLM/MiniMax 的现有 options 迁移到新规则，Kimi 的 `protocol` 改 `variant`，不保留旧配置。
6. 解析和 loader 保持“完整 TOML 校验成功后才替换配置”的原子语义，更新所有标准/development family TOML 和专用配置 fixture。

验收：一个 provider 可有 Chat 与 Responses endpoint，共用一份凭据；新增 DeepSeek 或自定义 Chat 模型无需修改 provider 的 adapter 列表；现有 gpt/kimi/deepseek/glm/minimax 逻辑模型 ID 和任务链引用保持稳定。

### 阶段 C：统一 Adapter 目录和生命周期

1. 将 `tinysoul/llm/provider/` 重组为 `tinysoul/llm/adapter/`，按 `openai/chat.py`、`openai/responses.py` 和 `models/*` 组织；同步 imports、公开 exports、prompts 注释和测试路径。
2. 抽取 `ApiModeAdapter`、`OpenAIChatAdapter`、`OpenAIResponsesAdapter` 公共边界；专属 adapter 只覆写 options、请求约束和响应推理解析。保留可注入 client protocol，删除同职责的重复 behavior 层。
3. Registry 以 `(provider_id, api_mode)` 复用 SDK client，adapter 借用 client，Registry/generation 负责一次 close。运行 adapter 以 `(provider_id, adapter_kind)` 取得 mode client。
4. OpenAI client 显式 `max_retries=0`；任务层是唯一重试 owner。先在 TinySoul Conda 环境升级 OpenAI、Anthropic、Google GenAI SDK，再以实际安装版本检查 signatures，并把 `pyproject.toml` 最低版本设为本轮实际使用的稳定接口；不把会变化的最新 patch 版本写成设计语义。
5. 增加 `AnthropicMessagesAdapter`、`GoogleGenerateContentAdapter` 的配置定义和 adapter contract；在没有 runtime factory 时 projection 标记 `runtime_available=false`，调用边界转换为明确的 configuration failure。不创建伪造的 HTTP 请求或 SDK 自动函数调用流程；后续 SDK 接入只需注册同一 base contract。

验收：公开 factory 只装配已注册 runtime adapter；未注册模式不会发送请求；client 创建/关闭、取消、ProviderError 映射和任务重试次数可由 mock client 验证。

### 阶段 D：重构消息、推理状态和缓存边界

1. 将 `Reasoning` 的不透明载荷从只命名 `encrypted_items` 改为带 `api_mode/adapter/variant/provider/provider_model` 来源的 ordered `NativeReplay` envelope；它必须保留 Responses item、Anthropic block 或 Google part 的原始顺序及 tool 关联，不能把各块拼成一段普通文本。
2. kernel signal、Trace、projection、context window 和 observation 同步迁移 envelope；展示只保留摘要与 digest，不显示签名、加密正文或完整 provider payload。只有来源完全匹配且中间没有删改、重排或合并时才回放；不满足条件时丢弃 envelope，工具回合无法安全降级则返回局部协议/配置失败。
3. 在 OpenAI Responses mapper 中支持最新 `reasoning.context` 的固定模型配置（默认不额外改写历史）；本轮不做 TaskCall 级动态 `configuration_update`，不改变已有 Context 组装。
4. `PromptCache` 改成调用级 typed intent（key、implicit/explicit、TTL、最终消息边界）；OpenAI adapter 映射 `prompt_cache_options`，TTL 当前只接受 `30m`，不再读取旧 retention。Anthropic 的 `cache_control` 绑定内容块，Google 的 `cachedContent` 只保存外部引用；本轮不创建、续期或删除外部缓存资源。
5. 保持消息堆栈由 Kernel/Context 生成，adapter 不保存第二份会话。遇到不能安全回放的跨 mode 状态，按既有文本事实投影或返回明确配置失败。

验收：OpenAI 加密 reasoning 可以在同一来源的后续工具调用中回放；不同 mode 不会误传签名；Trace/Observation 不暴露原始不透明载荷；cache 选项在请求 payload 中只出现一次。

### 阶段 E：Endpoint、Catalog 与前端配置交互

1. 更新 `infra/config/catalog/models.toml` 和配置 projection：provider 显示 endpoints、URL、headers/header_refs；adapter 显示 API mode、派生 runtime availability 和组合 options；删除旧 adapters 字段说明。

## 13. 目标配置示例

```toml
[llm.providers.multi-mode]
enabled = false
api_key_envs = ["MULTI_MODE_API_KEY"]

[llm.providers.multi-mode.endpoints.openai-chat]
base_url = "https://gateway.example/v1"

[llm.providers.multi-mode.endpoints.anthropic-messages]
base_url = "https://gateway.example/anthropic"
headers = { "anthropic-version" = "2023-06-01" }

[llm.models.example-latest]
family = "Example"
collapsed = false
adapter = "openai-chat"
providers = [{ provider = "multi-mode", provider_model = "vendor/example-latest" }]
context_window_tokens = 131072
capabilities = ["text_input", "tool_calling", "reasoning_output"]
reasoning_effort = "xhigh"

[llm.models.example-latest.adapter_options]
reasoning_efforts = ["high", "xhigh", "max"]
extra_body = { vendor_mode = "agent" }

[llm.models.example-latest.request_overrides]
top_p = 0.9
max_output_tokens = 32768
```

`extra_body` 的 `vendor_mode` 仅示例未占用的供应商扩展字段；它不需要先加入全局白名单，但不能覆盖 adapter 已占用或框架保留字段。示例中的 gateway 和 model 不代表当前项目要新增真实路由。Anthropic/Google 模型使用相同的 provider/model 结构，只替换 adapter、endpoint 和其 typed options。

## 14. 计划可行性与预期结果

计划可行，因为它把工作拆成已有稳定边界上的迁移：配置 parser 负责动态 TOML，catalog 负责前端描述，adapter 负责 API 映射，TaskRunner 继续负责模型链和重试。Anthropic/Google 的配置能力不会迫使本轮重建消息内核或缓存资源服务；它们的真实调用可以在同一 base contract 上后续补齐。

完成后，配置者看到的是“一个 provider 提供哪些 API 入口、一个 model 选择哪种 adapter、该 adapter 可配置哪些选项”；运行时看到的是“TaskCall → stable model → adapter/api mode → provider endpoint → provider_model → SDK request”。这条链路不再要求 provider 逐项登记 kimi、deepseek 等模型 adapter，也不会把缓存、思考状态或 SDK 名称混为一谈。

主要风险是一次性重命名范围较大，尤其是测试、文档和前端 catalog 引用；通过分阶段迁移、每阶段聚焦检查和最终 Full/typecheck 控制风险。主要功能不依赖真实网络凭据，只有 OpenAI mapper 的实际请求和后续 Anthropic/Google SDK 接入需要外部验证。
