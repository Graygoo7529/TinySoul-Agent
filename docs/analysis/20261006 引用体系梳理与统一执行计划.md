# 引用体系梳理与统一执行计划

日期：2026-10-06

状态：`pending`（分析与方案，待讨论确认；尚未修改代码、机器协议或当前设计文档）

关联计划：[模型上下文叙事投影与引用语义统一执行计划](<20261006 模型上下文叙事投影与引用语义统一执行计划.md>)。

## 1. 目标与边界

让维护者和模型能够用一致的概念回答三个问题：这个引用指向什么、在什么范围内有效、怎样读取或操作它。统一不仅涉及显示文字，也涉及 Action Catalog、typed request/result、Context、SDK/Endpoint 和当前设计文档中的机器字段。

目标语义是：**引用是由 owner 解释的精确定位值；模型用旁边的标题、摘要或命中依据判断是否需要读取，再把精确值交给支持它的操作。** 资源内容、历史出现位置、动态指向和临时读取状态不能因都含字符串而混为同一种事实。

本计划不建立新的资源数据库、通用文件 API、全局引用图或动态插件发现系统，不复制 Session 的关系图，也不赋予模型原本未授予的读取或写入能力。复用现有 owner、`ReferenceResolver`、`ResourceLocator`、Context segment 路由和 Disclosure/Search 协议；只有真实消费者无法由现有结构表达时才调整公共类型。

## 2. 已核对的引用类别与实际消费者

以下是当前实现清单，不是未来新类型清单。引用类别与来源 owner 是两个维度；不需要为每一行增加一个跨模块枚举。

| 类别 | 当前编码/字段 | 实际语义与消费者 | 有效范围与注意点 |
| --- | --- | --- | --- |
| Home 顶层入口 | `home:agent@<logical-path>`、`home:skills@<skill>` | HomeTopLink；Background catalog/load；home.inspect | 顶层逻辑名不带文件后缀，owner 映射到入口 Markdown；可加载不等于所有 Home 资源可加载 |
| Home 深层资源 | `home:<space>/<path.ext>` | HomeResourceLink；home.search/inspect、资源编辑、Markdown direct refs | 保留真实扩展名；读取后进入 Action 结果，不自动常驻 Background |
| Home 任务挂载 | `home:skills_domain:<domain>`、`home:skills_action:<domain>/<action>` | HomePromptMountLink；对应 TaskPrompt 的局部 Skill mount | 有资源身份，但不支持普通 load_background/home.inspect；相同前缀不代表相同能力 |
| Memory 持久文档 | `memory:daily/<date>`、`entity/concept/fact/note` | MemoryLink；search/inspect、Reflection write、真实 Markdown 引用边 | 身份稳定不等于正文永不变；redirect 与引用校验属于 Memory |
| Memory 动态入口 | `memory:current/latest/target`，可带 fragment | MemoryBackgroundRef；Context catalog、已安装内容及 resolved_references | 依赖 Turn/source day；历史 latest 必须使用当时记录的绑定，不能重新解释为今天 latest |
| Workspace 活动资源 | `workspace:<relative-path>` | WorkspaceLink；Working、read/search、修改 Action、内部 LLM 输入、进程 cwd 与产物 | 依赖日绑定；同一字符串在不同日不表示同一资源实例；不是文件正文 |
| 归档 Workspace 视图 | `workspace_archive:<day>[/path]` | 已安装只读归档段的 navigation/inspect | 当前仅在 profile 安装该段时有效；不是任何 Turn 都能读取任意归档的全局能力 |
| TurnTrace 原始位置 | `turn:trace@<turn>#input/...`、`#action/...`、`#entry/...` | Context 原始 input/action/entry 的 search、inspect、当前证据 | 活动 Turn 内有效；已完成 User Turn 转为 Session 的持久位置，不让新 Turn 读取旧活动 Trace |
| TurnTrace 压缩入口 | 根 `turn:trace@<turn>`、节点 `turn:trace/<turn>/<node>` | Trace heap 导航，Disclosure children | 节点是本轮原记录的组织视图，不是另一份历史；折叠后已返回节点保持可读 |
| Session 事实位置 | `session:turn/<id>` 及 input/action/output/note/resource 等 fragment | Session record、linear interaction、inspect、organize 证据 | 当日或所绑定归档日的历史事实；`#resource/n` 定位“本轮引用了某资源”这一出现位置 |
| Session 解释与目录 | `session:map/history/topics/annotations/unclassified`、`session:node/<id>`、`session:edge/<id>` | Session map、语义注释、Disclosure 导航 | 解释由 Organize 修改；事实与解释有不同来源语义，不能靠前缀统一而抹除 |
| 引用关系和来源 | `origin_refs`、`source_refs`、`DisclosureReference(target, relation, source_day)`、MarkdownReference | Action 来源、Session 解释证据、真实 backlinks；`reply_to` 连接问题身份 | 是现有领域关系；不升级为每个 TraceEntry 必备的通用关系图 |
| 内容片段与命中依据 | URI fragment；ContentUnit.ref/location；SearchEvidence.unit_id/range；ContentSlice | owner 按标题/行等解释片段；Search 把命中范围指回实际读取内容 | fragment、行号、字符范围不保证资源变化后仍是同一段原文；unit_id 是该快照内身份 |
| 解析后的绑定 | `ResourceLocator(link 或 ref, day, turn_id, view)`；resolved_references | SDK/Endpoint 导航、动态 Memory/历史 Workspace 解析、MessageStack metadata | locator 恰有一个 link/ref 身份；附加字段保存作用域，不是另一种内容正文，也不应让模型自行拼装 |
| 相对 Markdown 引用 | 相对路径、`#fragment`、label/target；origin_link | infra 解释 Markdown 语法，来源 owner 解释相对路径，目标 owner 校验目标 | label 说明用途；目标身份不从 label 猜测；没有来源不能正确解释相对路径 |
| 搜索结果句柄 | `result_ref=search-result:<id>` | SearchViews 中完整最终 CandidateSet；source=result 复用 | 绑定 Turn/profile 或 SDK lease；不是长期文档引用，也不是当前页的全部含义 |
| 分页与输出读取位置 | continuation/next_continuation、Workspace read cursor、Job 输出 offset 等 | 各读取协议的续页/位置 | 不属于资源身份；绑定内容、有效范围和重读语义各异，不能仅为字段统一相互替换 |
| 其它领域入口 | `mcp:<server>/<tool>`、`trash:workspace/<id>` | MCP 工具目录 Search、Workspace Trash list/restore | 工具定义入口、恢复入口各自受 owner 操作限制；不是通用 inspect 文件 |
| 局部身份 | Session Organize `local:<id>`、Search 模型候选短 ID、call_id/question_id/job_id 等 | 一次请求的指代、执行关联或监督身份 | 不自动成为内容引用；有真实读取消费者时才建立对应 owner 入口 |

## 3. 当前真实问题

### 3.1 同一语义使用多个机器字段

Home/Memory 的 Inspect 参数使用 `ref`，却接收被其它接口称为 Link 的资源身份；Workspace read 使用 `link`，修改使用 `target_link`，内部任务使用 `reference_links`，Search 范围使用 `ResourceScope.locator: str`。后者不是 `ResourceLocator` 对象，只是资源字符串。

Context Background 仍有 load_links/evict_links 与 entry.link；SearchCandidate、DisclosureHint 则用 ref。仅改中文 ToolSpec 的“链接”为“引用”无法消除维护者对这些字段的理解负担。

还发现具体说明与实现不一致：HomeTopLink 要求无后缀逻辑名，默认 Home Skill 说明也如此，但 `home/top_write.toml` 的 description 仍称 agent link 包含真实 `.md` 路径。应在 schema/Skill/owner 同步审核时修正，不能将旧说明继续写入统一规范。

### 3.2 不同语义又使用同一个名称

Session resource occurrence 同时有 ref、link、locator：其中 ref 是历史出现位置，link 是被引用的资源，locator 带原日/动态绑定。三者不是三个等价名字。若直接把全部 link 改成 ref，会覆盖原字段并丢失历史关系。

Search result_ref 也不是稳定内容 ref；Workspace cursor 与 continuation 也不是可长期保存的回忆入口。必须按消费者迁移，不能全局替换字符。

### 3.3 稳定身份、可读权限和历史原文容易混淆

稳定的 Memory/Home 身份不保证不可变正文；Workspace 还需日绑定。Trace entry、Action fact、Session canonical result、已保存 Heap snapshot 和 owner 当前文件保存的信息量不同。统一命名后仍要明确“读取当时已保存的事实”和“重新读取资源现态”的区别。

同样，Home prompt mount、MCP 工具、Trash 恢复入口都是可指代对象，却不都支持 core.context.inspect。模型知道引用值，不等于它拥有所有操作能力。

### 3.4 引用的解释随压缩丢失

`DisclosureHint(ref,title,clue)` 已有合适结构，Search 也有真实 preview/evidence。但部分 sources 只传裸字符串；foldable Action 只保留 selected refs；Trace node 的 clue 主要是类型、数量或 JSON 截取。这使模型获得精确身份，却不知道为什么需要读取。

“引用与解释一起显示/折叠”的投影修正在叙事计划实施，本计划负责保证身份和读取语义一致，不另建一套摘要状态。

## 4. 建议采用的统一设计

### 4.1 公共词汇与编码原则

1. 模型和当前设计文档以“引用/reference”为总称；“资源引用”“交互引用”“动态引用”等只在差异影响操作时使用。
2. 建议内容身份统一编码为 `ref`，集合为 `refs`；多个不同角色的引用保留 `target_ref`、`source_ref` 等明确名称，局部任务的参考输入可用 `references`，避免 reference_refs 一类重复表达。操作的可接受 owner/目标类别由 schema 与 owner 校验表达。
3. `link` 留给 Markdown/URL 的链接语法或边的自然语言概念，不再作为与 ref 并列且含义模糊的资源身份字段。owner 的 HomeTopLink/MemoryLink 等类名和包名是否改为 Ref，在同一 owner 的调用迁移中统一处理，不建立旧新类名 alias。
4. `locator` 专指“引用及解析所需绑定”的对象，不再同时指裸身份字符串。建议 ResourceLocator 收敛为唯一 `ref` 身份槽及有意义的 day/turn_id/view，保持公共无业务依赖边界。
5. Session 中“出现位置指向资源”明确为 `ref` 与 `target_ref`（以及必要的 target locator），两者同时保留。source_ref、reply_to、references 等有真实关系语义的字段不强行缩成同一个 ref。
6. 临时集合建议使用 `result_handle` 等明确名称，续页继续使用 continuation。Job ID、问题 ID、请求内短 ID 保持原语义。Workspace cursor 是否迁移只由分页契约是否相同决定，不属于必要的命名清理。

这些是目标契约建议，尚未宣布现有接口已经改名。迁移每个 owner 前记录旧字段、目标字段、全部真实消费者与存储影响；完成同一边界全部调用者后移除旧入口，不维持双名协议。

### 4.2 统一字段不强求一种路径语法

保留 owner 对现有地址的解释权，不为了外观一致把 `@`、`/`、`#` 全部重写。Home 顶层与深层资源有真实加载差异；Trace 根、原始 occurrence 与压缩节点也不相同。首要结果是同类字段同义、每个已暴露引用都能清楚使用。

如后续审计证明某个编码本身造成歧义，应提供该 owner 的完整编码迁移方案，并检查 Markdown、持久记录、归档、配置与实际外部消费者。不能把持久引用字符串的变更当作 Python 局部重命名。

### 4.3 绑定留给框架，模型取得可正确使用的入口

- 活动 Context 内的动态 Memory 和当日 Workspace 引用，沿已安装 owner 绑定解释；说明其用途与日期即可，模型不需处理 resolved_references 的内部对象。
- 历史叙事优先暴露 Session occurrence 引用及解释，由 Session 保留当时资源指向和原日绑定。不得把历史 workspace 字符串直接交给当前日写 Action，或把旧 memory:latest 重新绑定为今天。
- 需要从历史进入资源时，读取入口须确实支持该原日/绑定：已有安装的归档段、已有 SDK/Endpoint 日级读取，或明确范围的新 owner 读取能力。当前模型 Action 没有某种历史读取能力时应明确说明；字段统一不自动增加该能力。
- 暂不新增全局“ref 字符串 → 任意历史文件”服务。若维护者希望任何已显示引用都能单参数跨日读取，须另行确认日期限定编码和受约束服务的范围；现有 occurrence 读取与原日定位仍先保持正确。

### 4.4 读取动作的一致理解

统一的使用方法是“看线索 → 选择引用 → 用支持它的只读操作读取 → 继续沿返回的直接引用探索”，无需统一为一个万能工具：

| 当前引用 | 当前读取入口 |
| --- | --- |
| Trace、已安装 Session、已安装归档 Workspace | `core.context.inspect` |
| Home 顶层与深层资源 | `home.inspect`；顶层也可显式加载至 Background |
| Memory 文档 | `memory.inspect`；动态内容依实际 Context/服务支持读取 |
| 活动 Workspace 文本 | `workspace.read`；非文本按资源类型使用对应 owner Action |
| 搜索结果句柄 | Search 的 `source=result`，不能传给任意 inspect |

推荐本计划先保持这些 owner 入口，统一说明、参数与错误反馈。不为了少记几个 Action 名把 Home/Memory 的读取职责塞进 Context。若后续决定提供统一只读入口，应通过已授予服务路由，准确区分已安装快照与 owner 现态，保留分页、失败及权限语义；该项是待确认扩展，不混入字段迁移。

### 4.5 引用与解释成为一个导航单元

模型可见导航通常呈现“有意义的标题或实际摘录 + 精确引用”，必要时附日期、覆盖范围或下一读取方法。同一领域的通用读取方法在入口统一说明，不每行复制冗长工具教程。

优先复用 DisclosureHint 和 Search 的真实内容投影。label、已有 summary、命中片段可作为线索；“命中依据”只在确有搜索证据时使用，普通引用不编造相关性理由。

一个条目过大时，将它的引用和解释作为整体收进父层，父层保留自身解释和引用。Inspect 只展开选定层与页面，让下一层引用自然出现在正文旁边。不会把所有子引用永久保留在顶层，也不会折叠到只剩没有入口的总结。

“引用 + 摘要”是可见性约定，不要求存储所有 refs 的字段都改成 `{ref,abstract}`，也不新建摘要数据库。显示 owner 从当前已安装事实构造说明；底层原始关系仍可使用精确字符串。

## 5. 实施范围与顺序

建议先完成本计划的契约冻结，再实施叙事主线，最后完成其余引用迁移。问答可见性和 provider 结果完整性不依赖全库字段重命名；它们不应等待一次大迁移才能得到修正。

### R0：冻结词汇与契约

- [ ] 确认采用 ref/refs 为内容身份字段，保留关系语义和临时 handle 的区别。
- [ ] 确认 ResourceLocator 的唯一 ref 槽、Session occurrence 与 target_ref 的分工。
- [ ] 确认保留各 owner 读取入口；跨日模型读取或统一只读入口另行决策。
- [ ] 补齐机器字段 → producer → consumer → 持久化/Endpoint 影响表，核实所有 Link/ref 类型与 fragment 消费者，不猜字段语义。

### R1：模型输入输出与固定说明

- [ ] 配合叙事计划统一 Context、TaskPrompt、ActionResult、ToolSpec、Search/Inspect 的可见措辞。
- [ ] Catalog 的可配置工具语义仍在 Catalog；Home/Skill 指导仍在 Home；代码固定包装在所属 prompts；不建立副本。
- [ ] 同一 Action 的 schema、参数归一化、executor、Skill 示例与测试一起修改。
- [ ] 无效引用仍是所属 Action 的可修正结果，保留精确目标、范围约束和下一步可用入口，不转为 Runtime 转移。

### R2：owner 和公共机器协议

- [ ] Home/Memory/Workspace 的身份字段、Background 选择、局部任务引用按 owner 完整迁移。
- [ ] Session occurrence/target/binding、Trace origin_refs、Disclosure/Search 和真实 backlinks 同步核对。
- [ ] 执行/子代理 cwd、产物 locator、Web/Resource 保存结果、MCP/Trash 入口等真实消费者纳入同一字段清单。
- [ ] ResourceLocator、Agent SDK、Endpoint query/response、Observation 相关字段、契约样例一起更新。
- [ ] Search result_ref 的目标命名和生命周期说明一致；不改变 refs 精确读取、result 完整集合与 continuation 单页的语义。
- [ ] 核对已存在实例中的用户可编辑 Catalog/Skill、历史记录和归档。若需要迁移，采用明确可审阅的数据/配置迁移；不静默覆盖用户内容，不保留永久双名 alias。具体实例目录修改需要在该迁移方案确认后执行。

### R3：当前文档和收尾

- [ ] AGENTS 的资源/Context/渐进披露定义与新实现一致。
- [ ] 同步上述 docs/design、相关能力设计、docs/endpoint 和 contracts 样例；必要时在 docs/design/context.md 建立公共引用说明，各 owner 文档只解释自己的差异。
- [ ] 默认 Home 的 Context/Skill 指导与实际 Action schema 一致；更名 reference 文档时同步所有真实引用。
- [ ] 历史 docs/analysis/done 保留历史事实，不全局重写旧协议说明。
- [ ] 查找遗留字段和无消费者 alias，按语义逐项判断；不以全文不存在英文 link 作为验收标准。

## 6. 验证要求

测试覆盖契约和真实风险，不固定可编辑文案快照：

1. 各 owner 的规范身份、相对解析、fragment、存在性/能力限制与局部失败保持正确；同一资源通过 Search → Inspect/read → Action 不需人工换字段。
2. 当日 Workspace、历史 occurrence 原日定位、动态 memory:latest 绑定保持不同；缺少历史绑定不能悄悄读取今天内容。
3. ResourceLocator 单身份不变量与 Session occurrence/target 两种身份均保留，Endpoint 导航不丢失日期/Turn/view。
4. backlinks 仍来自真实 Markdown/Session 来源关系；改名不产生虚假引用边或读取未授权 owner。
5. Search result handle 指向完整集合，continuation 只续读页面，lease 到期后的局部失败明确；模型局部 ID 不能被当持久引用使用。
6. 实际模型 payload 中保留引用旁的解释；折叠后沿父入口能发现子入口；需要精确参数的 ref 可直接复制。
7. 默认生成配置、用户配置迁移、SDK/Endpoint 契约与类型检查通过；后端不修改 visualization，通过 Endpoint 文档交接必要字段变更。
8. 完成聚焦、Fast、Full 和 typecheck，逐项核对代码、文档、计划后才标记 done 并归档。

## 7. 本轮建议与待确认点

推荐接受：统一“引用”总称；真正内容身份逐步统一为 ref；保留 owner 与生命周期；locator 只表示带绑定的定位对象；导航引用与可证实说明共同折叠；以独立计划控制协议迁移范围。

仍需确认的是机器接口改名的范围（是否包括公共 SDK/Endpoint、内建 Catalog 与已有实例迁移），以及是否另增统一只读入口/跨日模型读取能力。推荐包括前者的完整设计与迁移，后者本次先不增加；当前真实读取能力在说明中讲清楚。
