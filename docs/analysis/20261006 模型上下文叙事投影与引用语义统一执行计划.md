# 模型上下文叙事投影与引用语义统一执行计划

日期：2026-10-06

状态：`pending`（2026-10-06 讨论修订；计划及引用目标设计已更新，代码和验证尚未实施）

已确认实施方向：ask 采用路线 A；引用采用 U0，统一 ref 与 inspect 抽象原语，保留各插件和域的读取入口。机器字段统一覆盖前后端真实消费者与持久格式，不提供向后兼容，不迁移 my-agent-dev 测试目录。Trace 共用根与 Home 显式类别格式已确认；Workspace Inspect 的正文保留、分页与较短身份方案继续讨论。

引用身份、机器字段与绑定协议的迁移单独由[引用体系梳理与统一执行计划](<20261006 引用体系梳理与统一执行计划.md>)承接。本计划负责模型叙事、交互可见性和分层回忆，复用引用计划确定的公共契约。

实施必须参考[引用格式与渐进读取](../design/references.md)中的目标格式。该设计文档经维护者授权先写预期格式并明确未实施；本计划的“当前事实”保留现有代码形态，不能用旧示例覆盖已确认的目标规范。

## 1. 目标和范围

本计划承接 `core.ask` 问答往返、TurnTrace 可见性和 Session 历史语境的复核。目标是保留现有 typed facts、Action、Context 段和 owner 持久化边界，同时改进模型实际看到的叙事内容，使当前 Turn、历史 Session 和按需资源具备同一套容易理解的表达。

本轮重点不是再建一套交互日志，也不是把所有结构化数据展开为正文，而是明确三层内容：

1. **Canonical fact**：由现有 owner 保存的 `ContextTurnInput`、`QuestionAnswer`、`TraceAction`、`ActionResult`、Session record 和资源记录。它们是唯一事实来源，继续使用稳定类型和机器协议。
2. **Model narrative**：根据 canonical fact 为模型构造的可读消息。它应直接说明发生了什么、用户回答了哪个问题、Action 得到了什么结果，并保留模型下一步需要的有限语义。
3. **Navigation reference**：用于 `core.context.inspect`、owner Action 和历史 map 的稳定定位。它只提供回忆入口，不代替正文，不要求模型推断内部存储结构。

涉及的代码范围包括：

- `kernel/context/builtin/trace.py`、`kernel/context/builtin/core.py`、`kernel/context/engine.py` 及 Context composer；
- `kernel/action` 的 ActionResult 可见/折叠投影，尤其是 `core.ask` 和 foldable resource Action；
- `plugins/session` 的 completion、linear interaction projection、SessionSegment render 和背景预算；
- Home、Memory、Workspace 的 Background 投影和 Action trace projection；
- 相关 `docs/design/`、`AGENTS.md`、prompts/tool description 和测试。

本计划不改变 Action Catalog 的可配置语义、Home/Memory/Workspace 的资源所有权、Session map 的解释职责、Action 的执行超时体系，也不把动态资源正文或配置副本移动到 `tinysoul/prompts`。

维护者进一步确认：Session 按 Turn 包装可读叙事，reply 补全选择含义与 comment；引用设计服务当前 Turn 和当日 Session/Workspace，不新增跨日回读 Session/Workspace 的能力。跨日记忆沿既有 Session → Memory → recall 语义发展；Reflection 避免把 Workspace 引用写入长期记忆属于另一项设计，本轮不实施。

## 2. 按 AGENTS.md 重新核对后的当前事实

### 2.1 Context 和 TurnTrace

AGENTS.md 规定 Context 只属于活动 Turn，Inputs 保存当前 Turn 的初始输入、已接受 append 和 reply；TurnTrace 按 owner 观察顺序保存当前 Turn 的输入可见位置、决策、执行事实和必要反馈。MessageStack 每次 LLM Task 前重新构造，Inputs、Session、Trace 由各自 owner 提供投影。

当前实现与该规定的大部分关系正确，但模型投影存在不对称：

- `InputsSegment` 将全部 `PendingInput.text` 渲染为普通 `user_input` 消息。它保存了 input、append、reply 的正文，但没有把 `reply_to`、选项 label/id 和 comment 的关系直接写进消息；`ContextTurnInput.answer` 仍只在 typed fact 中保留。
- 输入 signal 安装时只记录 `INPUT_INSTALLED`，下一次 cycle 边界 merge 后只记录 `INPUT_VISIBLE`。`TraceKind` 当前只有 `DECISION`、`ACTION_RESULT` 和 `PHASE_NOTE`，没有 input/reply interaction Entry。
- `core.ask` 的 ActionResult 已经作为 `ACTION_RESULT` ToolResultEntry 进入 Trace，payload 包含问题文本、选项、`allow_other`、timeout 和可选 explanation。因此问题内容没有丢失，但它以通用 JSON ToolResult 呈现，缺少直接的“agent 向用户提问”的叙事包装。
- reply 只作为 Inputs fact 和 `_current_search_facts()` 中的 input fact 出现，没有直接的 TraceEntry。`reply_to` 可以由内部 search/UI 使用，却没有在下一次模型消息中形成清楚的“回答上一问题”语义。
- `core.context.inspect` 的活动 Trace 只列出 TraceEntry、heap node 和 Action 线索；input ref 是可搜索/可 inspect 的事实入口，却不是 Trace child entry。因此前端通过 interaction projection 看到的完整往返与活动 Trace 页面并不一致。

这些代码事实支持“投影不利于理解和关联”的判断，但不能仅凭静态检查认定某一次模型遗漏完全由注意力导致。前端的 `project_current_interactions()` 会从 `ContextTurnFacts` 重新组合 input、question、reply；实际 MessageStack 仍按 Session、Inputs、Background、Trace 的段顺序收到分散的消息。验收必须覆盖真实 provider 请求映射。

进一步核对发现：

- 当前 Trace 已支持非 Action 内容：`PHASE_NOTE` 可以容纳纯文本或 JSON，TurnInbox 把环境事件、Job 通知等通过既有 Signal 管线写入此类 Entry。无需为外部事件再建另一套记录系统。
- `TraceEntry.origin_refs` 已存在，是 foldable Action 的来源引用元组；没有通用 `related_refs` 或带关系类型的图边。reply 的确定关系已在输入事实的 `reply_to` 中存在。
- `ToolResultMessage.from_parts()` 已支持 text + JSON；`MessageContentRenderer` 会将 JsonPart 转为 fenced JSON 文本，与 TextPart 拼接。上一版把该能力描述为尚待验证是否支持，不够准确；需要验证的是业务消息顺序及信息保持。
- 当前 adapter 的 `_tool_replay_plan()` 只认可 assistant tool calls 后连续、完整、身份匹配的一组 ToolResult。原生 tools 开启时，不被认可的 ToolResult 会被跳过。因此在调用和结果之间增加 UserMessage，可能导致结果未进入最终请求。当前 `mark_model_consumed()` 根据 MessageStack 判断 overlay 已消费，无法单凭它证明 adapter 实际发送了该内容。
- `label`、`MessageOrigin` 和 resolved binding 是框架 metadata，不是模型正文。重要的角色说明、资源身份和回忆入口不能只写入这些字段。

### 2.2 Session

Session 的事实拆分和 map 边界是正确的：输入和 Action 正文各保存一处，timeline 只引用事实；`project_interactions()` 能按顺序给出 input、append、question、reply、output，map 只存解释节点、关系和 source refs。

需要改进的是模型侧渲染，而非存储模型：

- `SessionSegment.render()` 当前为每个 turn 生成一个 `UserMessage.from_json(item.content)`，其中 `interactions` 仍是一个 JSON 数组。数组中的 `text` 是直接正文，但模型还必须理解 role、delivery、question_id、answer 等字段，才能重建人类能直接读懂的对话顺序。
- completed Session 的 question projection 从 `QuestionContent` 重建正文，当前没有转交 ActionResult 中的 `explanation`；`timeout_seconds` 是运行策略，除非存在实际决策消费者，否则不应进入历史叙事。
- interaction 中的 `delivery: visible/installed` 属于 Context 装配状态。它对前端诊断有用，但不是普通历史对话的语义，原则上不应成为模型必须理解的字段。
- 普通 Action（包括 reason）在当前历史投影中优先锚定 `ACTION_STARTED/ACTION_REQUESTED`，只有成功 ask 优先使用 `ACTION_SETTLED`。原先只是状态标记时不明显；改为直接展示实际结果后，必须区分开始行动与得知结果的时刻，不能把后来才收到的结果提前放到中途追加输入之前。
- map 使用 `session:map` 和 semantic refs 是合理的；不应为了改善线性叙事把 map 节点内容复制成第二份历史正文。

### 2.3 Home、Memory、Workspace 和折叠 Action

- Home catalog 只列出有界 link、title、description，加载后的 top 内容直接进入 Background。这符合 Home link 的 owner 和渐进加载边界。问题在于 catalog 和 resource 正文都以不同结构进入模型，缺少统一的“这里是可用资源，按 link 加载”的人类式叙事。
- Memory 的 loaded projection 在正文前放置 `{"ref": ..., "day": ...}` JSON header；ref/day 是定位信息，但目前没有简短的语义说明。Memory 正文本身仍应直接呈现。
- Workspace Working 段只提供 resource link/summary，不常驻文件正文，这与设计一致；当前整个资源列表作为一个 JSON 对象进入模型，资源很多或 summary 较弱时不易扫读。活动资源正文通过 `workspace.read`，候选通过 `workspace.search`；当前没有 `workspace.inspect` Action。绑定的归档 Workspace 段可通过 `core.context.inspect` 读取。
- Home/Memory/Workspace 的 Search/Inspect/Read Action 首次可见结果仍应保留完整、真实的 owner payload，并在真实决策模型请求消费后允许折叠。当前 foldable canonical payload 对 search 主要保留 source/selected refs，对 inspect/read 主要保留 ref/view，有些结果折叠后语义过薄，模型只能重新 inspect 才知道先前读到了什么。

每种 foldable Action 需要提供基于真实结果的有界语义线索，保证折叠后的 Trace 仍能说明“对哪个引用做了什么、实际返回了什么、可以从哪里继续读取”。但是否保留正文与如何压缩显示是两个决策，不能将 foldable 删除正文作为所有资源读取的强制规则。

另一个边界必须明确：活动 Trace 的 Action fact 仍持有完整 ActionResult，entry inspect 通常读 canonical message；Session completion 则只保存 foldable canonical payload。历史 Action ref 不承诺恢复未保存的完整读取正文。重新读取可变资源可能得到后来内容，不能称为“恢复当时原文”；已有 Session Heap snapshot 等真实快照仍可按原 owner 读取。不为本计划新增永久搜索快照库或文件版本库。

上述为当前实现。本轮按维护者方向进一步设计 workspace.inspect：无内部 LLM，返回的有界正文页可以成为 canonical ActionResult，沿既有 standard 路径进入 Trace 和 Session。具体保存与展示策略见第 4.7 节及引用计划，不能继续用旧 read 的“删除 text”假设约束它。

## 3. 统一的语义原则

### 3.1 事实、叙事、导航三层不得互相替代

- `ContextTurnInput`、`QuestionAnswer`、ActionResult 和 Session records 继续是事实唯一来源。
- Trace interaction 是从已接受、已达到可见边界的 fact 派生的模型叙事，不成为第二份持久交互事实。
- Session linear history 是从 Session records 派生的历史叙事；map 只负责解释和关系导航。
- Inspect/search 结果是按 ref 读取事实或正文的入口，不以引用字符串替代需要保留的短语义。

允许在 Inputs 和 Trace 中重复当前输入。该重复不是持久事实复制，而是为了让最近一次用户行为在按时间顺序的 Trace 中可直接注意到。Session 仍只保存一次正文。

### 3.2 模型看到的是叙事，机器边界保留结构

模型上下文中的自然语言应优先使用短句、明确角色和因果关系；只有需要 Action 参数或 Inspect 定位时才显示精确字段。建议的叙事形状如下：

```text
用户补充：<append 原文>

用户回答上一问题：<问题的简短定位或问题 ref>
选择：<option label>（<option id>）
补充说明：<comment>

Agent 提问：<question text>
选项：
- <label>（<id>）：<description>
说明：<explanation>
```

这里的文字由 Context/Session owner 根据已校验值构造；选项、answer、reply_to 等 typed fields 仍保留在 canonical fact 和必要的 machine payload 中。固定的短标签和包装文字属于相应 owner 的 `tinysoul/prompts`，动态问题、选项、comment、ref 和结果摘要由调用方提供。

### 3.3 Link 和 ref 的统一说明

上一版把 Link 和 ref 简单划为资源身份与 Context 位置，不能完整解释现状：`home.inspect`、`memory.inspect` 和 Search 已使用 `ref` 传递资源 Link；Workspace 的同一身份又由 `link`、`locator` 等字段传递。术语和机器编码一起纳入独立引用计划。

模型总称统一为“引用”；推荐内容身份统一使用 `ref`，差异由 owner、目标类别和有效作用域表达，不能把“字段叫 ref”解释成一定属于 Context。Home top 的可加载性、Memory 动态绑定、Workspace 原日身份、Trace 当前 Turn 和 Session 历史仍保留真实语义。

更正：当前 `ResourceLocator` 要求 `link` 与 `ref` **恰有一个**非空，再附加有意义的 day/turn_id/view；并不允许同时携带两个身份。它和 `ResourceScope.locator` 的裸字符串也不是同一种东西。机器字段统一见独立计划；读取采用已确认 U0，不增加统一工具门面，不设计新的跨日绑定编码或模型读取能力。

## 4. 目标改进设计

### 4.1 为当前输入建立可读的 Trace interaction

为 input/append/reply 增加明确的输入类 Entry，优先采用 `TraceKind.INPUT` 等窄分类，复用当前 `TraceEntry` 和消息协议。环境事件继续复用 `PHASE_NOTE`，由事件 owner 提供可读的事实内容；不新增万能 interaction 对象或另一套事件系统。枚举名称是实现细节，不单独作为维护者决策点。

Entry 的来源和可见时机：

1. 初始 input 在 `begin_turn()` 安装并立即可见时生成 interaction Entry。
2. append/reply signal 完成 prepare/install 后只先记录 `INPUT_INSTALLED`；在 cycle boundary 执行 `merge_pending_inputs()`、即下一次模型请求将看见它们时，再生成对应的 interaction Entry，并记录 `INPUT_VISIBLE`。
3. 未接受或未 merge 的输入不能通过 Trace hot message 提前进入模型。
4. Entry 的叙事消息使用当前 Context 的既有 user-role 约定，在正文中明确“用户输入/用户补充/用户回答”或事件来源。Trace render 按顺序返回这些 UserMessage，Composer 合入 Trace 段，adapter 映射为实际 user 消息；无需前置 tool call。
5. `INPUT_VISIBLE` 表达已安装到可构造上下文的位置，不等同于模型已经消费。输入可能在两个 Phase 之间进入可见状态；实现不能假设该位置永远在完整 tool block 之外，也不能用延后事实记录来掩盖协议问题。

对于 reply，Entry 必须同时表达：

- 用户选择的 option label/id；
- 选项描述若对理解答案必要；
- 用户 comment，并明确标注为“补充说明”；
- 与对应 `core.ask` 的关系。可显示简短问题文本，必要时附 `ref:`，不要求模型根据一个 opaque question id 自己猜关系。

Inputs 段仍保留原始 input 文本和接受顺序。输入 Entry 由同一输入事实派生，不能重新从渲染后的字符串反解析 typed answer。复用原有 `reply_to` 和 `QuestionAnswer`，不新增通用 typed related/source ref 图。Entry 如需关联 canonical input，仅保留完成映射和去重所需的输入身份，不能把所有 Entry 扩成关系对象。

邻近顺序可以解释正常问答；压缩、inspect 单独读取或中间插入事件时，回复正文还应带问题短提示与选择文字，避免出现孤立的“选 B”。这些文字从既有事实取得，不新增关系事实。

### 4.2 ask 同时保留 ActionResult 和可读 Trace 投影

#### 当前对象及时间语义

“ActionResult Entry”不是另一个 Entry 类，指 `TraceEntry(kind=ACTION_RESULT, message=ToolResultMessage)`。ActionResult 是执行层的 typed 结果；renderer 将它投影为 ToolResultMessage，再进入现有 TraceEntry。增强的是该投影的内容，不是将用户回复塞回 ActionResult。

另需区分两个时刻：`CoreAskActionExecutor` 生成合法问题意图，Phase3 收集结果后由 Turn `open_question`、发布 question Observation 并等待。Action 成功不等于前端已经显示或用户已经读到。当前 QuestionRequest 只转交 QuestionContent 和 timeout，未携带 Action payload 中的 explanation；若选择在 Turn 打开问题时生成独立叙事，要补全该数据流。

#### 路线 A：原 ActionResult Entry 内呈现问题（已确认）

```text
DECISION：请求 core.ask
ACTION_RESULT / ToolResult：core.ask 生成的问题 + 完整选项 + 说明
INPUT / UserMessage：用户回答的问题提示 + 选择含义 + comment
```

- ActionResult 的结构化 payload 保留问题、完整有序选项、allow_other、explanation 和运行参数，供执行、持久化与 Inspect 使用。
- 扩展 Action-owned 可见投影，令同一个 ToolResult 直接可读；不需要再保存一条完整的问题 Entry。结果语义是已生成提问，不能声称已完成前端交付。
- `TextPart + JsonPart` 已可承载；JsonPart 也会进入模型，不能把它当隐藏附件。按内容必要性决定文本与 JSON 的分工，不能无意复制两份完整问题。
- 优点是保留一个问题条目和现有 call/result 对应关系，Inspect、压缩和 completion 的身份映射较简单。代价是需要让 Action 可见投影支持自然语言，输入与问题仍使用不同底层消息类型。
- 问题被打开、超时、取消等生命周期事实如需显示，由 Turn 独立提供必要 note，不能修改已结算 ActionResult 的意义。

#### 路线 B：工具回执与问答叙事分离（讨论记录，本次不采用）

```text
DECISION：请求 core.ask
ACTION_RESULT / ToolResult：生成成功及必要结果信息
QUESTION / UserMessage：Turn 已打开问题 + 完整选项 + 说明
INPUT / UserMessage：用户回答的问题提示 + 选择含义 + comment
```

- 独立问题 Entry 可在 Turn 接受问题、进入待答时产生；从原问题事实派生，使用已有 question/result 身份映射。它表达一次新的交互阶段，而不只是 JSON 的重复排版。
- B1：工具结果保留完整 payload，问题 Entry 再呈现完整叙事。允许这种可见重复，但增加预算并使同一内容有两个导航/压缩位置。
- B2：完整 canonical ActionResult 保留，工具消息只呈现简短准确回执，问题 Entry 承载详细内容。此方案避免大段重复，但需要可见投影、两个 Entry 的语义关联、压缩完整性和 Session 去重，不能称为完全不动 Action 层的方案。
- B 的收益是把问答统一组织为独立交互消息，清楚区分生成问题与打开问题，后续若有问题撤回、替换等真实需求也有明确位置。代价是多一个条目及相应映射和分组规则；本轮不因假想的未来状态扩建状态机。
- QUESTION 放在已收敛的工具结果组之后，不插入 call/result 之间。此前 adapter 的连续组限制不能作为否定 B 的理由；位置正确的 B 同样能正常原生回放。
- Session completion 由同一 Action/Input canonical facts 生成一次问答，派生问题 Entry 不再另存重复 note；Inspect 能解释工具结果与问题内容的关系，去重不能依靠对自然语言字符串做匹配。

#### 路线比较与共同约束

| 判断项 | A：结果条目可读化 | B：独立问题条目 |
| --- | --- | --- |
| 模型直接读问题、选项和说明 | 可以 | 可以；不能仅凭 user/tool role 推断注意力一定更好 |
| 精确区分问题生成与 Turn 打开 | 由 Action 结果及必要 Turn note 分工 | 可分别记录，语义更显式 |
| 额外记录及压缩单元 | 无第二份问题 Entry | 增加派生问题 Entry；B1 重复正文，B2 需协调展示 |
| 所需展示设施 | Action 结果的可读投影 | B1 交互投影；B2 同时需要 Action 回执投影 |
| 输入、事件接入 | 独立 Entry | 独立 Entry；二者相同 |
| Session 按 Turn 叙事 | 都能从同一事实产生 | 不构成选择 B 的前提 |

维护者已确认 A：结果准确表达“生成了这个问题”，事实与展示关系更直接。上面的 B 比较保留为设计取舍记录，本次不增加独立 question Entry；输入与 reply 仍独立成条目，必要 Turn 生命周期反馈仍由原 owner 表达。

ask 和 reply 应是按实际发生顺序追加的两条内容，即使采用 B，也不在 reply 到来后反向改写过去的 ask 条目，把中间事件挤出时序。成组显示和压缩可以由投影根据既有 reply_to 完成，不新增通用 typed relation graph。

可读呈现与 foldable overlay 是两个维度：standard ask 不能为了文本展示冒充 foldable，不能滥用 trace_projection 绕过 Catalog 的 trace_mode 约束。canonical serialization、completion 和 Inspect 从 typed fact/既有 canonical payload 读取，不依赖“ToolResult 只有一个 JsonPart”的隐式假设。

两条路线都须核对 provider 结果完整性：完整 tool block 正常回放；夹入输入、事件、局部失败或取消导致无法原生回放时，按原观察顺序表达真实调用/结果，不静默丢弃、不伪造未执行结果。adapter 只理解 LLM 消息协议，不导入业务 owner。Inspect 展示保护以实际发送内容为准，优先验证忠实映射，不另建持久消费回执系统。

### 4.3 Trace inspect/search 和 completion 的一致性

新增 interaction Entry 后：

- 活动 `core.context.inspect` 的 Trace root/leaf/entry 页面提供 input、append、ask、reply 的带语义线索入口，并在选定条目中读取正文；input/reply 还可以通过原有 `#input/...` 事实 ref 精确读取。目录页保持有界，不为“直接可见”强制内联全部历史。
- Trace query 搜索 interaction 的正文和关联 ref，不要求模型先理解内部 `TraceFactKind`。
- `project_turn_record()` 不把新增输入 Entry 再保存为独立 Session note。通过原输入身份映射到已有 input canonical ref，避免两份正文或重复可见里程碑；ask 继续从 Action record 投影。事件 note 仍按原 completion 流程保存。
- Action result 的 `TraceEntry` 与 `TraceAction` 继续由 Action owner 的 canonical projection 分工；Trace interaction 只提供叙事，不改变 ActionResult 的 success/failed/timeout/cancelled 事实。

### 4.4 Session 线性历史

采纳维护者偏好：Session record 和 map 保持当前所有权，以 Turn 为清楚分隔；默认每个 Turn 一个可读 UserMessage，内部按同一 interaction sequence 排列段落。没有证据表明“消息越碎注意力越好”，不把每个 interaction 拆成底层消息当成目标：

- 直接显示 input、append、ask、完整有序选项、reply、comment、正式 output；
- Turn 标题展示日期/状态和带解释的回忆入口，内部显示用户输入、补充、Agent 提问、用户回答、内部行动和正式回答。需要进一步读取的交互单元附带 ref 与解释；无需每一行都重复 opaque id；
- map 作为独立导航入口显示，节点、关系和 refs 不复制交互正文；
- 不把 `delivery`、revision、digest、locator 绑定等内部字段放进普通历史叙事；
- question explanation 若是 ActionResult 的模型可见语义，必须保留；timeout 只有在模型决策需要时才显示；
- 叙事区分请求/开始与实际结果：展示已完成 Action 的产物时按既有 settlement 时间线定位，必要的开始线索仍来自原 requested/started 事实；不改变 owner 观察顺序，不从外部时间戳臆测因果，也不复制完整执行日志。代表性用例包含 Action 运行中插入 append，确保结果不会被误呈现为追加之前已知；
- 背景预算继续按 Session 自身高水位回收，并按实际叙事渲染字符计量，不能继续拿旧 JSON 长度冒充新消息长度。正常容量先保留直接内容；超限时缩为带 ref 的交互组，再缩为带摘要的 Turn，最后由有解释的目录入口覆盖。问题、完整选项和关联 reply/comment 共同保留或折叠，不留下孤立选择；
- `core.reason` 是显式执行的内部 Action，其实际产物与 provider 隐藏 reasoning 不同。当前历史只有 action 标记/状态/ref，缺乏可复用内容。正常预算内应保留有价值的直接结果；结果较大时提供真实摘录和 Action ref。它允许任意 JSON 输出，不能猜某个字段必然是“结论”，必要的表格/数字/结构化产物保留原语义，不把“叙事”理解为禁止 JSON。其它 Action 同样保留影响后续决策的结果、失败和产物线索；
- 不把预算结束前尚未被模型消费的输入说成 Agent 已处理。后台装配标识不直接暴露；如这一事实影响历史理解，使用简短的“收尾时收到，未继续处理”等可证实说明。

JSON interaction projection 是从持久 records 派生的读取视图，不是另存的交互日志。它继续供 Endpoint/前端消费；模型和 Inspect 的叙事从同一 facts/projection 产生。具体变更若影响公开字段，应同步 Endpoint 文档，并按维护者本轮明确授权对齐 visualization 的真实接口使用，不扩展为无关前端设计重做。

### 4.5 Home、Memory、Workspace 的叙事和折叠语义

保持三个 owner 的事实和 Action 边界，只调整模型投影：

- **Home**：catalog 用短标题、用途说明和引用呈现可加载入口；已加载 top 内容直接显示正文和身份。不要把 Home nested resource 的所有文件正文自动放入 Background。`home.search/inspect` 的折叠结果保留目标、视图、真实标题/摘录和覆盖说明。
- **Memory**：current/latest/target catalog 说明其用途和实际日期；正文前使用可读标题与实际引用，不把动态绑定藏在 label。`memory.search/inspect` 的 canonical projection 保留来源、目标、视图、真实标题/摘录和覆盖说明。
- **Workspace**：Working 段显示资源 summary 与引用，不常驻文件正文。现有 `workspace.read/search` 折叠后补足目标、范围/覆盖和真实摘录。新的 `workspace.inspect` 按第 4.7 节讨论保留实际返回页，不能套用旧 read 的删正文规则；再次读取资源返回现态，读取历史 Action 则只恢复实际保存的结果。
- **Search**：`selected` ref 列表不能成为唯一的折叠语义。owner 应从真实结果中提供有界标题、命中依据或结果摘要；不能由 Context 伪造通用理由，也不能把内部 provider、revision、digest 暴露给模型。
- **Inspect**：完整页面仍必须先进入一次实际返回的决策模型请求才允许折叠；折叠后的摘要只做回忆线索，正文继续通过统一 ref 读取。

所有动态摘要由 owner 根据真实结果构造，不进入 `tinysoul/prompts`，也不新增全局摘要器。优先复用已有标题、资源说明、Markdown link label、问答内容和真实命中片段；无证据的相关性解释不得编造。

### 4.6 引用与解释共同折叠

可导航单元是“引用 + 有意义的标题/线索”，复用 `DisclosureHint(ref, title, clue)` 等既有构件。层级示意：

```text
父入口：讨论了问答卡片的 Trace 可见性（ref1）
  inspect(ref1) → 当时的正文；问题“是否保留问答正文”（ref2）
  inspect(ref2) → 完整问题、选项与回答
```

工具接收精确 ref，标题/线索是帮助决定是否读取的上下文，不并入 ref 字符串。压缩时整项移入父层，父层保留自己的解释和入口；不能删掉解释却留下大量裸 ref，也不能只留下摘要而失去可定位的原事实。

Trace 现有压缩节点主要保存种类、Action 名称和计数，child clue 还在截取序列化 JSON；需改成来自实际交互的可读线索。摘要构造有界、确定性、无额外模型调用。Inspect 每次只展开选定层和页，保留直接子入口，不自动递归扩展，不要求遍历整棵树。临时 result handle 和 continuation 不伪装成永久回忆入口，其生命周期由引用计划明确。

### 4.7 Workspace Inspect 的正文与回忆（待讨论的具体方案）

维护者提出新的 workspace.inspect：按 ref 直接、只读地加载文档内容作为 ActionResult，不嵌入内部 LLM，顶层指导统一只称 Inspect。资源范围、片段、分页、失败、既有 metadata inspect 服务命名及旧 read 的边界由引用计划第 4.9 节维护，本节只定义与上下文叙事的协作。

建议本次实际返回的有界正文页作为 standard canonical result，不因来自 Workspace 就移除 text。Trace 正常容量直接展示；压缩后以标题/摘录、实际读取范围及 Action/Entry ref 导航，原结果保留在既有 Trace 事实与节点体系中。引用 Workspace 文件表示读取现态，引用 Action 记录表示回忆当时保存的页，二者清楚区分。

新一轮不携带旧 Trace，但会携带 Session 投影。建议 Session completion 沿既有 standard 结果路径保存该页，线性历史依据预算保留正文、摘录或整个交互的解释与引用；Session Inspect 可以读取保存的页。不自动保存未返回页、不复制整文件、不建设版本库；Working 仍只显示资源状态。

当前展示保护只追踪 visible_overlay。改用 standard 结果后须在现有 Trace append → 实际决策请求消费 → 压缩的路径补齐保护，保证正文未真正可见前不会被折叠；不能通过制造两份相同 payload 或冒充 foldable 来绕过契约。这与本计划已发现的 provider 丢弃不完整 tool block 问题共同验证。

正文叙事来自同一 typed result；避免自然语言和 JSON 重复完整页。覆盖元数据有界保留，source ref、历史 Action ref 和可续页令牌不混用。固定包装仍放在所属 prompts，真实正文、标题、范围和配置预算仍由 Workspace owner 提供。

## 5. 引用和模型可见内容的审核清单

每个新增或修改的模型上下文投影按下列顺序检查：

1. 该内容的 canonical owner 是谁，是否已经有 typed fact 或 ActionResult；
2. 模型是否需要正文、短摘要、link、ref 或仅需要一个状态；
3. 文本能否在不阅读内部 JSON schema 的情况下说明发生了什么；
4. 精确 link/ref 是否在需要调用 Action 时可直接复制使用；
5. 是否把 revision、digest、delivery、batch、invoke、provider 或存储 locator 等实现信息误放进模型叙事；
6. 折叠后是否仍有足够语义和唯一回忆入口；
7. 是否会因为同一事实在 Inputs、Trace、Session、ActionResult 之间重复而产生互相矛盾的正文；
8. 当前可见边界是否遵守 prepare/install/visible 和 Inspect overlay 保护；
9. 失败、取消、超时和未执行是否继续由原有 Action/LLM/Runtime 分层表达；
10. 固定包装文字是否放入所属 owner 的 `prompts`，动态内容是否仍由 owner 提供。

## 6. 实施阶段

### 阶段 0：先冻结引用公共契约与叙事边界

- 与独立引用计划确定当日内容身份、现有绑定、读取能力和临时句柄的契约，不增加跨日模型读取，不必等待全部字段迁移才能修复问答可见性；
- 按已确认路线 A，让 ask 复用自己的 ActionResult Entry；输入/事件独立记录，不新增通用 related/source 字段；
- 参考 `docs/design/references.md` 的已确认格式；与引用计划收敛短身份策略和 Workspace Inspect 保存实际页的契约；
- Session 采用 Turn 包装的叙事，范围包含显式 `core.reason` 产物；
- 检查最终 provider payload 和 overlay 消费保护，确定不会因为新增叙事静默丢失 Action 结果的方案。

### 阶段 1：Context/Trace interaction

- 从既有 input/answer 事实构造输入叙事，复用已有类，只有职责确实需要时增加最小类型；
- 在 visible boundary 安装 input/append/reply interaction Entry；
- 为 Trace inspect、query、semantic serialization、heap fold 和 completion 映射补齐 interaction 支持；
- 保持 Inputs 原始正文、typed answer 和现有 timeline 不变。

### 阶段 2：ask 和 Action 可读结果

### 阶段 3：Session 线性历史与 map

- 让 SessionSegment 从 interaction sequence 构造按 Turn 包装的可读历史与显式内部 Action 产物；

- 去除模型叙事中的内部 delivery/locator 字段，补齐 question explanation 和 reply/comment 语义；
- 重新核对 Session completion 不重复保存输入 Entry，确保 timeline/ref 可回溯，并按叙事的实际长度执行预算。

### 阶段 4：Home/Memory/Workspace 和引用表述

- 统一 catalog、loaded content、Action result 和 Inspect 工具说明中的 link/ref 叙事；

- 只在模型确有消费者时显示精确 machine ref，正文中不混用多个未解释的 locator 字段。
- Workspace Search → Inspect 原样传 ref，历史 Inspect Action 的回忆沿 Trace/Session 引用；默认背景指导统一只称 Inspect，具体域说明真实能力。

## 7. 测试和验收标准

测试保护真实可观察契约，不锁定可编辑文案的逐字快照：

- 初始 input、append、reply 在安装前/visible 后的可见边界正确；reply 进入下一次 LLM Task 的 MessageStack 和真实 adapter 请求，包含选择、comment 和对应问题语义；
- `core.context.inspect` 活动 Trace root/leaf/entry 能发现 input、append、ask、reply interaction，原有 `#input/...` 和 Action refs 仍能精确读取；
- ask 的 ActionResult payload、readable Trace projection 和 wait/resume 顺序一致，ToolResult 协议没有被重复结果或错误消息顺序破坏；
- Session linear history 按 input、append、ask、完整选项、reply/comment、output 顺序显示，map 只提供解释关系和 refs；
- Session completion 不把输入 Trace Entry 变成第二份 note；正常容量能看到 `core.reason` 的显式产物，压缩保留有解释的引用；读取历史时不承诺恢复从未保存的资源全文；
- 压缩后可沿有解释的父 ref 逐步找到子 ref 与原始记录；续页不能断开该链路，也不能把临时 token 当永久 ref；
- provider tools 开启/关闭、完整/中断的回放组都不静默丢失真实反馈；未实际进入返回请求的 Inspect 内容不解除保护；
- Action 开始和结果之间发生 append/环境事件时，消息和 Session 叙事保持可解释的观察顺序；input 可见里程碑不冒充模型已消费，结果不提前呈现为已知；
- Home/Memory/Workspace 的 loaded 内容仍由 owner 提供，folded result 保留目标引用和有界语义摘要，Inspect 完整结果的保护和分页契约不变；
- workspace.inspect 实际返回页进入模型请求及所选择的 canonical/Session 保留路径；压缩后仍可读取已保存页，Workspace 后续改写不改变该历史事实；未返回部分不得伪称已读或已保存；
- 模型自然语言投影中不会出现没有解释的 `resolved_locator`、revision、digest、batch、invoke 或 provider 字段；需要 Action 的 link/ref 仍是精确可复制值；
- 取消、超时、未执行、unknown、Action failure 和 Runtime bridge 语义沿既有体系，不用叙事格式替代失败分类；
- typecheck、`scripts/test.ps1 -Suite Full` 和必要的 endpoint/documentation review 全部通过后才可归档。
