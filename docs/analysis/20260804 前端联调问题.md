## Stage1 功能性优化

（1) llm action 提供的时长不足，建议后端增加各类 llm action 通用时长和专用时长

（2）重启后当天会话与 trace 不可恢复；事件缓冲在进程内（2000 条），重启即失；无 `/v1/session/*` 读取端点；前端事件在 2000 条上限处截断：超长会话最旧事件被丢弃，早期 turn 的 trace 会不完整；建议后端增加渐进式当日交互记录读取和局部trace的进一步读取；


## Stage2 问题与框架优化

（3）Endpoint 在特定工作负载下整体挂起 

- 现象：两次独立实例（pid 30888 / port 57000、pid 21376 / port 57702）在处理"帮我在工作区写一个很长的 markdown 文件"类输入后，进程存活、TCP 可连，但 `GET /v1/health` 5s 零字节、WS 8s 零帧，持续数分钟不恢复。
- 影响：主对话 cycle/stage 冻结、状态轮询失败、`stop_turn` 无法下达——用户此前报告的"stage 不即时更新、停止无效"大概率源于此。
- 需求文档：`visualization/docs/demand/20260804-endpoint-responsiveness.md`。
- 排查建议：workspace.write 的 LLM 组合（LLMActionTaskRunner）路径是否阻塞 ASGI 事件循环；Endpoint 服务与 Program 执行是否需要进一步解耦。

（4）Stage1 发生框架错误，但似乎没有作为局部错误反馈模型重试，而是 end turn

- 现象：[turn.failed] Phase1 did not produce a valid domain selection | {"kind":"loop.contract_violation","module":"loop","reason":"runtime.turn_end","status":"failed"}
- 运行轨迹：reference\running_trace\2026-08-04-1
- 排查建议：基于 AGENT.md 设计思路，检查异常处理和 stage1 的模型工具提供说明

（5）及时性反馈

- 前端对话和对话内部 Details 面板状态似乎因为后端推送阻塞不能即时更新；
- 检查后端提供用户主动中断当前turn端点的有效性；
- 检查后端发生end turn能够有效推送错误到前端；
- 检查后端 runtime 整体处理流程，哪些异常会触发 end turn，是否即时有效触发并推送到前端；
- 检查后端在 terminal 按下 ctrl c 能够即时退出 turn/再按一次即时有效退出 promgram；
- 检查后端整体 runtime 和错误与异常体系；
