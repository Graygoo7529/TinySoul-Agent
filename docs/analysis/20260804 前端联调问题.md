# 20260804 前端联调问题

状态总览：全部条目已完成根因排查、方案确认与实施；统一执行计划见 `docs/analysis/20260805-done-应用体验优化执行计划.md`。

## 已确认的根因(排查结论)

Endpoint 挂起(问题3/5):双重根因。(a) tinysoul/endpoint/server.py 所有 handler 是 async def 却直接同步调用阻塞的 engine 方法,任一请求阻塞即冻结整个事件循环(连无鉴权 /v1/health 与 WS 都无响应);(b) tinysoul/app/program.py 的 _run_user_request 在整个 User Turn 期间持有 active_day_lease()(排它 RLock),而 EndpointEngine.status()/workspace 读写都要抢同一把锁——Turn 有多长,前端就冻结多久。这也与 AGENT.md"UI mutation 可在活跃 Turn 内执行"的设计意图矛盾。

stop_turn 迟钝(问题5):控制信号只在 tinysoul/loop/cycle.py 的 _boundary()(Phase 边界)被消费;长 LLM 调用(最长 180s+)期间无法生效。Ctrl-C 在 tinysoul/app/cli.py 直接 KeyboardInterrupt 返回 130,无分级语义。

LLM action 超时不足(问题1):core.answer/core.reason 无专用超时,落 core domain 默认 60s;workspace.describe 落 workspace domain 默认 30s;思考型模型极易超时。

Phase1 失败即 end turn(问题4):tinysoul/loop/phases.py Phase1Unit.run 重试耗尽抛 LoopContractError;与 AGENT.md"phase 无法准备可用 action scope 应为局部结果"及 Phase2 的空 normalization 局部处理不一致。且失败尝试中模型给出的有效控制调用(load_background/todo)被整体丢弃。

会话不可恢复(问题2):事件仅存进程内 2000 条/32MB 缓冲(tinysoul/endpoint/events.py),前端 store 也 2000 条截断;重启即失、超长会话早期 trace 被丢。

已确认决策:采用 Endpoint 持久事件 Journal(不新增 Session REST);stop_turn 采用即时停止(放弃在途供应商调用等待、后台丢弃迟到结果)。

## 已确认决策

1. **会话恢复**：采用 Endpoint 持久事件 Journal，不新增 `/v1/session/*` REST。维持 AGENT.md「前端从真实 MessageStack 观察」边界；`/v1/events` 协议不变，支持 journal 深读与重启后续 sequence。
2. **停止语义**：`stop_turn` 采用即时停止。引入 Turn 级取消令牌，放弃在途供应商调用等待；孤儿请求后台完成后丢弃，不回写状态。SignalBus 在 Phase 边界的消费仍是权威控制流收敛。
