## 1. 结论

公共骨架已经建立，但不能认定 r4 已经干净、统一地完整落实。缺口主要出现在正常检索组合、内容证据传递、owner 来源适配和配置编辑，而不是极端故障恢复。

已经成立、应继续复用的部分：

- Action executor、统一执行期限及执行事实与模型用途分开；没有新增第二套 Action/Turn 调度器。
- LLM 复用 `LLMTaskRunner.invoke`，JEV/Embedding 保留专用 typed 服务；provider、model 和用途由配置决定，Search 请求不携带模型选择。
- `source + steps + page` 已成为生产协议；五个入口均已接入公共 SearchSession，filter/select/rerank 在同一管道内执行。
- 正常 Action 路径上的 select 保留输入相对顺序，rerank 校验全排列；显式模型步骤失败不会静默伪装为成功。
- SearchViews 保存完整最终成员，page.limit 不再删除尾部；翻页和 result 来源不重新读取文件，Turn 与 SDK 服务各自绑定生命周期。
- 向量缓存已按 provider/model/use/extraction 及实际文本摘要复用，局部 scope 不再覆盖其他 scope。完整测试包含不同 scope、内容身份与 extraction 的缓存验证。
- Memory 普通错误引用在 SearchSession 的来源边界转换成局部 INVALID_REQUEST；真实反链现在附带来源正文。旧 MEMORY_DAILY 枚举已移除，但配置和文档清理仍未完成。

主要问题共享三个原因：

1. 内容单元、命中证据、模型输入和页面仍在复用可裁剪的 SearchCandidate/evidence，未形成清楚独立的投影语义。
2. 公共协议虽然统一，owner 仍沿旧 corpus 遍历方式准备 refs、聚合属性和匹配内容，若干旧约束也被带进新管道。
3. 实施完成的核对偏重“入口存在、门禁通过”，没有逐项验证 r4 的组合行为及配置编辑契约。

## 2. 确认的问题

### R1：命中证据尚未贯穿操作结果和展示

状态：`pending`；优先级：高。对应 r4 F1、C2/C4、§7、验收 1/11/21/24。

位置：`kernel/retrieval/selection.py:83-103`、`:235-239`；`engine.py:120`、`:305`、`:319`；`contracts.py:203-277`。

实际情况：

- Embedding rerank 在 `embedding_rank()` 中按贡献单元生成正确 evidence；`CandidateSelector.apply_step()` 随后从 original 重建候选，只拷贝 score/score_kind，丢掉该次排序产生的证据顺序及依据。
- 混合召回把 lexical 的首条证据放在 Embedding 命中之前；页面固定最多取 2,000 字符。lexical 首单元占满预算时，同一候选的真实向量命中仍会在页面消失。
- LLM 当前只被要求返回 `{"ids": [...]}`，没有依据单元选择或校验。JEV 当前是 Score，也没有启用 basis Choice 的 descriptor。这一点需要结合第 4 节 D1 明确最终契约。
- 模型输入固定按每候选 4,000 字符摘录；Embedding 分支实际使用全部内容，却仍从这份 4,000 字符投影计算 `input_coverage`，会把实际完整评估标成 excerpt。
- 页面调用 `bound_evidence()` 修改 `evidence_complete`，`to_json()` 再把它写成 `content_coverage`。因此同一完整快照只因本页缩短，就被报成快照 excerpt；snapshot/model/page 三种覆盖没有分开。
- 非文本资源的 metadata 同样会进入默认 content unit，并可能标成 full；当前只输出 full/excerpt，无法表达计划要求的 metadata 覆盖。

隔离复现：一个候选同时具有 2,000 字符 lexical 片段和另一资源的 automobile 语义命中。混合 query 返回了候选，但页面只含 lexical 片段；快照完整为 true，页面 content_coverage 为 excerpt。另一调用的 Embedding rerank 得分 0.95，最终 evidence 仍从无关首段开始，逐单元 embedding basis 消失。

建议：保留同一份 owner 内容快照，让 Evidence 引用内容单元；操作结果明确保存依据/覆盖，模型输入与页面分别投影。不要通过统一增加截断长度来补偿证据流丢失。页面必须能呈现贡献命中或最后一次判断依据，同时保持快照覆盖不变。

### R2：Workspace 仍有两套对外搜索，匹配语义发生退化

状态：`pending`；优先级：高。对应 C5/C8、§11.1、验收 15/19。

位置：`plugins/workspace/services.py:99,115`；`engine.py:601,686`；`inspection/search.py:168`；`kernel/retrieval/operations.py:232,273`。

`WorkspaceService.search` 仍调用旧 `WorkspaceTextSearchService`，返回 fragments/line_hints/top_k；新增 `search_retrieval` 才是 Action 使用的统一协议。旧 candidate_limit/default_top_k/max_top_k 等配置和大量旧搜索测试继续服务独立路径。

新 query 没有适配原生 matcher，而是对 `title + 拼接后的 evidence` 使用公共 regex/count。内容先被切成展示单元，再通过换行拼接回“可检索文本”，导致匹配范围被改变，也没有原生的列位置和邻近行语义。

隔离复现：

- 文件正文为 `intro\nneedle\ntail\n`，查询 `^needle$`：原生逐行 matcher 命中 1 行，新统一入口返回空集。
- 长行在第 2,000 字符附近包含跨单元的完整 `needle`：原生 matcher 命中 1 行；新入口在正文中间插入换行，返回空集。

建议：只保留一个 SDK/Action Search 入口；原生 matcher 留在 Workspace owner 内，输出完整匹配成员及真实行/列/正文范围，再交公共管道。匹配应发生在 owner 原始内容上，内容切片用于后续披露，不能反过来定义匹配文本。移除已失去独立业务职责的旧外部协议和配置。

### R3：Home Reflection 的 Search 读取 effective Home（已接受）

状态：`dropped`；维护者于本次后续讨论明确接受该读取语义。原判定来自 r4 §15.4 的 profile 来源视图描述，现以维护者最新确认更新，不再列为实现缺陷。

位置：`plugins/home/plugin.py:133-160`；`services.py:30`。

`extend()` 根据 profile 计算 actual，并将其传给 Background segment；但 `queries()` 闭包始终调用未传 actual 的 `owner.search_corpus()`。因此 Reflection 的背景使用 actual，search 却使用 effective。HomeService.inspect 也直接绑定默认 effective 的 owner.inspect。

隔离复现使用真实 HomePlugin 装配：actual 文档不含 `unaccepted overlay text`，仅 overlay 含该内容；HOME_REFLECTION 的 HomeService.search 仍能按该文字召回它。

确认后的边界：普通 Search 可供 Reflection 探查 effective Home；当前通用 Inspect 也读取 effective Home。Background 基线与受约束 review/diff 服务仍按各自实际职责工作，读取 overlay 不表示它已被接受进 actual Home。撤回“强制查询/读取与 Background 使用相同视图”的建议，不改写归档计划的历史记录。

### R4：refs 尚未成为独立、精确、稳定有序的来源

状态：`pending`；优先级：高。对应 C1/C5、§4.5/5.10/12.1、验收 3/19/23。

位置：`kernel/retrieval/policy.py:127-135`；`plugins/home/engine.py:420-433,526-539`；Memory/Workspace/Context 的现有 corpus 遍历。

- 只要 policy 开放 SELECT，parser 就强制每个 refs 请求包含 select；不是某个 profile 明确声明的业务要求。`refs → rerank`、`refs → filter` 及纯 refs 均被拒绝。
- 生成的 schema 却接受这些请求。能力开放 SELECT 被错误解释为每次必须执行 SELECT。
- Home refs 按文件遍历顺序返回，未保留请求顺序；Memory/Workspace 同样按各自资源目录遍历，Context 的多个来源也按 segment 汇集。
- `home:skills@design#L6` 会进入 skill_seeds 分支，被扩大成完整 Skill，fragment 丢失，深层资源正文也进入候选。

隔离复现：上述三种 refs 请求通过 JSON schema，parser 全部报 `Refs source requires an explicit select step`；Home 反序请求得到正向目录顺序；top#L6 请求带出了 deep.md 中的 zephyr 内容。

建议：来源只解释身份与读取范围；是否 filter/select/rerank 由显式 steps 决定。owner 先规范化请求 refs、保序去重，再准备精确范围。query/directory 的 Skill top 聚合规则不能自动套用到精确 refs/fragment。

### R5：Home 资格过滤仍基于子文件，而非聚合候选

状态：`pending`；优先级：高。对应 C5、§8.1/11.1/15.4、验收 6/20。

位置：`plugins/home/plugin.py:57`；`engine.py:410,457-462,534-539`；`kernel/retrieval/engine.py:277`。

计划要求的 `resource_types` 没有落实；capability 仍只有 `file_type`。owner 在读取每个子文件时按 suffix 应用 where，随后才按 Skill top 去重。聚合保留首次候选 attributes，不构造完整集合属性。

正常后果：一个 Skill 同时含 .py 示例与 .md 说明；where 选择 .py 时，.md 内容先被删除，即使 query 真正命中其中说明，整个 Skill 也消失。后置 filter 则可能只看到首次子文件的 .md 属性。这不是同一候选资格的两种合法时机，而是不同判断对象。

隔离复现：包含 .py 的 design Skill，其 deep.md 命中 zephyr；`query(zephyr, file_type=.py)` 返回空集。

建议：先由 Home 建立 top/resource 的候选身份与聚合元数据，按 r4 使用集合属性 resource_types；source.where 只决定整个候选是否有资格，保留该候选应检索的内容。filter 使用同一快照属性。

### R6：result 派生丢失来源覆盖，并把旧 evaluation 当作新步骤

状态：`pending`；优先级：中。对应 C6、§9.2/9.3、验收 8/20/24。

位置：`kernel/retrieval/engine.py:100-105`；`operations.py:134-140`；`engine.py:196-249`。

SearchViews.result 只返回 candidates，SearchSession 随后建立默认 complete/stages/missing_stages 的 CandidateSet；原始覆盖不再可用。同时原 candidate.evaluation 完整保留，即使派生请求完全没有模型步骤。

隔离复现：原结果 `missing_stages=[embedding:unavailable]`，result 派生后变成 `[]`；另一个 select 结果经过空 steps 派生，coverage.steps 为空，candidate 却仍声明 `step_index=0, op=select`。

建议：result 返回同一冻结视图的来源覆盖及成员/内容；新操作保留来源事实，但重新建立本次 evaluation。无模型步骤时不发布新 evaluation，旧视图翻页保留原事实。

### R7：能力/schema 宣布可用的日期过滤在 owner 内被拒绝

状态：`pending`；优先级：中。对应 C1/C5、验收 6/20/21。

位置：`plugins/memory/engine.py:271,305-307`；`kernel/context/search.py:51,73-75`；`plugins/workspace/engine.py:517,549-552`。

来源入口校验传入 ordered 字段；实际候选循环再次调用 eligible，却没有传 ordered。Memory.updated_on、Context.day、Workspace backlinks.day 的 before/after 因而先通过公共校验，再在有候选时成为 INVALID_REQUEST。空库可能不暴露这个差异。

隔离复现：已有一份 Memory 文档及一个 Context 事实，分别使用合法的 updated_on/day before 条件，两者均报 `Invalid ordered filter`。

建议：把 owner 的属性类型/比较能力解析成单一对象供 schema、入口校验与实际比较共用，不再在多个调用点手写近似字段集合。无须引入表达式语言。

另一个同类缺口：Memory DocumentQuery 的 schema 只声明任意 object，没有公布 document_ref 字段及互斥结构；schema 还要求 scope，而 parser 支持默认 scope。应一起核对模型看到的契约与真实 parser。

### R8：exclude_refs 没有在来源准备前生效

状态：`pending`；优先级：中。对应 §8.2、§15.2、验收 2/14/20。

位置：各 owner search_corpus/retrieval_corpus；`kernel/retrieval/operations.py:150`；`engine.py:196-199`。

owner 未消费 request.exclude_refs；公共层在 corpus 已读完后按字符串相等排除，并在 compose 再排除一次。被明确排除的资源仍消耗来源扫描/读取预算。排除身份也没有形成统一的 owner 规范化边界。

## 4. 需要讨论的语义与修订方向

### D1：LLM 判断依据是否为必需输出

状态：`pending`，后续讨论已补充具体含义与建议，尚未确认。

r4 §7.3 要求 LLM 输出候选 IDs 和 basis unit IDs；§15.3 又把 basis 选择表述为 descriptor 可选。当前实现没有 basis 选择能力，需要明确最终承诺。

进一步建议：LLM select/rerank 在同次结果中返回候选 ID 与 `basis_ids`，后者允许为空；非空 ID 必须指向该候选实际提供给模型的原文片段。不能强迫低相关的 rerank 成员或依据 metadata/Context 的选择编造正向正文依据。依据只表示模型指认的材料，不证明其推理或结论正确。JEV 保持 Score 和真实输入覆盖，不默认增加 Choice 调用；Embedding 使用实际贡献单元。三者共享内容、覆盖和结果契约，允许依据能力不同。

另一种可行语义是三类模型只承诺实际输入覆盖、不要求模型指认依据，但必须明确修订 r4 的 basis 承诺，不能仅在代码中省略。

### D2：MCP 新增 query 是否为有意扩展

状态：`pending`，需要确认范围，不影响上述确定缺口的判断。
