## 总体结论

四份计划的共同问题是：**在写计划之前没有对目标代码做充分核实**。诊断章节中大量"现状描述"是推测（部分文档自标"推测"，但推测内容大部分猜错），导致：

- 约一半任务在**重复建设已上线的功能**；
- 若干"修复"建立在**误诊**之上，会把有意设计当作 bug 推翻；
- 计划 ④ 的一半 P0 任务与 AGENTS.md 的架构语义**正面冲突**，执行即违规；
- 计划 ② 的示例代码基于**不存在的 store 结构**，无法编译落地。

建议：**不要按原样执行任何一份**。按本文逐份裁剪后的"真实增量清单"执行；被裁剪项如认为仍有价值，需先重做现状核查再立项。

## 计划①：主对话与 Context 核心优化

**裁定：阶段一（问答卡片）已于 2026-10-05 实施并经本次评审验收（commits `3a3c5ff` / `601d2a7`），阶段三在基线中早已实现，仅阶段二待执行。**

### 阶段一（WaitingResponseDock / 问答卡片）——已实施，验收结论：方向恰当

实际实施**没有**按计划①的"修复为文档流布局"执行（本评审曾指出该"修复"建立在误诊之上——覆盖层是有意的模态等待设计，非 bug），而是保留了覆盖层语义并增强，与本评审的建议一致：

- 保留模态覆盖层（`role="dialog"` + scrim），新增**可折叠**控制条——解决了"长对话被遮住"的真实痛点，且比改文档流更尊重原设计；
- 等待期间 Composer 整体隐藏（`{!pendingQuestion && <Composer />}`），把"等待时不能自由输入"从隐含缺陷变为显式语义；
- 问题文本改 Markdown 渲染；readonly 态的自填答案带字母编号（A/B/C…+1）、补充想法内联为带图标卡片；scrim 仅展开时存在；spring 进出场与顶部光泽线。

**遗留问题（实施质量，需修复后方可视为完成）**：
1. **类型检查未过**（`npx tsc --noEmit` 4 个错误，`npm run build` 会失败）：
   - `QuestionForm.tsx:117`：Markdown origin 传了 `view: "active"`、`turnId: null`、`day: null`，与 `MarkdownOrigin` 类型（`view: "live" | "history"`，day/turnId 为可选）不匹配——应传 `{ link: "", view: "live" }` 或经 `origin.ts` 的构造函数；
   - `QuestionCard.tsx:110`：`commentAsBubble` prop 声明后不再使用（使用时已硬编码 `showReplyComment={false}`）——死参数，违反项目"不留死抽象"原则，应删除该 prop 或恢复其语义。
2. **测试未同步**（`vitest run src/features/chat`：5 失败 / 121）：placeholder 文案变更（"Comment (optional)…"→"Additional thoughts (optional)…"）、readonly 结构变更（comment 移入卡内、自填答案编号化）后，`QuestionCard.test.tsx`（4 例）与 `ChatView.test.tsx`（1 例）未更新。
3. 小问题：`absolute`→`fixed` 后 dock 相对**视口**居中，NavRail（52px）使卡片中心与聊天列中心偏移 26px，Inspector 抽屉打开时 dock 会延伸其下；折叠后文案固定为 "Agent is waiting for your reply"，提交后自动折叠时语义不再准确（已答复、等待 agent 继续）；`aria-expanded` 挂在 `role="dialog"` 元素上不规范（应在控制按钮上）。

> 本节原含的" Dock 覆盖层系误诊修复 / z-(--z-overlay) 语法断言错误 / 任务 1.2 伪当前代码"等分析随实施完成移除；结论记录：计划①阶段一未被采纳，实际实施方案更优。

### 阶段二（ActivityGlimpse 容器级状态色）——真实增量，待实施

plan 灰 / success 绿 / failure 红 / timeout 橙的容器级视觉区分 + 状态图标行 + workspace/execution 摘要。注意现状文本级状态色已存在（failure 红字、exit code 着色），真正缺的是**容器级**区分；实施时先查 `components/ui/Badge.tsx` 实际 API（只有固定 `tone` 枚举，无 `size` prop）。

### 阶段三（Context 资源紧凑目录行）——无需执行

计划自引基线 commit 971b810 中已实现：当前 `BackgroundPanel.tsx` 已是默认全折叠的 ResourceCard（chevron + 标题 + 来源标签 + 字数 + 摘要行）。另注意 `resourceBody()` 对 `memory:current/latest/target` 的 JSON 元数据头解析，任何改动不得绕过。

### 计划未覆盖（属设计方案独占内容）

- detail 面板（ProcessPanel/ModelCallPanel）的全部问题：裸 `phase1/2/3`（`PHASE_META` 友好名存在于 `components/trace/semantic.tsx` 却未用）、全长 call_id、LLM trace 无耗时（`elapsed_seconds` 解析了未消费）、消息全文铺开无折叠、answer 不渲染 Markdown、ProcessTree 正序 vs Timeline 倒序无图例；
- 对话流动作断层：`agent.action` 被完全过滤（`ChatView.tsx:123`、`ConversationRows.tsx:101`），`features/trace/ActionGlimpse.tsx` 生产零引用。

## 计划②：Settings 页面卡片化与交互优化

**裁定：可执行性最低。核心诊断与现状大面积冲突，示例代码基于不存在的结构，且会加剧真实的架构问题。**

### 误诊（有证据）

1. **"配置项直接堆叠在表单中，没有卡片化分组"——错误。**
   providers/actions 等集合页已是 `ObjectEditorLayout`（左列表 + 右单对象编辑器），编辑器内已有 `FieldSection` 分组（如 `LlmProvidersPage.tsx:106,290,319`）。§4.1 自称"推测当前实现"为"一个大表单，所有 providers 展开"——推测错误。

2. **"Draft 数量只在 BottomBar 显示；修改后的配置项没有视觉标记"——错误。**
   `SettingsNav.tsx:130` 已有每页 draft 计数 Badge；字段级有脏标记（editors 完整徽标 / models 6px 脏点）；对象列表项与详情头部均有"草稿新增/已修改"Badge（`LlmProvidersPage.tsx:133`）；底栏已有草稿数/基线变化数/字段问题数 + 重置此页/放弃全部/应用配置/激活已保存配置。计划的 §5.2"导航项增加 Draft 计数（2h）"任务对象已存在。

3. **示例代码基于不存在的 store 形状——无法落地。**
   计划使用 `s.config?.llm?.providers`、`drafts["llm.providers.<name>"]` 整对象 draft；实际 `draft/store.ts:64-72` 是 `saved/active/catalog/drafts: Record<path, DraftEntry>` 的**字段级路径** draft（`llm.providers.<id>.base_url`），无 `config` 字段、无整对象 draft。计划风险节自称"保持现有 store 结构即可缓解风险"，与其示例代码自相矛盾。

4. **对目标页面的结构假设虚构。**
   - Provider 卡片假设有 `api_key` 密码输入框与 "● Connected" 状态——实际密钥值永不显示（`api_key_envs` 环境变量名 + dotenv draft，`LlmProvidersPage.tsx:360` 注释 "never displayed"），且页面 docstring 明示 "enabled is a configuration fact, never a reachability test result"；
   - ActionsPage 假设 action 有 enabled/timeout/model 可编辑——实际 Action 目录字段全部只读展示，唯一可编辑的是 `action.models.bindings`（`ActionsPage.tsx:14-16` docstring）；
   - PhaseBindingsPage 假设有 phase1/2/3 的 available_domains/available_actions 列表——实际页面只有两个任务链下拉（`PhaseBindingsPage.tsx:21-22`），无 phase3、无 domain/action 列表。

### 架构风险（最重要的反对理由）

计划要新建的 `ConfigCard`/`ConfigSummary` 会成为**第三/第四套平行控件体系**（现状已有 `editors/controls.tsx` 1250 行与 `models/controls.tsx` 559 行两套平行控件 + Interface 页第三套样式），且其表单控件用裸 `<input>` 绕开两套现有 controls。Settings 真实的首要问题是**控件语义不统一**（脏状态呈现不一致、Escape 恢复只有一套有），本计划恰好加剧它。PhaseBindings 卡片还自建了一份 `phaseInfo` 友好名，与既有 `PHASE_META` 平行。

### 真实增量（可保留执行）

- **页内 sticky 草稿提示**（DraftBanner 的痛点成立：长表单滚动时底栏在视口外）——但实现应复用现有控件与字段级 draft 模型，而非新建卡片体系；
- "放弃全部"无二次确认、字段级看不到新旧值对比——计划**未解决**这两个真实问题，且 DraftBanner 反而增加了一个同样无确认的 Discard 入口。

### 建议

本计划整体推倒重做现状分析。Settings 的优化以设计方案 §3 为准（控件库统一为正典 + Draft 可见性三件套 + 保存语义显式化），其诊断全部经代码核实。

## 计划④：Home-Memory 图形化优化

**裁定：Memory 侧命中真实缺口、可执行；Home 侧 P0 的一半与架构语义正面冲突，必须砍掉；两处核心诊断为误诊。**

### 架构违规项（必须删除，最高优先级）

**Home 的查看/编辑模式切换 + Save/Cancel 流程（§3.4 及相应验收项、API 保存路径）——与 AGENTS.md 设计语义正面冲突。**
Home/Memory 页面只读是明示设计：普通界面不取得持久 Memory、actual Home 写权限；"整理走 Reflection、编辑走对话"；review 语义由审核来源 token 保护。当前代码亦如此：`HomeContentView`/`MemoryDocumentView` 操作只有 references/copy/quote。计划把"只读"当作"缺少编辑模式"来补，执行即架构违规。这不是功能缺失，是设计的边界。

### 误诊（有证据）

1. **"Home 有 Markdown 编辑器，编辑器与预览混在一起、缺模式切换"（问题 B，自称推测）——根本不存在编辑器，问题整体是误诊。**
2. **"引用关系（含 Memory backlinks）当前是隐藏的，只能通过阅读正文发现"（问题 C）——错误。** 引用/backlinks 已在右侧 ReferencesPanel 浮层呈现。真实问题是**呈现粗糙**：等宽 ref 字符串列表、无语义标题、无 context——应改进呈现（语义化 LinkChip + 关系图谱，见设计方案 §4.2-3/§4.4），而非"从无到有建设"。
3. **"改进前"对比图大幅低估现状。** Home 已有 actual/effective Tabs、独立 Changes 面板、双模式 HomeDiffView（unified/side-by-side + 真实行号）；Memory 已有动态能力渲染的 SearchPanel、ReflectionDialog 完整链路、空库空态的真实下一步。

### 真实增量（可执行，与设计方案 §4 一致）

**Memory 侧（全部有效）：**
- 五类文档图标+色彩系统（现状 kind 徽标全部粉色，`MemoryNav.tsx:238`——计划命中真实缺口）；
- 列表元信息（日期/大小/摘录——现状 catalog 行无任何元信息，`status` 裸出枚举）；
- backlinks 卡片化（现为裸 ref 列表）。

**Home 侧（裁剪后）：**
- 目录条目的 overlay 状态标注 + Changes 计数徽标（计划 §3.3 的 source 徽标恰好能解，但计划自己不知道缺口的真实形态——它假设的是更基础的"无元信息"）；
- 内容头部去重（现状标题是 `link.replace(/^home:/,"")`，副标题又放完整等宽 link，两行几乎同一字符串）。

### 待核实项

- 计划列的后端字段需求（size/links_to/linked_by/preview/tags）全部未调研现有 API 载荷——catalog item 实际已带 `size`（前端未显示而已）。执行前先盘点现有端点，缺什么再经 `visualization/docs/demand` 提，避免让后端重复提供已有字段。
- 验收标准中"保存后正确更新资源"等编辑相关验收项随编辑模式一并删除。
- P2 的图谱视图可参考设计方案 §4.4 的两期设计（第一期 ego graph 零新依赖）。
