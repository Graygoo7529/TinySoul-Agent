# LLM API 模式与适配器重构设计草案

日期：2026-10-18。

状态：`pending`，现状核对与官方资料调研完成；以下是待讨论方案，不代表已经实现或已确认执行计划。

目标：以 API 模式组织模型接入，明确 provider、adapter、model 的关系；复用现有调用、配置保存和前端草稿机制，消除重复规则及 SDK 隐藏行为。无需旧配置兼容层。

## 1. 已核对事实

| 位置 | 当前行为 | 需要改进的原因 |
| --- | --- | --- |
| `llm/protocol/` | TinySoul 内部消息、工具、请求、响应、模型等契约 | 保留内部协议含义，不用 protocol 同时命名外部 API 与模型变体 |
| `protocol/adapter.py` | adapter 规则、供应商选项验证与 Kimi k2/k3 分支 | 具体适配规则应归 adapter；当前通用 Chat 的 options 为空 |
| `provider/openai_sdk/` | 已有 Chat / Responses 公共请求与响应映射 | 可复用，不需要另写平行 mapper；通用 Responses 尚未单独登记供用户选用 |
| 专属 provider 模块 | 公共 adapter 子类 + behavior 对象组合 | 定制入口重复；统一为通用 adapter 的明确子类覆写点 |
| ProviderSpec | adapters 列表、一个 URL、凭据环境变量 | 应按 API 模式声明入口，避免重复声明 kimi/deepseek 等实现类型 |
| ModelSpec | 单一 adapter、有序 provider_model bindings、能力及两组参数 | 基础关系正确；保留稳定 ID 和有序 binding |
| execution/task.py | task/call 设置、model overrides、provider/model 重试切换 | 保留唯一调用协调者，加入通用 top_p |
| SDK 初始化 | 未显式关闭 OpenAI SDK 重试 | 本地 SDK 默认重试 2 次，会叠加已有任务重试 |
| 前端模型与 provider 页面 | 根据 provider.adapters 筛选；从后端读 options/protocols | 改为 api_mode 匹配，继续消费后端规则，避免前端重写供应商知识 |

当前 `openai` adapter 实际是 GPT 的 Responses 行为；`openai_compatible_chat` 是通用 Chat。Kimi 的 `protocol=k2/k3` 是专属行为分支，两者仍使用 Chat API。Family 和 collapsed 已经只用于展示；模型文件按 family 组织。

现有异常主线合理：ConfigError → 配置边界；ProviderError → LLM 局部重试/切换；TaskFailure → 已完成调用的协议反馈；LLMInvocationFailure → 无法继续的模块失败；`run` 通过 RuntimeLLMBridge 进入 Runtime，`invoke` 保持可组合。重构继续遵循此分层。

本地环境已安装 `openai==2.36.0`，未安装 `anthropic`、`google-genai`；没有真实远端调用验证。参考材料在 `reference/api_mode/`，该目录被现有 `.gitignore` 忽略；本文件独立记录需要版本管理的设计结论。

## 2. 术语与所有权

| 概念 | 负责什么 | 例子 |
| --- | --- | --- |
| 内部协议 protocol | TinySoul 的消息、工具意图、调用输入与输出 | MessageStack、TaskCall、RawResponse |
| API 模式 api_mode | 线上请求/响应结构及 SDK 调用入口 | openai-chat、openai-responses、anthropic-messages |
| Adapter | 从内部协议转换到一种 API 模式，并解释响应 | openai-chat、gpt、kimi、deepseek |
| Adapter variant | 同一 adapter 内有实际语义差异的行为分支 | Kimi 的 k2/k3 |
| Provider | 可独立启停的一组服务入口及其共享凭据 | orca、openai、deepseek |
| Model | 任务引用的稳定逻辑模型、能力、选项与 provider chain | gpt-sol、deepseek-pro |
| provider_model | 特定 provider 接受的不透明远端名称 | openai/gpt-5.6-sol |
| family / collapsed | 展示分组、文件组织与默认折叠 | GPT、DeepSeek |

Provider 不再声明模型 adapter 列表。Model 仍只选择一个 adapter，api_mode 从 adapter 的后端定义派生；不让用户重复填写 model.api_mode，也不允许 binding 再选择另一个 adapter。

Model adapter 与 family 没有强制同名关系。新 family 可以使用通用 adapter，不需新增 Python 类。模型 ID、provider ID、API 模式和 adapter ID 使用 lower-kebab-case；Python 包名、字段名仍用 snake_case。远端模型名及外部参数值保持供应商原样，不做全仓字符串替换。

Kimi 的配置从 `adapter_options.protocol` 改为 `adapter_options.variant`；目录、类型、catalog、前端标签与文档统一称“适配变体”，不根据 provider_model 字符串推断变体。

## 3. API 调研对设计的约束

| API 模式 | 思考控制 | 原生回放状态 | 缓存要点 |
| --- | --- | --- | --- |
| OpenAI Chat | reasoning_effort；模型支持集合不同 | 第三方 reasoning_content 属于兼容扩展 | 支持字段随具体模型变化 |
| OpenAI Responses | reasoning.effort、summary | reasoning items / encrypted_content；摘要另存 | 不能把旧 retention 字段当成全部模型统一配置 |
| Anthropic Messages | thinking mode/budget、output_config.effort | 完整 thinking/signature/redacted blocks | cache_control，与内容块位置相关 |
| Google GenerateContent | thinkingConfig 中 level 或 budget | 与 part 关联的 thoughtSignature | 隐式缓存；部分模型还支持显式缓存资源 |

来源：[OpenAI Chat](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create)、[OpenAI reasoning](https://developers.openai.com/api/docs/guides/reasoning)、[OpenAI caching](https://developers.openai.com/api/docs/guides/prompt-caching)、[Anthropic thinking](https://platform.claude.com/docs/en/build-with-claude/thinking)、[Anthropic effort](https://platform.claude.com/docs/en/build-with-claude/effort)、[Anthropic caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)、[Google thinking](https://ai.google.dev/gemini-api/docs/generate-content/thinking)、[Google caching](https://ai.google.dev/gemini-api/docs/generate-content/caching)。

额外发现：Google GenAI 是 SDK，当前官方文档还区分 Interactions API，并推荐新接入使用它。它的请求结构、状态与缓存不同，应使用单独的 `google-interactions` 身份；`google-generate-content` 明确表示 GenerateContent，不能让同一个 api_mode 随 SDK 升级改变含义。[Google Interactions](https://ai.google.dev/gemini-api/docs/interactions-overview)

SDK 代为发送 HTTP 和认证头，不消除 header 概念。额外路由头、版本头或环境变量引用仍属于 provider endpoint。Google 云端 IAM、Bedrock 等接入不自动被“URL + API key”涵盖，本轮不引入无消费者的认证框架。

## 4. Provider 配置

建议使用按 API 模式命名的 `endpoints` table；每个模式一个入口，provider 级 enabled 和凭据保持现有语义。以下仅为结构示例，域名不表示已验证服务：

```toml
[llm.providers.gateway-main]
enabled = false
api_key_envs = ["GATEWAY_API_KEY"]
headers = { "X-Client-Name" = "TinySoul" }

[llm.providers.gateway-main.endpoints.openai-chat]
base_url = "https://gateway.example/chat/v1"

[llm.providers.gateway-main.endpoints.openai-responses]
base_url = "https://gateway.example/responses/v1"
headers = { "X-Route" = "responses" }
header_refs = { "X-Route-Token" = "GATEWAY_ROUTE_TOKEN" }
```

- 共享 api_key_envs 只保存一次，继续按现有顺序取首个已配置值。普通 header 放 headers，敏感 header 保存环境变量引用；复用 Infra 现有 credentials 设施。
- provider 可声明共享 headers/header_refs，endpoint 可局部覆盖；先分别解析两层，再由 endpoint 同名项覆盖共享项。标准认证由 API client 处理。前端只展示凭据名称与状态，不投影密钥值。
- 不另加 endpoint ID、优先级、enabled、模型白名单或 adapter 白名单。删除 endpoint 表示不再提供这个模式；同模式确需不同服务/凭据时，新增一个 provider 即可。
- `base_url` 保存该模式 SDK 接受的根地址，前端按模式提示路径约定；不统一补 `/v1`。未来 Google 的 API version 等字段随实际 adapter 一起引入。
- Provider 启用仍要求本地凭据就绪，不进行隐式网络探测。禁用 provider 可继续保留在模型链中。

兼容判断统一为：`adapter.api_mode in provider.endpoints`。是否启用单独决定运行可路由性，不把禁用 provider 从编辑候选中永久隐藏。API 模式匹配并不证明远端模型存在、所有扩展参数可用；用户继续显式填写 provider_model。

一个逻辑 Model 的各 binding 继续承诺同样的能力和选项。若某条服务路由实际提供不同的能力，应另建模型配置，不逐渐给 binding 添加另一套 options/overrides。

现有模板映射：orca 的 adapters 列表合并为 Chat 与 Responses 两个 endpoint；openai、wenrugou、sublyx-proxy 配置 Responses；deepseek、kimi、glm、minimax 配置 Chat。仅迁移当前声明过的能力，不因服务名称猜测它还支持其他接口。development/standard 共用结构，各自保留正常可编辑的启用状态与路由顺序。

## 5. Adapter 组织与复用

建议 `tinysoul/llm/provider/` 改为 `tinysoul/llm/adapter/`，保留 ProviderSpec 表示服务供应商。拟采用：

```text
llm/
  protocol/                 # 内部调用、消息和响应值对象；只留必要身份类型
  config/                   # TOML 边界、provider/model/task 解析
  adapter/
    base.py                 # ModelAdapter / AdapterRequest / 供应商失败分类
    catalog.py              # API 与 adapter 选项规则，组合与前端投影
    factory.py              # 显式装配，公共入口
    registry.py             # 唯一 client 与绑定 adapter 生命周期 owner
    openai/
      client.py             # AsyncOpenAI 装配、SDK 异常边界
      chat.py               # OpenAIChatAdapter
      responses.py          # OpenAIResponsesAdapter
      ...                   # 复用现有 payload、response、tool-name helpers
    models/
      gpt.py                # GptAdapter(OpenAIResponsesAdapter)
      kimi.py               # KimiAdapter(OpenAIChatAdapter)
      deepseek.py
      glm.py
      minimax.py
  execution/                # 任务、模型链、provider 链与局部恢复
```

通用 adapter 自身可以被模型选择。现有 `openai_compatible_chat` 改为 `openai-chat`，现有 `openai` 专属 adapter 改为 `gpt`，新增可选择的 `openai-responses`。其他专属 adapter ID 保持现有清晰名称。

通用类负责消息、工具、输出格式、usage 和 stop reason；专属类只覆写确有差异的参数/约束/响应处理。现有薄子类再注入同职责 behavior 的双层定制可收敛为受保护方法，不再创建一层重复的 strategy。SDK 客户端注入仍保留，便于资源复用与无网络测试。

后续真实接入 Anthropic / Google 时，按同一边界增加对应模块。当前不创建空目录、不可用枚举项或前端可选但无法执行的 adapter。

Client 按 `(provider_id, api_mode)` 创建并复用；绑定 adapter 按 `(provider_id, adapter_id)` 取得相应 client，由实际 Model 引用推导需要的组合。Registry 唯一拥有 client，adapter 借用；generation 结束或装配失败时关闭一次。保留单一公开装配门面，不新增第二套 provider 服务或动态插件发现平台。

## 6. 选项定义与层次

规则层次为：API 模式的通用规则 → 专属 adapter 的增补/限制 → variant 的增补/限制 → 当前 model 的值。规则组合只在后端完成，前端消费有效字段及来源标识。复用当前 AdapterSpec/AdapterOptionSpec 的职责，不做通用 schema 编程语言。

- `ApiModeSpec` 提供该模式通用 adapter 的规则；它不承诺所有兼容服务支持所有选项。
- `AdapterSpec` 指向唯一 api_mode，声明新增、替换或禁用规则；variant 仍只是有限命名分支。
- adapter 配置解析后成为明确 typed options，运行期不用多个模块反复从宽泛 dict 解析同一值。具体 dataclass 归对应 adapter，不把所有供应商字段塞进一个万能类型。
- catalog 暴露已组合的选项、类型、可选值/建议值、适用变体与来源。服务端校验是权威边界，前端只做即时编辑检查。

需要区分真实协议限制与模型易变的可选档位。缓存模式、thinking 对象形状等可以有固定校验；某个模型支持哪些 effort 不应永久硬编码在全局 adapter 枚举里。

### 6.1 Request overrides

`request_overrides` 仍表示模型对通用请求参数的固定覆盖，不是任意 JSON 请求体。增加 `top_p`，与 temperature、max_output_tokens 同级；Task CallSettings 和任务编辑页同步支持 top_p。

优先级明确为 task settings → 单次 call settings → model.request_overrides → adapter 必要的协议归一化。最后一步只能执行已声明的规则，例如思考模式不接受采样参数，不可在 HTTP 400 后猜测性删字段重试。

top_p 是 nucleus sampling 的累计概率阈值，不是模型的置信度。通用边界验证有限数值及合理范围，API/模型进一步限制由 adapter 解释。temperature 与 top_p 都允许配置，界面提示通常选一种调节方式，不强加所有 API 都不允许二者并存的错误限制。

对于不接收采样参数的通用 API 模型，可提供简单的 adapter 选项 `sampling="omit"`；默认 `pass-through`。专属 adapter 可以声明更准确的约束，例如当前 GPT 推理规则；UI 据此说明实际会省略哪些参数。这样不需要给 TOML 引入 null 或让用户通过 extra_body 覆盖 temperature。

### 6.2 思考强度的声明与选择

按照用户建议，编辑可用档位时输入逗号分隔文本，模型主面板用下拉框选当前值。持久化保持数组和单一选择分离：

```toml
[llm.models.example-latest]
family = "Example"
collapsed = false
adapter = "openai-responses"
providers = [{ provider = "gateway-main", provider_model = "vendor/model-latest" }]
context_window_tokens = 131072
capabilities = ["text_input", "tool_calling", "reasoning_output"]
reasoning_effort = "xhigh"

[llm.models.example-latest.adapter_options]
reasoning_efforts = ["high", "xhigh", "max"]
reasoning_keep = "encrypted"
reasoning_summary = "auto"
store = false
sampling = "omit"

[llm.models.example-latest.request_overrides]
max_output_tokens = 32768
```

这是 schema 示例，不表示该虚构模型真实支持这些档位。

- `adapter_options.reasoning_efforts` 是该模型的适配能力声明，只供校验和控件使用，不直接发送给供应商。AdapterOptions 的定义应相应改为“适配声明与专属行为设置”，不是原样转发的请求字典。
- 顶层 `reasoning_effort` 是选定值，只存一份；不再同时保留 adapter_options.reasoning_effort。必须属于声明列表。
- 不配置选定值表示不发送 effort，使用远端默认；字符串 `none` 只在模型明确支持时代表实际档位，不等同于没有配置。
- 输入 `high, xhigh, max` 后去外围空白、去重并保序，写入 TOML 数组。删除当前选中档位时明确要求重新选择或清空，不静默改选第一档。
- API/variant 不支持 effort 时不显示该控制，并在后端拒绝相关配置；思考 budget 单独保留，不把 token budget 换算成虚构档位。
- 当日实现使用的 Kimi k3 max、DeepSeek low/high/max 等集合迁入相应模型配置；新增模型版本支持档位时可编辑 TOML，不用改全局枚举。现有固定协议限制仍由 adapter 保证。
- 本轮 effort 仍是模型级选择，任务链只选模型；不再引入任务级 effort 标签、模型版本快照或 binding 参数覆盖。

### 6.3 通用 adapter 的可用能力

通用 Chat/Responses 都应具有正常的文本/图片、工具、JSON 对象、采样、输出上限、思考与缓存映射；仅呈现该模式实际支持的选项。一般 Responses 的 summary、加密推理回放、verbosity、store、缓存等规则下沉，不再只有 gpt 能用。

对于常见 Chat 兼容差异，提供有限的 `output_token_field` 选择（max_completion_tokens / max_tokens），由专属 adapter 给出自己的规则；它只决定通用输出上限如何映射，不额外保存第二个 token 上限值。

Chat 的 reasoning_content 可作为显式启用的常见兼容扩展，不能冒充所有 Chat endpoint 的标准能力。新模型需要额外 body 字段时，可使用 `adapter_options.extra_body` 的 JSON 对象；它只能补充未由框架/typed 选项占用的字段，不能覆盖 model、messages/input、tools、输出协议或已经映射的参数。校验后的扩展仅在 SDK 边界传入，不新增第二套 HTTP 客户端。

extra_body 能解决请求扩展，不能描述任意响应解析、签名回放或工具协议。出现真实不同的响应语义时增加专属 adapter，避免发展成字段映射 DSL。

## 7. 推理状态、缓存与内部协议

以下四件事分别表达：思考模式/投入、可见推理摘要、原生推理状态回放、输入前缀缓存。不能统一成一个“推理开关”或“缓存开关”。

当前 Reasoning.content/summary 可保留语义；encrypted_items 的命名只适合当前 Responses。建议以一个有来源的原生回放载荷替代裸 encrypted_items：包含 API 模式、adapter/variant、provider 与远端 model 身份，以及由相应 adapter 校验的 JSON 载荷。当前 Chat 文本回放和 Responses items 是实际消费者；不预造尚未实现的 Anthropic/Google 载荷类型。

来源用于当前已有的模型/provider 切换主线：默认只在匹配的调用来源回放不透明状态，不因 API 模式相同就把一家的签名发给另一家。无法原生回放的历史工具交换沿用现有文本投影路径，保留行动与结果事实；这是 TinySoul 的默认回放策略，不宣称供应商绝对不支持跨平台签名。

`reasoning_keep` 本轮继续表达 none/content/encrypted 这些已消费的选择，由 adapter 约束可选项；不为未来模式预填空壳枚举。以后接入完整 block/part 回放时，再增加对应原生策略及关联结构。不能以当前 envelope 已有 JSON 为由宣称完整兼容所有未来 API。

状态仍附着在已有 AssistantMessage/Trace，不新增 provider 私有会话历史。Kernel 只运输 typed envelope，不解析供应商字段。Context 的投影、容量统计和安全 Observation 同步消费它，可读界面不显示加密正文。

PromptCache.key 继续只是现有 key hint，不把它扩张成跨 API 缓存资源句柄。模型缓存选项归 API/adapter；OpenAI 新缓存字段按 SDK/端点支持映射。Anthropic 内容断点、Google 显式缓存的创建与生命周期，留给相应 API 真实接入时设计，不为目前不存在的消费者建立缓存管理器。

## 8. 调用与错误处理主线

```text
TaskCall + TaskSpec
  → 选择稳定 model ID
  → Model.adapter 确定 api_mode 和有效规则
  → 有序 binding 选择 provider 及 provider_model
  → provider.endpoints[api_mode] 取得 URL / headers / client
  → 合并通用参数、模型覆盖、选定 effort
  → adapter 映射消息/工具/专属参数
  → SDK 一次请求
  → adapter 归一化 RawResponse
  → LLMTaskRunner 解释任务结果，或按既有策略重试/切换
```

1. ConfigError 尽早报告缺少 endpoint、非法 effort 选择、变体选项冲突和未知键；失败候选配置不持久化。
2. ProviderError 继续表达服务错误及 provider/model scope。已知 SDK 鉴权、限流、超时等只在 adapter 边界映射；原始异常链仅用于调试。
3. SDK 重试设为 0，由 Task retry policy 唯一管理。取消、剩余时限与关闭流程复用现有机制。
4. 已返回但不满足任务输出契约的响应继续是局部 TaskFailure，不被重写成无限重试。无法继续才进入模块失败及 Runtime bridge。
5. 缩窄 create 周围异常捕获：SDK 失败与 TinySoul 内部缺陷分开，不能把 TypeError 等实现问题包装成供应商瞬时错误。Observation 仅携带稳定 kind、scope、路由身份等摘要。
6. SDK 不自动执行业务工具、不维护另一份上下文；未来使用 Google SDK 时关闭自动函数调用，并明确关闭或接管自动续写，保持一次 LLM Task 的时限和预算可解释。

## 9. 前端改动预览

Provider 页面：顶部编辑 ID、启用状态和共享凭据；下方为“API 入口”列表，每项显示模式、URL、附加 headers。增加一个模式即增加一个 endpoint 表。去除 kimi/deepseek 等 adapter 多选框。

模型创建：已有/新 family → 唯一 adapter → 自动显示 API 模式 → 兼容 provider → 远端模型名。通用 adapter 与专属 adapter 在同一选择器中按 API 模式分组。保留现有 family 文件创建与统一 TOML 保存机制。

模型详情：主面板放稳定 ID、family、adapter/API 模式、provider chain 与选定思考强度；高级区显示“可用档位”输入框、通用 API 选项、专属选项/变体、请求覆盖。选项来源可用简短标签区分，实际可编辑列表由后端组合。

切换 adapter/variant 时，保留仍兼容的 provider binding 及公共设置，清理不适用选项；变化作为同一草稿提交，并在已有 diff 中可见。不创建静默重写已保存配置的新流程。

任务链：继续引用稳定模型 ID，保留共享 ModelPicker 的 family 胶囊、搜索、折叠和单一模型替换；通用参数编辑增加 top_p。运行方案继续只保存声明的任务链、路由与预算，不复制 provider endpoint 或物理模型版本。

配置应用：仍走 TOML source → Infra → LLM parser/catalog → Endpoint → draft → apply/reload。Endpoint 只扩展结构化投影与契约文档，不增加任意文件写入接口。失败沿现有请求错误流程，保留编辑草稿。

## 11. 可行性与待讨论项

可行性：现有通用 mapper、ModelProviderBinding、配置 source 写入、catalog 投影、family ModelPicker 和 TaskRunner 均可复用。主要工作是配置模型/规则归属与前后端编辑联动；不需要重建 Context、Agent 调度、Runtime bridge 或运行方案机制。

建议本轮落地范围：完整改造现有 provider/model，开放通用 Chat 和 Responses；四类接口的边界进入设计，但 Anthropic/Google adapter 与 SDK 在有真实接入目标时实施。前端只列实际可运行的模式。这与“本轮先改造现有模型，但架构按 API 模式设计”一致。

需讨论的设计选择：

1. 是否采用上述本轮范围，还是本轮就同时接通 Anthropic 与 Google？若扩展 Google，需要选择实际服务提供的 GenerateContent / Interactions，不能仅指定 SDK 名称。
2. 通用 adapter 是否开放受约束的 extra_body？建议开放，以覆盖代理扩展和较新请求字段；不开放任意响应映射。
3. 是否接受 `adapter_options.reasoning_efforts` 声明候选、顶层 `reasoning_effort` 选择这一持久化结构？建议采用，匹配期望交互，并避免标签或版本别名系统。

以上选择确认后，再把本草案转为按实际文件逐项勾选的执行计划；当前不能标记为准备实施或已完成实现。
