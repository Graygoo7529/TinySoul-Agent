日期：2026-09-27（Asia/Shanghai）。

状态：`pending`。本稿是改动预览与讨论材料，未授权实施、未修改生产代码。事实依据见 [实施复核](../analysis/20260927%20检索重构实施复核.md)；r4 的已归档验证记录保留历史意义，不代表本稿缺口已经解决。

## 1. 保留已成立的整体设计

继续使用一个 Action 执行体系、一套模型用途绑定、一套 `source + steps + page` 协议。Agent 选择来源、业务条件和有限函数组合；用户配置 query 通道、select/rerank 实现与模型用途。这里需要修正的是契约在各层之间的传递，不需要增加新一套 Search 模式或按插件派生 selector。

三类发现来源是 query、backlinks、directory；refs 提供显式已知入口，result 提供当前 lease 内已冻结集合。后三类操作 filter、select、rerank 处理当前集合。没有操作步骤也是合法请求。filter/select 保留输入相对顺序，rerank 保留全部成员。

本稿列出的工作组成同一轮完整修订；下文顺序表示实施依赖，不把内容依据、owner 适配或配置清理延后成未定义的演进工作。

## 2. 两个待确认点究竟影响什么

### D1：判断依据与实际输入覆盖

例如 query 返回的 `home:skills@design` 候选聚合了入口文档和深层资源，其中一段是通用介绍，另一段说明“按供应商隔离向量缓存”。使用 select 判断“哪些资料能帮助处理向量缓存”，模型选择了该 Skill。

只返回候选 ID 能说明“选中了谁”，框架也能记录“给模型看过哪些内容”；但框架不知道模型希望突出哪一段。如果页面默认展示入口开头，即使选择正确，Agent 仍看不到有用材料。

`basis_ids` 让模型在同次回答中指认已经提供的片段。框架通过 ID 提取对应原文，附真实资源 ref 和范围。它不要求模型重写原文或给出长篇推理，也不能证明这段话必然导致了该判断。可验证的是身份和读取范围，语义是否充分仍可能判断错误。

建议收敛为以下固定实现契约，不另设没有真实使用差异的可选模式：

| 实现 | 返回什么 | 怎样形成展示依据 |
| --- | --- | --- |
| LLM select/rerank | 候选 ID、可为空的 basis_ids | 在同一次生成中指认实际输入片段，校验后引用原文 |
| JEV select/rerank | 每候选 Score；select 依用途阈值保留成员 | 记录真实输入覆盖；沿用来源命中或普通内容预览，不宣称 JEV 指认了某段 |
| Embedding rerank / query 通道 | 相似度及实际贡献内容单元 | 保留计算产生的贡献单元；相似度不被表述为模型的文字理由 |

LLM 的 `basis_ids` 字段存在，但允许空数组：rerank 中低相关候选仍须保留；部分判断依赖属性、Context 或“缺少相关材料”，不存在必须引用的正向命中。非空 ID 必须属于该候选实际输入的片段，不能引用快照中未展示给模型的单元或其未展示部分。错误 ID 是本次操作协议失败。

示意输出为 `{"items":[{"id":"c0","basis_ids":["u3"]},{"id":"c1","basis_ids":[]}]}`。select 中顺序仍以输入集合为准；rerank 中 items 必须构成完整排列。空依据不删掉候选，也不制造正文理由。

这是对上一轮“LLM 返回依据”建议的精确化：保证存在指认机制，不要求每个判断都假装有正向正文证据。替代方案是所有实现仅承诺输入覆盖、完全不提供 LLM 指认；其代价是 select/rerank 后页面不能按模型指认材料定位，且须明确缩减 r4 的依据承诺。

### D2：MCP 是否保留词法 query

原 r4 给 MCP 的发现入口是 directory：枚举指定服务的真实工具定义，再用 select/rerank 理解自然语言需求。当前代码额外开放了 literal/regex query，对名称、描述和参数定义进行词法匹配。

两个入口服务不同的正常需求：

- 已知名称或参数，如 `read_file`、`max_results`：query 可以直接定位相关定义，无须先调用语义选择模型。
- 只知道“读取项目配置文件并返回正文”：directory → select 可以选择名为 `fs.readResource` 的工具，即使需求文字与工具名没有重合。

建议保留现有 query 能力并正式纳入设计。它是同一来源准备、内容快照、步骤和分页链路中的词法通道；没有隐藏工具执行、额外索引或另一套模型搜索器。directory → select 不经过 query 预筛，MCP 不因此声明 Embedding 能力。

删除 query 也能满足 r4 原定范围，但会失去直接定位工具定义的便利性；不建议仅为维持旧清单而删除真实有用的能力。

## 3. 统一数据流与职责

```text
owner 解释范围、规范身份、资格和排除
  → 真实来源内容与位置
  → query 通道 / 真实入边 / 目录或显式 refs
  → 有序 CandidateSet（内容快照 + 来源依据）
  → filter / select / rerank 的显式组合
  → 冻结 SearchView
      → SearchPage：展示一页成员及原文预览
      → result：复用完整集合继续操作
```

内容快照由 owner 的实际资源生成，受既有 Turn/profile 或 SDK lease 管理。共享 retrieval 不成为正文的持久 owner，也不反向解析插件的路径、fragment 或工具字段语法。

### 3.1 内容、证据和投影各自只有一个职责

沿现有类型演进，优先调整 `contracts.py`、`engine.py`、`selection.py`、`disclosure.py`，不为六个操作各建一组平行类：

- `ContentUnit` 保存唯一一份不可变真实内容、来源 ref 和位置；长行切片保留字符位置，不能把不同片段都说成同一完整行。结构化来源保留其字段位置。
- `SearchEvidence` 引用内容单元及其中实际范围，表示词法命中、向量贡献、真实引用边或模型指认；不再另存一份可单独裁剪的正文。
- `SearchCandidate` 表达结果身份、标题、属性与所属内容单元；`CandidateSet` 表达有序成员、来源覆盖及本次操作事实。成员、内容与模型判断不混成一个反复改写的 JSON 对象。
- 共用内容投影函数为模型输入与最终页面生成片段。投影保存回原内容的映射；模型使用的短 ID 指向实际输入片段，包括其真实子范围。

select/rerank 返回成员或排列、分数与依据映射，再与原内容快照组合；不能重建候选时只复制 score 而丢掉 Embedding 的贡献片段。页面缩短也不能改写来源内容或模型实际输入事实。

### 3.2 覆盖、预算和预览顺序

下面四个问题必须分别回答：

| 事实 | 含义 | 不能由什么代替 |
| --- | --- | --- |
| 来源完整性 | 显式资格范围是否完整处理、哪些 query 通道实际参与 | 本页是否还有下一页 |
| 内容快照覆盖 | 保存了全文、摘录还是只有 metadata | 模型输入长度 |
| 模型输入覆盖 | 本次实现实际使用了哪些内容 | 预先为另一种实现准备的摘录 |
| 页面预览覆盖 | 此页实际展示了哪些内容 | 来源或模型已处理全文的声明 |

全文、摘录、metadata 使用同一有限覆盖语义，但分别归属各自投影。source_complete 只表达来源处理事实；非文本资源的 metadata 不冒充正文已被读取。

沿用来源读取预算、快照预算、操作输入总预算、页面预算的职责划分。操作预算检查包括 criterion、可选 Context、指导、协议提示或问题，以及实际序列化的候选材料。LLM/JEV 的片段输入由共用投影确定，Embedding 按实际参与向量计算的单元记录覆盖。不能统一截成 4,000 字后把所有实现都标成相同覆盖。

模型步骤让当前全部成员参与，允许长内容明确摘录；现有候选内容上限收口到共用投影规则，不在各实现中另写截断。总输入仍超预算时返回 scope_required，不通过隐式 top-k 删除成员，不追加自动摘要或多轮内部搜索。具体字符上限用正常样例验收，属于实施参数，不再成为平行语义开关。

投影优先展示当前步骤指认的材料，再展示来源贡献命中；没有依据时展示明确标记的普通内容预览。混合召回的 lexical 与 Embedding 命中按来源分配片段空间、去重，不能让第一条 lexical 片段吞掉全部预览。模型指认和来源命中使用各自标签，低分依据不能标成正向语义命中。

页面字符预算决定每页容纳多少候选；预览可缩短，但必须保留可解释的真实片段与位置。连一个有意义的候选展示都容纳不下时明确反馈预算问题，不返回只有 ref 的伪完成页。成员续接复用 SearchViews；更深正文通过 owner 的 Inspect/read/describe 打开，不新增一套 Search 正文游标。

### 3.3 result 与 Context

result 复用原视图的完整最终成员、顺序、内容和来源覆盖，不读磁盘、不重做 query。新请求的模型评估从空开始；旧模型分数、basis 和 step_index 不伪装成新步骤。原视图继续保留原评估供原分页读取；派生视图保留来源命中，当前操作重新产生判断材料。保留原结果身份作为来源即可，不累积多轮评估历史或复制日志。

一次请求中 `context=current` 使用同一份已构造的 Context 快照；新的请求可使用变化后的 Context。因此同一 result 可以在新语境下重新 select/rerank。`criterion` 明确表达“尚未解决的部分”“已经尝试失败的方式”等当前目标，不自动继承 query 作为每一步 criterion。

`exclude_refs` 由请求显式提供，按 owner 的候选身份生效；seen、低分或未被选中均不自动形成黑名单。辅助模型调用仍不能解除 Inspect 展示保护。无需新增语境检索状态机或持久负反馈库。

## 4. owner 来源及公共契约的改动预览

| 范围 | 拟改动 | 改完后的正常行为 |
| --- | --- | --- |
| 公共 refs | 移除强制 select；由 owner 规范身份、范围并保序去重 | 纯 refs、refs → filter、refs → rerank 均成立，fragment 不扩大 |
| Home | 先形成候选身份及聚合 resource_types，再应用 where；query/directory 按 Skill top 聚合 | Skill 包含 .py 即可取得资格，其 .md 的相关内容仍参与检索 |
| Workspace | 仅保留一个公开 search；原生 matcher 接入公共 query 通道，直接匹配原始正文并返回位置 | 逐行锚点和跨披露单元文本仍可命中；行列位置进入同一候选协议 |
| Memory / Context / Workspace | 来源与 filter 共用解析后的属性比较条件 | 同一日期 before/after 在 schema、请求校验与实际匹配中一致 |
| 各 owner 的排除 | 在读取候选正文前按规范身份执行 source.where/exclude；result 只用冻结身份 | 明确排除的正文不消耗内容读取预算，排除不依赖当前磁盘存在性 |
| MCP | 按 D2 保留真实目录上的 lexical query，directory 与语义步骤独立组合 | 已知词汇直接定位；未知表达通过内容模型发现 |

Home 的精确读取特别明确：`refs(home:skills@design)` 读取该入口实际对应的 SKILL.md，`#L6` 只读其第 6 行，与 Inspect 的入口含义一致；它不因 query 曾按 top 聚合而自动读取所有深层资源。需要继续处理之前发现的完整聚合内容，使用 result；需要某个深层文档，显式给它的 resource ref。query/directory 的聚合是发现时的候选准备规则，不改变 Link 本身的读取语义。

Home 的 top 聚合属性使用 resource_types 集合，具体 resource 的文件类型保留 owner 明确声明的属性。集合比较和有序比较来自有限的 typed 属性声明；schema、parser、来源资格与 filter 复用同一解释，不再多处手写 supported/ordered 集合。Memory DocumentQuery 的 document_ref 等变体也由真实 typed 请求生成明确 schema。

query 的通道选择与融合继续由公共 retrieval 编排；Workspace 提供原生 matcher，其他 owner 可复用公共正文 matcher。匹配基于未被展示切片改变的内容，ChannelHit 指向原文位置，不能返回已经按展示 top_k 裁掉的成员。来源超过真实处理预算时明确请求缩小范围，不返回伪完整集合。

Reflection Home 的普通 Search/Inspect 保持 effective 读取；Background 和 review/diff 的基线职责独立表达。这是已确认的现状说明，不需要增加 profile 专属检索器。

## 5. 配置、清理、观测与接口

`action.retrieval` 注册为整体 object，Action ID 是 map 内的原子 key；读取、生成、PATCH、重载共用这种形状。编辑一个 Action 的设置时提交整个 map，不引入新的点路径转义语言。删除为错误拆分树增加的多层 wildcard 和递归补偿解析。

移除 Workspace 第二套公开 search/search_backlinks 返回协议及其仅服务旧路径的 top_k 配置；内部 matcher 继续复用。移除无生产消费者的 memory_daily 配置和对应旧测试要求；保留仍被使用的通用 llm_action task。同步 Home/Memory/Workspace/MCP 的 Action 帮助、Skill、当前设计与 Endpoint 文档。

观测沿用既有 Observation：每次模型步骤携带 search_id 与 step_index；LLM 的 TaskCall 已有 task_id，在调用边界补充它与 Search 步骤的关联即可。JEV/Embedding 的现有 ModelCallEvent 沿操作调用传入关联；query 通道记录来源阶段，不冒充 steps 中的一项。由此能区分同次请求中的两次 rerank，无须增加日志持久化或新的追踪框架。

Endpoint 路由和设置保存/重载流程继续复用。需要同步的是 retrieval capability、属性/query schema、配置整体值、SearchPage 的覆盖/评估含义和观测关联。前端无需知道内部 ContentUnit ID 的存储方式；模型用于指认片段的短 ID 也不成为跨 Turn 资源身份。

## 6. 实施依赖与验收预览

1. 固定 D1/D2 及内容、依据、覆盖的契约；调整公共类型、投影与属性声明。
2. 接通公共操作、query 通道、result 派生和页面投影；保留现有模型用途、向量缓存与 lease。
3. 按各 owner 差异接入身份、范围、属性、排除和 matcher，统一 SDK/Action 入口。
4. 清除旧配置与补偿分支，同步生成模板、Action 帮助、设计与 Endpoint。
5. 聚焦行为验证、Fast、Full、typecheck；逐项记录落实证据后再归档执行计划。

必要验证集中在真实主线：无词面重合的深层语义命中贯穿输入和页面；LLM basis 只引用实际输入；JEV 不伪称指认；Embedding 评估与贡献单元一致；refs 顺序与片段范围；Home 聚合资格不裁正文；Workspace 锚点与跨单元命中；result 保留来源覆盖并重建评估；显式排除先于正文预算；配置整体编辑可保存重载。公共契约在 retrieval 覆盖，owner 测试只补各自差异。

本次仅讨论，没有执行新的生产代码测试或真实模型调用。初次复核的 Full/typecheck 结果留在分析记录中，不作为拟议改动已经通过验证的证据。
