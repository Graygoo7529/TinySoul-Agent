（1）前端需要承接本次后端重构最新的设计语义和功能接口；
（2）前端的设置页面，需要整体重新设计和重构，可以重新调整设置页面的布局和内容，包括重新设计左侧配置分栏和配置子页面的进一步划分和设置内容，使相关设置内容的安排更让人容易理解和使用，同时配置页的划分更合理、负载更加均衡、主要配置项更突出；具体配置项在使用交互上可以让用户更容易操控，可以使用更现代化的交互方式来进行配置（如滑块来配置顺序）；此外，当前配置确认的方式应该已经改变，不再逐条同步配置，而是批量配置后重载 agent，可以考虑在批量配置无法应用时提供重置选项（即不保存修改）；在重新设计和规划设置页面时，还可以远见地预先考虑后续可能增加的配置，例如其他模型（但不是通用 llm）如生图模型、结构化模型（Jev），相关 API 的扩展性如其他 embedding 模型、其他 web search 工具配置等等。
（3）可以考虑在前端进一步区分前端自己本地的设置项和对后端进行的设置项，前端设置项例如字体、主体、字体大小等等前端常见的可配置内容；
（4）由于我们 agent 使用不同的 llm task / model chain，因此不像常规 agent 那样在调用时选择模型和推理强度，但我们考虑可以对配置内容打包保存并命名配置名，并允许在 agent 主对话界面使用不同的配置；你可以进一步设计和分析一下是对全量配置打包还是局部配置打包、是否需要后端支持、打包的配置是通过前端本地保存还是后端保存；
（5）最新的 context 设计，进一步设计和规划如何在前端合理的呈现，当前前端有按钮呈现 context 中加载的 home 内容，可考虑对于 context 中的 memory/home/session map 的进一步呈现；此外，可以考虑改进对于 turn trace 里 context/模型调用记录的呈现，结合我们最新 context 的设计语义；
（6）前端 visualization 设计会在主对话进行中，对于不同类型的 action 呈现不同的细节，visualization\docs\demand 之前有一些需求，需要后端进行对接/进一步设计呈现内容；当然，当前后端已经重构，visualization\docs\demand 的需求单已经过时，但可以进一步分析和设计当前最新后端所支持的 actions，以及如何在前端进行优雅美观的可视化呈现；这部分可以要求后端进一步提供支持；
（7）对于 ACP、MCP 等新功能接口的接入和使用，以及具体的使用情况，设计分析如何在前端进行体现；以及环境事件、Job 执行和状态、工作区监听等等；若能够有额外组件呈现子智能体运行状态、Job 执行状态、MCP 的接入情况等等就更好了；
（8）考虑在前端主对话页面对于用户追加输入/智能体提问/用户回复智能体进行风格一致、美观有序有交互的呈现；主对话界面不会遗漏这些交互信息；同时，对于智能体提问/用户回复智能体，可以考虑允许让智能体通过特定格式协议的代码块提出，前端可识别将其渲染为可交互的选项表单，用户选择 A/B/C 即可认为按照智能体提供的选项回答，且默认提供一个尾选项允许用户自行输入提供其它看法（类似 kimi code 和 cursor 等 agent 的做法）；这部分可以要求后端进一步提供支持，让智能体在提问时（可选地）按照代码块协议输出选项表单；此外，考虑模块功能的抽象统一设计，前端可以考虑设计比较统一的代码块支持能力和插件式扩展能力，类似 obsidian 的第三方插件可以自定义许多种代码块的渲染，我们以后可能考虑以 markdown 代码块为可扩展协议，让智能体生成并由前端渲染出各种视觉效果；例如 mermaid、TikZJax、flowchart；
（9）当前主要页面有主对话页面和工作区页面，可以考虑增加memory页面和home页面，来向用户呈现当前memory/home plugin 所维护数据的实际情况；如何使用数据、如何呈现需要进一步结合设计语义进一步分析和思考；其它后端重构后的状态如何在前端披露呈现也可以多多考虑；
