// 回顾一下之前提到的本轮工作初始思路和整体意图

请重新加载项目 AGENTS.md；基于我们已经完成的后端重构，下面我们考虑另一项重新设计/重构：基于当前整体项目的设计语义以及本次后端重构，对前端 visualization 也进行一次重构、扩展和改进：
（1）前端需要承接近期后端重构最新的设计语义和功能接口；
（2）前端的设置页面，需要整体重新设计和重构，可以重新调整设置页面的布局和内容，包括重新设计左侧配置分栏和配置子页面的进一步划分和设置内容，使相关设置内容的安排更让人容易理解和使用，同时配置页的划分更合理、负载更加均衡、主要配置项更突出；具体配置项在使用交互上可以让用户更容易操控，可以使用更现代化的交互方式来进行配置（如滑块来配置顺序）；此外，当前配置确认的方式应该已经改变，不再逐条同步配置，而是批量配置后重载 agent，可以考虑在批量配置无法应用时提供重置选项（即不保存修改）；在重新设计和规划设置页面时，需考虑各类模型的配置，包括通用对话 llm 以外的其他模型类型，如，生图模型、嵌入模型、结构化模型（Jev）等专用模型的（ provider）配置；在进一步使用模型时，当前需要嵌入 Model 的一些 Actions 已不再局限于只使用 llm，因此 llm_action 的命名和模型配置方式已经过时，更符合语义的是能够配置如 Search 这样的 Action 开启哪些模型，如允许切换使用 Jev or LLM、是否使用 embedding 等；但还是应该能够自定义使用 llm 的 action 所用模型链，以及最新设计里 reflection actions 相当于特殊情景下对 home/memory domain 的扩充，如果 reflection actions 使用 llm，其模型链的配置应该与其它常规 action 配置 llm 模型链方式是一致的（而非单独硬编码配置出来）；
（3）可以考虑在前端进一步区分前端自己本地的设置项和对后端进行的设置项，前端设置项例如字体、主体、字体大小等等前端常见的可配置内容；
（4）由于我们 agent 使用不同的 llm task / model chain，因此不像常规 agent 那样在调用时选择模型和推理强度，但我们考虑可以对配置内容打包保存并命名配置名，并允许在 agent 主对话界面使用不同的配置；你可以进一步设计和分析一下是对全量配置打包还是局部配置打包、是否需要后端支持、打包的配置是通过前端本地保存还是后端保存；
（5）最新的 context 设计，进一步设计和规划如何在前端合理的呈现，当前前端有按钮呈现 context 中加载的 home 内容，可考虑对于 context 中的 memory/home/session map 的进一步呈现；此外，可以考虑改进对于 turn trace 里 context/模型调用记录的呈现，结合我们最新 context 的设计语义；
（6）前端 visualization 设计会在主对话进行中，对于不同类型的 action 呈现不同的细节，visualization\docs\demand 之前有一些需求，需要后端进行对接/进一步设计呈现内容；当然，当前后端已经重构，visualization\docs\demand 的需求单已经过时，但可以进一步分析和设计当前最新后端所支持的 actions，以及如何在前端进行优雅美观的可视化呈现；这部分可以要求后端进一步提供支持；
（7）对于 ACP、MCP 等新功能接口的接入和使用，以及具体的使用情况，设计分析如何在前端进行体现；以及环境事件、Job 执行和状态、工作区监听等等；若能够有额外组件呈现子智能体运行状态、Job 执行状态、MCP 的接入情况等等就更好了；
（8）考虑在前端主对话页面对于用户追加输入/智能体提问/用户回复智能体进行风格一致、美观有序有交互的呈现；主对话界面不会遗漏这些交互信息；同时，对于智能体提问/用户回复智能体，可以考虑允许让智能体通过特定格式协议的代码块提出，前端可识别将其渲染为可交互的选项表单，用户选择 A/B/C 即可认为按照智能体提供的选项回答，且默认提供一个尾选项允许用户自行输入提供其它看法（类似 kimi code 和 cursor 等 agent 的做法）；这部分可以要求后端进一步提供支持，让智能体在提问时（可选地）按照代码块协议输出选项表单；此外，考虑模块功能的抽象统一设计，前端可以考虑设计比较统一的代码块支持能力和插件式扩展能力，类似 obsidian 的第三方插件可以自定义许多种代码块的渲染，我们以后可能考虑以 markdown 代码块为可扩展协议，让智能体生成并由前端渲染出各种视觉效果；例如 mermaid、TikZJax、flowchart；
（9）当前主要页面有主对话页面和工作区页面，可以考虑增加memory页面和home页面，来向用户呈现当前memory/home plugin 所维护数据的实际情况；如何使用数据、如何呈现需要进一步结合设计语义进一步分析和思考；其它后端重构后的状态如何在前端披露呈现也可以多多考虑；
（10）可以考虑前端设计和实现一个通用模块用来渲染和点击跳转链接，例如模型回答中可能会出现 workspace/home/memory 链接和网页链接，前三者考虑路由到相应的页面资源，后者考虑打开用户浏览器（也可以考虑内嵌浏览器，因为我们后续也可能会增加功能让 agent 来使用浏览器）；
（11）设置页面整体需要重构，但之前旧版本的 llm 模型配置/provider配置/model chain配置这一块的设计和页面逻辑是比较好的，仅需要调整的是局部组件的交互（例如拖动块进行排序），以及一些新语义适配，例如，当前 reflection 中使用的 llm 模型应当也归属于 llm action，可能在界面上不需要单独拿出来设置任务链了；另一方面，专用模型的 provider 配置等也可以参考 llm 模型的配置，先配好 provider，再在模型中排序 provider；此外一个可以考虑的规划是，有一些（但不是全部） llm action 以后可以在使用 llm chain 和专用模型（如 jev）之间切换，可以考虑对 llm actions 设置模型链的这个页面进行改进（也就是说，我是从 action 的角度出发，配置 action 内部嵌入使用的模型，而这个模型可能是llm、jev、生图、嵌入等等），从这个角度，也许应当在 action 页面来设置这一点？
（12）整体前端视觉效果，配色、光泽、动效和视觉设计等应当基于原版的风格，可适当设计优化；对话页面、工作区页面的主要布局和交互以增加新能力/界面为主（例如智能体提问卡片），需要完整重设计/重新布局的是设置页面，以及新增 Home 页面和 Memory 页面、扩充的运行时页面等；真实页面设计应该延续现有风格，页面上不要放很多小字，例如“让每一种运行事实，在合适的位置被看见”，以及“ · ”这种连接符号，真实页面是一个精心设计和应用的用户交互界面，而非一个 AI 感很强烈的 Demo 说明；
（13）其它你觉得可以进一步进一步在本次前端重构中可以设计、添加或改善的地方；请进一步思考和设计前端如何与后端、用户进行对接和交互。
